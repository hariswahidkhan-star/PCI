# Domain 3 — Budgeting & Forecasting

## KA 3.2 — Cost estimation

Every figure this book has used so far as a "base estimate" — the $7,500,000 that anchored the Northgate
Water Treatment Upgrade's budget in KA 3.1, the $600,000 Budget at Completion (BAC) that Domain 6 has
already used throughout its Pipeline Segment 4B earned-value examples — had to be produced by somebody,
using some defensible method, at some point before it could be authorised as a budget at all. This Knowledge
Area is where that number is actually built. It covers the discipline of **cost estimating**: the AACE
International Cost Estimate Classification System that names how mature (and therefore how accurate) an
estimate can be at each project stage; the three families of estimating method — analogous, parametric and
bottom-up — that PMI's PMBOK Guide and AACE's Total Cost Management (TCM) Framework both recognise; the use
of cost estimating relationships (CERs) and three-point (PERT-type) technique to handle genuine uncertainty
in a single estimate element; how time (escalation) and risk (contingency) are priced into an estimate
before it becomes a budget; and the Basis of Estimate (BoE) that documents and defends every figure once it
is issued. The running illustration is **Pipeline Segment 4B** — a buried drainage/utility pipeline within a
wider rail-corridor programme delivered by **Meridian Rail Contracting LLC**, the continuing worked entity
first introduced in KA 1.1. Where Domain 6 has so far treated Pipeline Segment 4B's $600,000 BAC as a given,
fixed number, this KA follows it back to its origin — showing, work package by work package and unit rate by
unit rate, exactly how Meridian's estimators arrived at it. Everything here feeds forward: KA 3.1 supplies
the hierarchy this KA's output slots into (base estimate → cost baseline); KA 3.3 spreads the resulting
budget across the schedule; KA 3.4 and KA 6.3 reuse the same estimating logic to forecast Estimate to
Complete (ETC); and KA 12.2 develops the quantitative risk analysis this KA's contingency treatment only
introduces.

### 3.2.1 Cost estimating in the project lifecycle: the AACE Cost Estimate Classification System

**Definition & purpose.** A **cost estimate** is a documented prediction of the likely cost of a defined (or
partially defined) scope of work, produced using a stated method and expressed with an accuracy range
appropriate to how much of that scope is actually known at the time. It is distinct from the **budget**
(the authorised figure the estimate becomes once approved — KA 3.1) and the **forecast** (the live,
periodically revised prediction of final outturn once work is under way — KA 3.4); those distinctions are
introduced fully in KA 3.4.1 and are not repeated here. **AACE International's Cost Estimate Classification
System** (Recommended Practice 18R-97, previewed in KA 3.1.2's Fig 3.1.2 and given full treatment here) is
the industry-standard framework for naming an estimate's maturity: it defines five classes, **Class 5**
(least mature, least accurate) through **Class 1** (most mature, most accurate), each tied to how much of
the project's scope is actually defined when the estimate is prepared, not to how carefully the estimator
worked.

**The underlying principle.** An estimate's accuracy is bounded by the maturity of the scope it estimates,
not by estimator skill or the sophistication of the calculation — a highly skilled estimator working from a
one-page concept sketch cannot produce a definitive-quality number, because the information needed simply
does not exist yet. The classification system exists to keep this honest: it forces a stated accuracy range
onto every estimate, so a reader cannot mistake an early, necessarily wide-range figure for a late-stage,
narrow-range one. As the project matures — more design, more quotations, more site data — the achievable
accuracy range narrows, but so does the flexibility to prepare each successive class cheaply: a Class 1
estimate can cost, in professional hours, ten to a hundred times what a Class 5 estimate cost, which is
exactly why a project moves through the classes progressively rather than jumping straight to Class 1.

*The five AACE estimate classes (illustrative, typical published ranges — confirm against the current
edition of AACE 18R-97, see SME verification; Classes 5, 4 and 3 reuse the accuracy bounds already
introduced in KA 3.1.2's Fig 3.1.2):*

| Class | Project definition (% complete) | Typical purpose | Primary methodology | Expected accuracy range (low / high) | Preparation effort (relative) |
|---|---|---|---|---|---|
| Class 5 | 0–2% | Concept screening, order-of-magnitude (ROM) | Analogous, capacity-factored, judgement (§3.2.2) | −30% / +50% | 1× |
| Class 4 | 1–15% | Feasibility / concept study | Parametric, cost estimating relationships (§3.2.3) | −20% / +30% | 2×–4× |
| Class 3 | 10–40% | Budget authorisation / control estimate | Semi-detailed unit costs, mixed parametric/bottom-up | −10% / +20% | 3×–10× |
| Class 2 | 30–70% | Control estimate / bid-tender | Detailed unit costs, substantially complete take-off (§3.2.4) | −8% / +15% | 5×–20× |
| Class 1 | 50–100% | Check estimate / definitive bid-tender | Detailed unit costs, complete take-off (§3.2.4) | −3% / +10% | 10×–100× |

*Quick reference — estimating methods and the classes they typically serve:*

| Method | Typical class | Data required | Best suited to | Weakness if misapplied |
|---|---|---|---|---|
| Analogous (§3.2.2) | Class 5–4 | One (or a few) genuinely comparable historical projects | Very early screening, pre-design | A poor comparator, or real differences left unadjusted |
| Parametric / CER (§3.2.3) | Class 4–3 | A statistically adequate historical dataset and a measurable cost driver | Early-to-mid design, repeatable scope types | A driver not genuinely linked to cost; a thin or unrepresentative dataset |
| Bottom-up / definitive (§3.2.4) | Class 2–1 | A mature, detailed scope: take-off, vendor quotations, resourced unit rates | Execution-ready budgeting, tendering | Omissions or double-counts in a large take-off; time- and effort-intensive |

**Formula.** No single arithmetic formula defines a "class" — classification is a judgement about scope
maturity against the table above. What *is* formulaic is applying the resulting accuracy range to a stated
estimate: `Expected range = Point estimate × (1 + Low%) to Point estimate × (1 + High%)`, where Low% is
negative (a downside bound) and High% is positive (an upside bound), both drawn from the estimate's declared
class.

**Example 3.2.1 — classifying and bounding Pipeline Segment 4B's estimate across its lifecycle.**

*Scenario.* Meridian Rail Contracting LLC prepares three successive estimates for Pipeline Segment 4B as the
work matures: a Class 5 analogous estimate of $644,000 at the bid stage (built in full in §3.2.2), a Class 3
parametric estimate of $610,000 once early engineering is under way (built in full in §3.2.3), and a Class 1
bottom-up estimate of $600,000 once the design and take-off are execution-ready (built in full in §3.2.4).

*Required.* The expected accuracy range implied by each estimate's class, and the actual percentage
deviation of each estimate from the Class 1 figure (taken here as the best available reference point).

*Working.*
Class 5 ($644,000, range −30%/+50%): low bound `= 644,000 × 0.70 = 450,800`; high bound
`= 644,000 × 1.50 = 966,000`. Deviation from Class 1: `(644,000 − 600,000) / 600,000 = +7.3%`.
Class 3 ($610,000, range −10%/+20%): low bound `= 610,000 × 0.90 = 549,000`; high bound
`= 610,000 × 1.20 = 732,000`. Deviation from Class 1: `(610,000 − 600,000) / 600,000 = +1.7%`.
Class 1 ($600,000, range −3%/+10%): low bound `= 600,000 × 0.97 = 582,000`; high bound
`= 600,000 × 1.10 = 660,000`.

*Answer.* **The stated accuracy bands widen from ±roughly 5%–10% at Class 1 to −30%/+50% at Class 5; the
three actual estimates deviated by 7.3%, 1.7% and 0% respectively from the Class 1 figure — narrowing at
each stage, as the classification system predicts.**

*Interpretation.* The Class 5 estimate's actual miss (+7.3%) sat comfortably inside its wide theoretical
band, but that is a feature of this particular illustration, not a guarantee: the −30%/+50% band is the
envelope of *typical* outcomes across many projects, and a less well-chosen historical comparator could
easily have produced a miss much closer to the edge. What the professional should take from this table is
not "our estimate was better than the range implied," but the funnel itself: each additional stage of design
maturity bought a materially tighter, more defensible number, at the cost of more estimating effort — the
trade-off the classification system exists to make explicit.

**Mini-case — the cost of the estimate itself.** Meridian's estimating department logs professional hours
against each estimate: the Class 5 analogous estimate for Pipeline Segment 4B took 4 hours (roughly $400 of
estimator time at a $100/hour rate); the Class 3 parametric estimate took 18 hours (~$1,800); the Class 1
bottom-up estimate — requiring a full take-off, vendor quotations and a detailed resource build — took 140
hours (~$14,000). Preparing a Class 1 estimate at the concept-screening stage, before the design existed to
support it, would therefore have wasted the great majority of that $14,000 on a scope that was still likely
to change materially — precisely why estimate class is matched to project stage, not maximised regardless of
stage (cross-reference KA 8.1, KA 8.2 on progressive elaboration through the project lifecycle).

**Common pitfalls.** (1) Requesting or presenting a Class 5 estimate as though it carries Class 1 precision —
the single most common and most damaging estimating error in project controls (cross-reference KA 3.1.2's
identical pitfall in the budgeting context). (2) Treating estimate class as a statement about estimator
competence rather than about scope maturity — a highly competent estimator working from immature scope still
produces a Class 5-accuracy number. (3) Skipping intermediate classes under time pressure and jumping
straight from a Class 5 screening figure to what is presented as a Class 1 bid, without the intervening
design maturity that a genuine Class 1 estimate requires.

**AI in this topic.** AI-assisted estimating platforms can assess the completeness of the design and
scope information supplied for a new estimate request and flag which AACE class that information actually
supports — a genuinely useful check against exactly the first pitfall above (cross-reference KA 13.4, KA
13.5). Such a tool cannot itself judge whether a borderline case (say, 38% versus 42% project definition)
should be classed 4 or 3 — that boundary judgement, and the accuracy range attached to it, remains the
estimator's professional call, made and documented in the Basis of Estimate (§3.2.7).

### 3.2.2 Analogous estimating

**Definition & purpose.** **Analogous estimating** derives a new estimate by scaling the actual, known cost
(or unit rate) of a genuinely comparable historical project, adjusted for identified differences between the
two. PMI's PMBOK Guide lists it among the standard cost-estimating techniques; AACE International associates
it with the earliest classes (Class 5–4, §3.2.1) precisely because it needs the least project-specific detail
of any method — only a comparator and a size driver. KA 3.1.2 already introduced the *whole-project* version
of this idea (a single unit-cost benchmark applied to a top-down budget); this topic develops the
finer-grained technique of scaling a *specific* historical comparator project and formally adjusting it for
the ways the new project genuinely differs.

**The underlying principle.** An analogous estimate is only as reliable as the comparability judgement behind
it. Two projects rarely match perfectly on every dimension that drives cost — size, complexity, location,
labour market, and the time elapsed (and therefore cost escalation) since the comparator was priced — so the
method's discipline lies in identifying which of those dimensions genuinely differ for this project and
adjusting for each one explicitly, rather than applying the historical rate unadjusted and hoping the
differences wash out.

**Formula.**
`Adjusted rate = Historical rate × (1 + Σ adjustment factors)`
`Analogous estimate = Adjusted rate × New project's size driver`

where the *historical rate* is a $-per-unit figure drawn from the comparator project's own actual outturn
cost, and each *adjustment factor* is a stated, justified percentage responding to one specific difference
(complexity, location, escalation). This KA sums the individual factors for simplicity; a more theoretically
precise approach compounds them multiplicatively (`(1 + f₁) × (1 + f₂) × …`), which gives a marginally
different result for materially large adjustments — the simpler additive convention is used here, and should
be stated explicitly in the Basis of Estimate whichever convention an organisation adopts (§3.2.7).

**Example 3.2.2 — an analogous estimate for Pipeline Segment 4B.**

*Scenario.* Before detailed engineering exists, Meridian's estimator needs an early, bid-stage figure for
Pipeline Segment 4B (2,000 m of buried pipeline). The most recent genuinely comparable project, **Pipeline
Segment 2A** (1,800 m, completed 18 months ago), had a historical actual cost of $504,000 — a blended rate of
$280/m. Two adjustments are identified and justified: Segment 4B includes additional valve-chamber
complexity not present on Segment 2A (+6%), and general cost escalation plus a marginally more remote site
access have moved since Segment 2A's completion (+9%).

*Required.* The adjusted unit rate and the resulting analogous estimate.

*Working.*
Historical rate `= 504,000 / 1,800 = $280/m`.
Combined adjustment `= 6% + 9% = 15%`.
Adjusted rate `= 280 × 1.15 = $322/m`.
Analogous estimate `= 322 × 2,000 = $644,000` (SAR 2,415,000 at an illustrative SAR 3.75 = USD 1).

*Answer.* **Analogous (Class 5) estimate for Pipeline Segment 4B = $644,000.**

*Interpretation.* The two named, individually justified adjustments moved the estimate by $84,000 relative
to an unadjusted, naive scaling of Segment 2A's rate. Because each adjustment is documented separately — not
folded into one unexplained "uplift" — a reviewer can challenge either one on its own terms (is 6% the right
complexity premium for the extra valve chambers? is 9% the right combined escalation-and-access premium?)
without having to accept or reject the whole estimate as a single black box.

**Mini-case — the naive, unadjusted shortcut.** A junior estimator, under time pressure, instead applies
Segment 2A's $280/m rate directly to Segment 4B's 2,000 m with no adjustment: `2,000 × 280 = $560,000` — 15%
(exactly the combined adjustment factor omitted) below the properly adjusted $644,000. Left unchallenged, this
shortcut would have understated the bid-stage estimate by $84,000 before any detailed design existed to
reveal the gap, and — had it been carried forward as the working assumption into the Class 3 and Class 1
stages — could have anchored the whole estimating team on a figure that was wrong from the outset. This is
exactly the comparability judgement KA 3.1.2 warned about: skipping the adjustment step is not a shortcut
that saves time proportionate to the risk it introduces.

**Common pitfalls.** (1) Selecting a comparator that superficially resembles the new project (same trade,
similar description) but differs materially in a cost-driving way — ground conditions, crew experience,
regulatory regime — without recognising the difference. (2) Blending several adjustment reasons into a
single unexplained percentage, making the estimate impossible to challenge or defend line by line (the
opposite of the discipline this method depends on). (3) Never revisiting an early analogous estimate once
better information exists, so a Class 5 figure quietly persists in circulation long after a Class 3 or Class
1 estimate has superseded it.

**AI in this topic.** Machine-learning comparator-matching tools can search a much larger historical project
database than a manual review typically can, scoring candidate comparators across several attributes
simultaneously — length, diameter, ground class, region — rather than relying on a description match alone
(cross-reference KA 13.4, KA 13.5). This widens the pool of comparators a human could realistically review.
It does not remove the comparability judgement itself: an algorithm cannot confirm that a suggested
comparator's ground conditions or crew productivity genuinely resemble the new project's without a human who
knows both sites, and an unreviewed AI-suggested comparator can silently reproduce the naive-shortcut error
shown in the mini-case above, just with more apparent sophistication.

### 3.2.3 Parametric estimating and cost estimating relationships (CERs)

**Definition & purpose.** **Parametric estimating** derives an estimate from a mathematical relationship —
a **cost estimating relationship (CER)** — between a project's cost and one or more measurable **cost
drivers** (length, floor area, capacity, equipment count), fitted from a dataset of historical, comparable
projects. Where analogous estimating (§3.2.2) scales a *single* comparator, parametric estimating draws on a
*population* of historical data points, making it less dependent on any one comparator being a perfect match
and more dependent on the dataset being large enough, and consistent enough, to support a reliable
relationship. AACE International's TCM Framework and PMI's PMBOK Guide both recognise parametric estimating
as a standard technique, typically associated with Class 4–3 estimates (§3.2.1), once enough historical data
exists to fit a relationship but before a full, detailed take-off is possible.

**The underlying principle.** A CER works because, across a large enough sample of similar projects, cost
tends to move systematically with one or more measurable physical drivers, even though any single project's
actual cost will scatter around that underlying trend for reasons specific to it. Fitting a CER — most simply,
a straight line, `Cost = a + b × D` — separates that systematic relationship (the fitted line) from the
project-specific noise (the scatter around it). The statistical **goodness of fit**, commonly summarised by
**R²** (the proportion of cost variation the driver explains, from 0 to 1), tells the estimator how much
confidence the relationship deserves: a high R² supports real reliance on the CER; a low R² signals that the
chosen driver alone does not explain cost well and the estimate should be treated with wider uncertainty, or
a different or additional driver should be sought.

**Formula.**
`Cost = a + b × D`, where *D* is the primary cost driver (e.g. metres of pipeline), *a* is the fixed/base
cost component (mobilisation, engineering — largely independent of *D*), and *b* is the variable cost-driver
rate (USD per unit of *D*). For two known data points, the rate can be derived directly:
`b = (Cost₂ − Cost₁) / (D₂ − D₁)`, then `a = Cost₁ − b × D₁`. A full-dataset fit would normally use
least-squares regression across all available historical points rather than just two; the two-point method
below illustrates the underlying mechanics.

**Example 3.2.3 — building and applying a CER for Pipeline Segment 4B.**

*Scenario.* Meridian's estimating database holds four recently completed pipeline segments of the same
ground class:

| Segment | Length (m) | Actual cost ($) |
|---|---|---|
| P-Alpha | 1,200 | 402,000 |
| P-Bravo | 1,600 | 506,000 |
| P-Charlie | 2,400 | 714,000 |
| P-Delta | 3,000 | 870,000 |

*Required.* A fitted CER (Cost as a function of length), a check of that CER against the dataset, and its
application to Pipeline Segment 4B's 2,000 m scope.

*Working.*
Using P-Alpha and P-Delta to derive the relationship:
`b = (870,000 − 402,000) / (3,000 − 1,200) = 468,000 / 1,800 = $260/m`
`a = 402,000 − 260 × 1,200 = 402,000 − 312,000 = $90,000`
`CER: Cost = 90,000 + 260 × Length`
Check against the two remaining points: P-Bravo `90,000 + 260 × 1,600 = 90,000 + 416,000 = 506,000` ✓
(matches exactly); P-Charlie `90,000 + 260 × 2,400 = 90,000 + 624,000 = 714,000` ✓ (matches exactly).
Applied to Pipeline Segment 4B: `Cost = 90,000 + 260 × 2,000 = 90,000 + 520,000 = $610,000`.

*Answer.* **CER (Class 3) estimate for Pipeline Segment 4B = $610,000** (SAR 2,287,500 at an illustrative
SAR 3.75 = USD 1).

*Interpretation.* This illustrative dataset fits its own CER exactly, isolating the mechanics of building and
applying the relationship. Real project data is rarely this clean — historical costs scatter around the
fitted line for reasons the length driver alone cannot explain (site-specific delays, differing crew
composition, weather) — which is exactly why a real CER should always be reported with its R² or an
equivalent goodness-of-fit measure, and why a professional should be more confident relying on a CER fitted
across many points with a tight scatter than on one derived, as this illustration was for teaching clarity,
from just two.

**Mini-case — a multi-driver CER.** A single driver is not always enough. For a facility fit-out programme
(a different illustrative scope, chosen to show the technique without reusing Pipeline Segment 4B's numbers),
Meridian's estimating department has fitted a two-driver CER from historical projects: `Cost = 40,000 + 850 ×
Floor area (m²) + 3,000 × Number of process skids`. Applied to a new facility of 500 m² with 4 process skids:

`Cost = 40,000 + (850 × 500) + (3,000 × 4) = 40,000 + 425,000 + 12,000 = $477,000`

*Interpretation.* Adding a second driver (skid count) alongside floor area captures cost variation that
floor area alone would miss — two facilities of identical floor area but different numbers of process skids
plainly do not cost the same. A multi-driver CER is more work to build and validate (each driver needs its
own justified, statistically supported relationship to cost) but can materially improve accuracy where a
single driver leaves too much cost variation unexplained.

**Common pitfalls.** (1) Fitting a CER to too few or too dissimilar historical data points and treating the
result as reliable — a relationship derived from a thin or inconsistent dataset carries far more uncertainty
than the clean arithmetic of applying it suggests. (2) Using a cost driver that correlates with cost by
coincidence rather than by genuine cause (a classic statistical trap) — the driver chosen must have a
believable engineering or economic reason to move cost, not merely a numerical association in the sample.
(3) Applying a CER outside the range of the data it was fitted on (e.g. extrapolating a pipeline CER built
from 1,200–3,000 m projects to a 6,000 m scope) without flagging the extra uncertainty that extrapolation
introduces.

**AI in this topic.** Statistical and machine-learning tools can fit CERs automatically across large
historical datasets, test multiple candidate drivers simultaneously, and report goodness-of-fit statistics
far faster than a manual regression (cross-reference KA 13.4, KA 13.5) — a genuine strength when an
organisation's estimating database is large enough to support it. Such tools cannot determine whether a
statistically strong driver is *causally* meaningful or merely coincidentally correlated in the available
sample, nor whether the underlying historical dataset is itself complete, consistently coded and free of
data-quality problems (cross-reference KA 13.2) — an automated CER built on a flawed dataset simply produces
a fast, confidently wrong relationship, which the professional must interrogate before relying on it.

single-comparator predecessor to this population-based method); §3.4.2 (driver-based *forecasting*, which
reuses this same cost-driver logic once work is under way); KA 13.2 (data quality and governance).

### 3.2.4 Bottom-up (definitive) estimating

**Definition & purpose.** **Bottom-up (definitive) estimating** builds an estimate from the most granular
level upward: each work package's cost is derived directly from its own resources (labour hours, equipment
hours, material quantities and rates) or from vendor/subcontractor quotations, and the work-package figures
are summed into the total. AACE International associates this level of detail with Class 2–1 estimates
(§3.2.1), requiring a mature, largely complete scope definition. KA 3.1.3 already introduced bottom-up
*budgeting* — summing already-known work-package figures into control accounts; this topic goes one level
deeper, into how each individual work-package figure is itself actually calculated.

**The underlying principle.** A definitive estimate is only as reliable as the resource rates, productivities
and quotations feeding it — the method trades the speed of analogy and the elegance of a fitted relationship
for the accuracy that comes from pricing the *actual* resources this specific scope requires. Two broad
sourcing approaches typically combine within a single bottom-up estimate: a **resource-based build**
(quantity × productivity × rate, for work Meridian will self-perform) and a **quotation-based build** (a
priced vendor or subcontractor quotation, for work or materials to be bought in) — each work package uses
whichever is genuinely available and appropriate to it, exactly as KA 6.1.4 later uses whichever earned-value
measurement method genuinely fits each work package.

**Formula.**
Resource-based: `Unit rate = (Σ resource cost per period) / (productivity, units per period)`;
`Work-package cost = Unit rate × Quantity`.
Quotation-based: `Work-package cost = Priced vendor/subcontractor quotation` (taken directly, with any
allowance for scope gaps stated separately).
`Base cost estimate = Σ (work-package costs)`, across all work packages in the scope.

**Example 3.2.4 — building Pipeline Segment 4B's Class 1 bottom-up estimate.**

*Scenario.* With design and take-off now execution-ready, Meridian's estimator prices Pipeline Segment 4B

### 3.2.5 Three-point (PERT-type) estimating for estimate elements

**Definition & purpose.** **Three-point estimating** derives a single expected value for an uncertain
estimate element — a unit rate, a quantity, or a duration — from three judgement-based scenarios: an
**optimistic (O)**, a **most-likely (M)**, and a **pessimistic (P)** outcome. PMI's PMBOK Guide describes
this technique within both its cost- and duration-estimating processes. This topic applies the technique at
the level of a *single, specific* uncertain input — as PMBOK originally intends it — which is a different use
from KA 3.4.6's three-point (PERT-type) formula, which instead *blends several independent, already-completed
forecasts* produced by different methods; the arithmetic is identical, but what is being combined is not.

**The underlying principle.** A single point figure for an uncertain input hides how confident the estimator
actually is in it. Three-point estimating makes that confidence explicit by capturing the realistic range,
then combining the three scenarios into one expected value using a **weighted (PERT-type / beta
distribution)** formula that gives the most-likely case four times the weight of either extreme — reflecting
the reasonable assumption that the true outcome is more likely to land near the most-likely estimate than at
either edge of the range. A simpler **simple average (triangular distribution)** of the same three points is
sometimes used instead; the two differ whenever O and P are not symmetric around M, because the simple
average gives each of the three scenarios equal weight.

**Formula.**
`E = (O + 4M + P) / 6` — weighted (PERT-type) expected value.
`E (triangular) = (O + M + P) / 3` — simple-average alternative.
`σ = (P − O) / 6` — an approximate standard deviation, giving a rough ±1σ range around E (about a 68%
confidence interval, assuming a roughly symmetric, well-behaved distribution).

**Example 3.2.5 — three-point estimating the trenching unit rate.**

*Scenario.* Rather than assuming a single trenching rate, Meridian's estimator captures a genuine range for
the rate developed in §3.2.4, reflecting uncertainty in ground conditions along the 2,000 m alignment:
optimistic $85/m, most-likely $100/m, pessimistic $115/m.

*Required.* The weighted (PERT-type) expected rate, its approximate standard deviation, and the resulting
range on WP3's total cost.

*Working.*
`E = (85 + 4 × 100 + 115) / 6 = (85 + 400 + 115) / 6 = 600 / 6 = $100/m`
`σ = (115 − 85) / 6 = 30 / 6 = $5/m`
WP3 expected cost `= 100 × 2,000 = $200,000` (exactly the rate used in §3.2.4).
Approximate ±1σ range on WP3, treating the rate uncertainty as applying across the whole 2,000 m run (ground
conditions act on the alignment as a whole, not independently metre by metre, so the rate's uncertainty
scales directly with quantity rather than by the square-root-of-n rule that would apply to many independent,
uncorrelated risks — cross-reference KA 12.2 for the fuller correlated-versus-independent treatment):
`Low = (100 − 5) × 2,000 = 95 × 2,000 = $190,000`
`High = (100 + 5) × 2,000 = 105 × 2,000 = $210,000`

*Answer.* **Weighted expected rate = $100/m; approximate ±1σ range on WP3 = $190,000 to $210,000.**

*Interpretation.* The three-point technique independently validates the $100/m rate used as the point figure
in §3.2.4 — a useful cross-check, not a coincidence, since the most-likely scenario (M = $100/m) was set
using the same resource build-up. Its real value is the $5/m standard deviation it adds: WP3's cost is not
simply "$200,000," it is "$200,000, with a reasonable one-standard-deviation range of roughly ±$10,000" —
information §3.2.6's contingency calculation can draw on directly.

**Mini-case — three-point estimating a duration, not just a cost.** The same technique applies to schedule
durations. Using productivity scenarios of 50 m/day (optimistic), 40 m/day (most likely) and 32 m/day
(pessimistic — the same figure used in §3.2.4's sensitivity mini-case) for the 2,000 m trenching activity:

`Optimistic duration = 2,000 / 50 = 40 days`
`Most-likely duration = 2,000 / 40 = 50 days`
`Pessimistic duration = 2,000 / 32 = 62.5 days`, rounded to 63 days (partial days are rarely schedulable,
consistent with the rounding convention used in KA 3.4.3)
`E = (40 + 4 × 50 + 63) / 6 = (40 + 200 + 63) / 6 = 303 / 6 = 50.5 days`, rounded to **51 working days**.

*Interpretation.* The expected duration (51 days) is slightly longer than the most-likely single-point
assumption (50 days) precisely because the pessimistic scenario (63 days) is further from most-likely than
the optimistic scenario (40 days) is — an asymmetric range, which is why the weighted formula and the simple
average would not agree here (`(40+50+63)/3 = 51`, coincidentally close in this instance but not
guaranteed to be). This is a reminder that a cost three-point range and a duration three-point range on the
same activity are not automatically the same shape or the same confidence level — each should be elicited on
its own merits, not assumed to mirror the other.

**Common pitfalls.** (1) Setting O, M and P casually, without genuine engineering or historical justification
for each — the technique's value depends entirely on the three scenarios being real judgements, not an
arbitrary ± percentage dressed up as three points. (2) Applying the three-point *rate* uncertainty and then,
separately, an unrelated flat contingency percentage to the same risk — double-counting the same ground-
condition uncertainty twice (cross-reference KA 3.1.6's identical warning). (3) Treating the ±1σ range as a
guaranteed bound rather than an approximate, roughly-68%-confidence interval — a genuinely poor outcome can
still fall outside it.

**AI in this topic.** Historical productivity and rate databases, mined by AI tools, can suggest plausible
optimistic/most-likely/pessimistic ranges for a given activity type and ground class, speeding up the
elicitation step (cross-reference KA 13.5). Accepting a suggested range uncritically risks an anchoring
effect — the estimator adopting the tool's range instead of forming an independent judgement about *this*
specific site — which is exactly the sign-off responsibility the estimator retains: the three scenarios must
reflect this project's conditions, confirmed by the responsible professional, not merely a database average.

### 3.2.6 Pricing time and risk into the estimate: escalation and contingency

**Definition & purpose.** A base cost estimate, however carefully built (§3.2.2–3.2.4), is priced at a stated
point in time and against a defined scope. Two further, conceptually distinct adjustments are needed before
it is ready to become a budget: **escalation** — an allowance for the time value of cost inflation between
the estimate's pricing date and when the money will actually be spent — and **contingency** — the risk-based
allowance for identified, in-scope risks that KA 3.1.6 introduced at the budgeting-hierarchy level and this
topic now builds from first principles at the estimate level. The two are often confused, but they answer
different questions: escalation asks "what will the same scope cost later, given market movement?";
contingency asks "how much extra might this specific scope cost if an identified risk occurs?"

**The underlying principle.** Escalation is a near-certain, market-driven adjustment — prices generally do
rise over time, and the only real question is by how much and over what exposure period — so it is
calculated deterministically from a stated rate and time exposure. Contingency responds to genuinely
uncertain, identified risks that may or may not occur, so it is properly sized using probability-weighted
(expected-value) or fuller quantitative methods (Monte Carlo — cross-reference KA 12.2), exactly as KA 3.1.6
described. Conflating the two — using contingency to cover known inflation, or an escalation allowance to
quietly absorb an unquantified risk — obscures which fund is meant to answer which question, the same
governance failure KA 3.1.6 warned against for contingency and management reserve.

**Formula.**
`Escalation = Base cost × Annual escalation rate × (Exposure period, months / 12)` — a simple, linear
proration; more sophisticated compounding methods exist for long exposure periods and should be used where
the exposure is multi-year.
`Contingency (expected-value method) = Σ (Probability_i × Impact_i)`, summed across identified risks *i*
(identical to KA 3.1.6's formula, applied here to a specific project's estimate rather than to the whole
budgeting hierarchy).
`Base estimate = Base cost + Escalation`
`Cost baseline (BAC) = Base estimate + Contingency` — reusing KA 3.1's formula exactly, once management
reserve (set separately, at sponsor level) is layered on top.

**Example 3.2.6 — escalating and adding contingency to Pipeline Segment 4B's estimate.**

*Scenario.* Pipeline Segment 4B's $600,000 base cost estimate (§3.2.4) is priced at today's rates. WP2
(Pipe & valve procurement, $150,000) will not be spent until roughly six months from now, and materials-cost
inflation is forecast at 4% per year. Separately, Meridian's risk register for Pipeline Segment 4B identifies
three risks:

| Risk | Probability | Impact if it occurs ($) | Expected value ($) |
|---|---|---|---|
| Utility conflict during trenching (WP3) | 30% | 60,000 | 18,000 |
| Weld rework due to a quality failure (WP4) | 20% | 40,000 | 8,000 |
| Weather-related delay costs, extended plant hire (WP3/WP4) | 25% | 16,000 | 4,000 |
| **Total** | | | **30,000** |

*Required.* The escalation allowance, the base estimate, the contingency reserve, and the resulting cost
baseline (BAC).

*Working.*
`Escalation = 150,000 × 4% × (6/12) = 150,000 × 0.04 × 0.5 = $3,000`
`Base estimate = 600,000 + 3,000 = $603,000`
`Contingency = (0.30 × 60,000) + (0.20 × 40,000) + (0.25 × 16,000) = 18,000 + 8,000 + 4,000 = $30,000`
`Cost baseline (BAC) = 603,000 + 30,000 = $633,000`

*Answer.* **Escalation = $3,000; Base estimate = $603,000; Contingency = $30,000; Cost baseline (BAC) =
$633,000** (SAR 2,373,750 at an illustrative SAR 3.75 = USD 1).

*Interpretation.* Three clearly separated adjustments — the $600,000 base cost itself, a $3,000 time-based
escalation allowance, and a $30,000 risk-based contingency built from three named risks — combine to a
$633,000 cost baseline, exactly matching KA 3.1's hierarchy formula (`Cost baseline = Base estimate +
Contingency`). This fuller build differs from KA 6.1's simplified $600,000 BAC used for teaching the earned-
value mechanics — a difference flagged explicitly for SME reconciliation (see below), since it is entirely
reasonable for a chapter introducing EVM mechanics to hold escalation and contingency constant while
teaching PV/EV/AC, and for this estimating chapter to show the fuller build those simplified figures were
drawn from.

**Mini-case — escalation and contingency are not interchangeable.** Under schedule pressure, a different
estimator on a comparable package folds an unquantified "risk cushion" into the escalation rate — using 7%
instead of the market-justified 4% — reasoning that "it covers a bit of everything." Six months later, when
a genuine, identified risk (a utility conflict, matching the register above) actually occurs, there is no
clearly labelled contingency line to draw down against, because the extra allowance is buried, unlabelled,
inside what is nominally a market-escalation figure. The project team either has to seek a fresh, unplanned
change to cover the utility-conflict cost, or quietly absorbs it against the inflated escalation line — in
either case losing the audit trail KA 3.1.6 identified as essential to defending, or correctly releasing,
either reserve. Keeping the two adjustments separate and individually justified, as the worked example does,
is what avoids this outcome.

Double-counting risk between an individually padded unit rate (e.g. an estimator quietly inflating the
trenching rate "to be safe," beyond the three-point range established in §3.2.5) and the formal contingency
reserve calculated from the risk register — inflating the total beyond what the documented risk actually
supports, exactly the pitfall KA 3.1.6 flagged at the budgeting-hierarchy level.

a full probability distribution across a risk register far faster than manual expected-value arithmetic,
producing a P50/P80 contingency figure rather than the single expected-value number shown above. Neither
tool can identify a risk that has not been entered into the register, and neither can decide the
organisation's risk appetite or approve a contingency drawdown — those remain the accountable professional's
judgement and decision, as KA 3.1.6 establishes in full.

### 3.2.7 The Basis of Estimate, accuracy ranges and estimate assurance

**Definition & purpose.** The **Basis of Estimate (BoE)** is the documented record that accompanies every
issued estimate, stating its scope basis, methodology, source data, pricing date, key assumptions, explicit
exclusions, and the escalation and contingency basis used to arrive at the final figure. An estimate number
without its BoE is not usable by anyone other than the person who produced it: it cannot be audited,
defended, updated when circumstances change, or handed over to another estimator. AACE International's TCM
Framework treats a documented basis as inseparable from the estimate itself, not an optional add-on prepared
after the fact.

**The underlying principle.** Every technique in this KA — the AACE class (§3.2.1), the comparator and its
adjustments (§3.2.2), the CER and its dataset (§3.2.3), the resourced rates and quotations (§3.2.4), the
three-point ranges (§3.2.5), the escalation rate and risk register (§3.2.6) — embeds a judgement that is only
as good as its documentation. A single dollar figure carries none of that judgement forward on its own; the
BoE is what allows a reviewer, an auditor, or the estimator's own future self to reconstruct *why* the number
is what it is, and to judge whether it still holds when the underlying assumptions change. This is also where
the estimate's declared scope should be checked against what it needs to *become*: for a capitalised asset,
the base cost estimate's scope of included costs should align with what IAS 16 would recognise as directly
attributable to bringing the asset to its working condition (cross-reference KA 2.4.3), and, where the
project is financed by borrowing during construction, whether the estimate's scope is expected to interact
with IAS 23's borrowing-cost capitalisation (cross-reference KA 2.4.6) — a reminder that the estimating
professional and the finance professional are estimating and reporting the *same* underlying scope, even
though they use it differently.

**Formula.** No new arithmetic; the "assurance" content of this topic is the reconciliation of what has
already been calculated. A useful supplementary concept is expressing accuracy as a **confidence level**
(commonly P10, P50, P90 — the cost value below which the true outturn is expected to fall 10%, 50% or 90% of
the time, drawn from a probabilistic contingency analysis — cross-reference KA 12.2) rather than as a single
deterministic ± range, once a quantitative risk analysis is available to support it.

**Example 3.2.7 — reconciling Pipeline Segment 4B's estimating history into its Basis of Estimate.**

*Scenario.* Pipeline Segment 4B's estimate has now passed through three classes: Class 5 analogous ($644,000,
§3.2.2), Class 3 parametric ($610,000, §3.2.3), and Class 1 bottom-up ($600,000 base cost, §3.2.4), with
escalation and contingency added at the final stage to reach a $633,000 cost baseline (§3.2.6).

*Required.* A summary reconciliation table for the Basis of Estimate, and confirmation that each stage's
deviation sat within its declared accuracy range.

*Working.*

| Stage | Method | Class | Base cost estimate ($) | Deviation from Class 1 | Declared accuracy range |
|---|---|---|---|---|---|
| Bid | Analogous (§3.2.2) | 5 | 644,000 | +7.3% | −30% / +50% |
| Early engineering | Parametric/CER (§3.2.3) | 3 | 610,000 | +1.7% | −10% / +20% |
| Execution-ready | Bottom-up (§3.2.4) | 1 | 600,000 | reference | −3% / +10% |

*Answer.* **Basis of Estimate summary: base cost estimate $600,000 (Class 1); base estimate, escalated,

*Interpretation.* A BoE is not just the final number; it is the whole table above, plus the narrative
assumptions behind each row — the comparator and its adjustment factors (§3.2.2), the CER dataset and its
driver (§3.2.3), the resourced rates and vendor quotations (§3.2.4), the escalation rate and risk register
(§3.2.6) — retained together so that a reviewer six months from now, or a client's own cost auditor, can
follow the figure back to its source rather than simply being asked to trust it.

**Mini-case — an audit, eight months later.** A client's independent cost auditor requests supporting
documentation for Pipeline Segment 4B's $633,000 cost baseline. Because Meridian retained a complete BoE —
the risk register with its probabilities and impacts, the trenching resource build-up, the CER dataset and
its fit, the analogous comparator and its named adjustment factors — the auditor is able to trace every
dollar of the figure to a documented, dated source within a single meeting. A competitor bidding the same
scope, whose estimator kept only the final total in a spreadsheet with no supporting basis, cannot answer the
same questions and has the figure rejected pending re-substantiation, delaying payment certification. The
difference in outcome is entirely the documentation, not the arithmetic — both totals may well have been
correct.

- *Frame 4:* the escalation and contingency blocks stack on, reaching $633,000, with a small BoE-document
  icon appearing beside the final figure. Narration cue: "Three classes, three methods, one documented trail
  — this is what a defensible estimate looks like, from first screening to final baseline."

**Common pitfalls.** (1) Issuing a bare number without its BoE, so the estimate cannot be defended, updated,
or audited once the estimator who produced it is unavailable. (2) Letting the BoE drift out of date as
assumptions change during subsequent stages, so the documented basis no longer matches the figure actually
being used. (3) Presenting a single-point estimate to a client or steering committee without disclosing its
class and accuracy range, inviting the reader to assume a precision the underlying method does not support —
the same pitfall §3.2.1 raised, now viewed from the documentation side.

**AI in this topic.** GenAI drafting tools can assemble a first-pass Basis of Estimate document from an
estimate's underlying source data, assumptions log and risk register, saving material drafting time on a
routine but detail-heavy document (cross-reference KA 13.3, KA 13.5). Such a tool cannot verify that the
assumptions it is summarising are themselves correct or complete — a polished, well-formatted AI-drafted BoE
can mask a missing exclusion or an unjustified adjustment factor just as easily as a hastily written one, and
the estimator who signs off the estimate remains accountable for confirming the BoE is a true and complete
record before it is issued. **AI proposes a draft record; the professional decides by verifying, and
standing behind, what it says.**

### Key terms

- **Cost estimate** — a documented prediction of the likely cost of a defined or partially defined scope of
  work, produced by a stated method and expressed with a declared accuracy range.
- **AACE Cost Estimate Classification System (Class 5–1)** — the industry-standard framework naming an
  estimate's maturity, from Class 5 (least defined, widest accuracy range) to Class 1 (most defined,
  narrowest accuracy range).
- **Analogous estimating** — scaling the actual cost of a genuinely comparable historical project, adjusted
  for identified differences.
- **Parametric estimating / cost estimating relationship (CER)** — a fitted mathematical relationship between
  cost and one or more measurable cost drivers, derived from a historical dataset.
- **Cost driver** — a measurable physical parameter (length, area, capacity) that a CER links to cost.
- **Bottom-up (definitive) estimating** — building an estimate from resourced unit rates or vendor
  quotations at the work-package level, summed to a total.
- **Three-point (PERT-type) estimating** — combining optimistic, most-likely and pessimistic scenarios for a
  single uncertain estimate element into one expected value, `E = (O + 4M + P)/6`.
- **Escalation** — a time-based allowance for cost inflation between an estimate's pricing date and the
  expected date of expenditure.
- **Contingency (estimate-level)** — a risk-based allowance, sized from an identified risk register using an
  expected-value or probabilistic method, identical in concept to KA 3.1.6's treatment.
- **Basis of Estimate (BoE)** — the documented record of an estimate's scope, methodology, assumptions,
  exclusions, source data and pricing/escalation/contingency basis.
- **Accuracy range / confidence level (P10/P50/P90)** — the declared or probabilistically derived band within
  which the true outturn cost is expected to fall.
- **Goodness of fit / R²** — a statistical measure of how well a fitted CER explains historical cost
  variation.

### Sample MCQs

**MCQ 3.2.1 [topic 3.2.1, level: recall]**
Which AACE estimate class is most closely associated with a fully detailed, bottom-up estimate prepared from
a complete cost take-off?
A. Class 5
B. Class 4
C. Class 3
D. **Class 1** ✔
*Rationale:* Class 1 requires the most complete project definition and supports the narrowest accuracy range
(§3.2.1). Classes 5 and 4 are associated with analogous/parametric methods at much lower project definition;
Class 3 is an intermediate, semi-detailed stage.

**MCQ 3.2.2 [topic 3.2.3, level: application — numerical]**
Using the cost estimating relationship `Cost = $90,000 + $260 × Length (m)`, what is the estimated cost for a
2,500 m pipeline segment?
A. $650,000
B. $715,000
C. **$740,000** ✔
D. $780,000
*Rationale:* `90,000 + 260 × 2,500 = 90,000 + 650,000 = 740,000`. A omits the $90,000 fixed component; B and
D result from using an incorrect slope or driver value.

**MCQ 3.2.3 [topic 3.2.5, level: application — numerical]**
A three-point estimate for a work package gives optimistic $40,000, most-likely $50,000 and pessimistic
$90,000. Using the weighted (PERT-type) formula `E = (O + 4M + P)/6`, what is the expected value?
A. $50,000
B. **$55,000** ✔
C. $60,000
D. $65,000
*Rationale:* `(40,000 + 4×50,000 + 90,000)/6 = (40,000 + 200,000 + 90,000)/6 = 330,000/6 = 55,000`. A reports
only the most-likely figure; C is the simple (unweighted) average of the three points; D is the simple
average of only the two extremes.

**MCQ 3.2.4 [topic 3.2.6, level: application — numerical]**
A project's risk register lists three risks: Risk 1, probability 20%, impact $50,000; Risk 2, probability
40%, impact $30,000; Risk 3, probability 10%, impact $80,000. What is the risk-based contingency reserve
using the expected-value method?
A. $18,000
B. **$30,000** ✔
C. $53,333
D. $160,000
*Rationale:* `(0.20×50,000) + (0.40×30,000) + (0.10×80,000) = 10,000 + 12,000 + 8,000 = 30,000`. C is the
simple average of the three impacts (ignoring probability); D is the sum of the impacts alone.

**MCQ 3.2.5 [topic 3.2.2, level: analysis]**
An estimator applies a historical comparator project's unit rate directly to a new project of similar
description, without adjustment, to save time. What is the most significant risk this creates?
A. The estimate will automatically fall into a higher AACE class than it should
B. **Genuine differences between the two projects (ground conditions, complexity, escalation) are left
unpriced, and the estimate's reliability depends entirely on a comparability judgement that was never made**
✔
C. The estimate becomes a parametric estimate rather than an analogous one
D. The resulting figure can no longer be expressed with an accuracy range
*Rationale:* Analogous estimating's entire value lies in the comparability judgement and its adjustments
(§3.2.2); skipping it (as in §3.2.2's mini-case) risks a materially wrong figure that looks complete. A
misstates how classification works — class depends on project definition, not on method choice; C confuses
method labels; D is false — every estimate class carries a declared accuracy range regardless.

**MCQ 3.2.6 [topic 3.2.1, level: application — numerical]**
A Class 4 estimate of $2,000,000 is prepared with a declared expected accuracy range of −20% to +30%. What is
the upper bound of that range?
A. $2,200,000
B. $2,300,000
C. **$2,600,000** ✔
D. $1,600,000
*Rationale:* `2,000,000 × 1.30 = 2,600,000`. D is the lower bound (`2,000,000 × 0.80`); A and B apply an
incorrect percentage to the upper bound.

### Self-check questions (answers in Appendix C)

1. Explain, using the AACE Cost Estimate Classification System, why a Class 5 estimate is both cheaper to
   prepare and far less accurate than a Class 1 estimate for the same scope of work.
2. Using the cost estimating relationship `Cost = $90,000 + $260 × Length (m)`, calculate the estimated cost
   for a 1,000 m pipeline segment.
3. A risk register lists two risks: Risk A, probability 25%, impact $40,000; Risk B, probability 50%, impact
   $20,000. Calculate the risk-based contingency reserve using the expected-value method.
4. Explain, in your own words, why escalation and contingency are calculated using different methods (one
   deterministic, one probability-weighted), and why folding a risk allowance into an escalation rate is
   considered poor practice.

**Answers**

1. A Class 5 estimate is prepared very early, before the scope is defined in any detail, using an analogous
   or parametric method that needs little project-specific data and therefore little estimator effort — the
   mini-case in §3.2.1 costed this at roughly $400 of estimator time. Because so little of the scope is
   actually known at that stage, the achievable accuracy is inherently wide (illustratively −30%/+50%) no
   matter how skilled the estimator is. A Class 1 estimate, by contrast, requires a complete take-off,
   resourced rates and vendor quotations against a mature design — around $14,000 of estimator time in the
   same mini-case — and because the scope is now fully known, the achievable accuracy range narrows sharply
   (illustratively −3%/+10%). The trade-off is fundamental: accuracy costs effort, and that effort is only
   available once the design has matured enough to support it.
2. `Cost = 90,000 + 260 × 1,000 = 90,000 + 260,000 = $350,000`.
3. `Contingency = (0.25 × 40,000) + (0.50 × 20,000) = 10,000 + 10,000 = $20,000`.
4. Escalation responds to a near-certain, market-driven cost movement (general price inflation over a known
   exposure period), so it can be calculated deterministically from a stated rate and time period. Contingency
   responds to specific, identified risks that may or may not occur, so it is properly sized using a
   probability-weighted (expected-value) or fuller probabilistic method that reflects genuine uncertainty,
   not certainty. Folding a risk allowance into the escalation rate (§3.2.6's mini-case) hides which fund is
   meant to answer which question: if the disguised risk allowance is never triggered, there is no clear,
   auditable route to release it back; if the risk does occur, there is no clearly labelled contingency line
   to draw down against, and the true cost of the risk is never visible in the record — undermining the
   audit trail and governance discipline KA 3.1.6 established for contingency and management reserve.
