# Domain 6 — Earned Value Management & Forecasting (EVM/EAC)

## KA 6.2 — Variances & indices

KA 6.1 established the three foundational EVM measures — Planned Value (PV), Earned Value (EV) and Actual
Cost (AC) — and showed how to build a trustworthy EVM data set at a status date. On their own, PV, EV and AC
are simply three numbers in the same currency; they do not yet tell a controls professional *how far* ahead
or behind the project is, nor whether that gap is significant. This KA turns those three measures into the
formally named, universally understood metrics that answer those questions: the **Cost Variance (CV)** and
**Schedule Variance (SV)** (absolute, currency-denominated gaps), the **Cost Performance Index (CPI)** and
**Schedule Performance Index (SPI)** (normalised, ratio-based efficiency measures), and the
**To-Complete Performance Index (TCPI)** (the efficiency still required to hit a cost target). Every one of
these five metrics is derived directly and only from PV, EV, AC and BAC — there is no new data collection
in this KA, only calculation and interpretation. The variances and indices calculated here are, in turn, the
direct inputs to KA 6.3's Estimate at Completion (EAC) forecasting: `EAC = BAC / CPI` and the
schedule-adjusted EAC formula both use CPI and SPI exactly as defined below, so precision here matters
downstream. This KA continues the Pipeline Segment 4B illustrative project from KA 6.1 (BAC $600,000 /
SAR 2,250,000 at an illustrative SAR 3.75 = USD 1; Month-3 status date: PV $270,000, EV $330,000,
AC $280,000) so the notation and figures stay identical across KA 6.1, 6.2 and 6.3.

### 6.2.1 Cost Variance (CV)

**Definition & purpose.** Cost Variance is the absolute, currency-denominated difference between the value
of work actually performed and what it actually cost to perform it. It answers the question: "for the work
we have done, did we spend more or less than its budgeted value?"

**The underlying principle.** CV compares EV — the *budgeted* value of the work performed — against AC —
what that work *actually* cost. Because both are expressed at the same data date and in the same currency,
the difference is a direct, uncontestable measure of cost performance to date; unlike a simple
budget-versus-actual report, it is anchored to work actually done, not merely to elapsed time or spend rate.

**Formula.**
`CV = EV − AC`
where EV and AC are both cumulative to the data date, expressed in the project's reporting currency (USD,
with an SAR illustration where useful). CV is itself expressed in that same currency — a dollar (or riyal)
amount, not a ratio.

**Example 6.2.1 — Cost Variance for Pipeline Segment 4B at Month 3.**

*Scenario.* Using the Month-3 EVM data set established in KA 6.1.6: EV = $330,000; AC = $280,000.

*Required.* CV at Month 3, and its interpretation.

*Working.* `CV = EV − AC = 330,000 − 280,000 = 50,000`

*Answer.* **CV = +$50,000** (SAR 187,500 at the illustrative rate).

*Interpretation.* A positive CV is **favourable**: the project has earned $50,000 more in budgeted value
than it has actually cost to deliver — the work performed to date cost less than its budgeted worth. A
negative CV would be **adverse** — the work performed cost more than its budgeted value, an overrun for the
scope actually delivered (illustrated for a different scenario in 6.2.5).

**Common pitfalls.**
- Reading CV as a percentage or a schedule signal — it is a currency amount and says nothing about *time*;
  that is SV's job (6.2.2).
- Computing CV from an unadjusted, cash-only AC. Using the KA 6.1.3 ledger figure of $280,000 rather than
  the accrual-adjusted $305,000 overstates CV by $25,000 (+$50,000 reported instead of the true +$25,000) —
  a material difference for a decision-maker.
- Treating a small, immaterial CV as proof of good cost control without checking whether it masks offsetting
  favourable and adverse variances at the work-package level (cross-reference KA 6.1.5's Project Nova
  mini-case).

**AI in this topic.** A dashboarding or BI tool can compute and refresh CV automatically the moment PV, EV
and AC update, and can flag when CV crosses a materiality threshold (cross-reference KA 4.3, KA 4.4,
KA 13.5) — a genuine speed benefit over manual recalculation. It cannot judge *why* CV has moved, nor verify
that the AC feeding the calculation is complete and accrual-adjusted; a fast, automatically refreshed CV
built on incomplete AC is simply a fast, wrong number. The professional remains accountable for confirming
the inputs before acting on an automated CV alert — **AI proposes; the professional disposes.**

**Cross-references.** KA 6.1.1, 6.1.3 (EV, AC and the accrual-adjustment issue); KA 4.2 (variance analysis
more broadly, including cost/price/quantity bridges); KA 6.3 (CV underpins EAC reasoning); KA 6.2.5
(interpretation matrix, combining CV with SV/CPI/SPI).

### 6.2.2 Schedule Variance (SV)

**Definition & purpose.** Schedule Variance is the absolute, currency-denominated difference between the
value of work actually performed and the value of work that was scheduled to have been performed by the
data date. It answers: "for the plan we set, are we ahead of or behind where we should be, in earned-value
terms?"

**The underlying principle.** SV compares EV against PV — both budgeted values, but one reflecting what was
*actually accomplished* and the other what was *supposed to be accomplished* by now. Because SV is expressed
in currency rather than calendar time, it measures schedule performance *in value terms*, which is powerful
for aggregation across dissimilar work packages but — as explored fully in 6.2.7 — is not the same thing as
calendar lateness, and that distinction becomes critical near project completion.

**Formula.**
`SV = EV − PV`
where EV and PV are both cumulative to the data date, expressed in the reporting currency. Like CV, SV is a
currency amount, not a ratio.

**Example 6.2.2 — Schedule Variance for Pipeline Segment 4B at Month 3.**

*Scenario.* Continuing the Month-3 data set: EV = $330,000; PV = $270,000.

*Required.* SV at Month 3, and its interpretation.

*Working.* `SV = EV − PV = 330,000 − 270,000 = 60,000`

*Answer.* **SV = +$60,000** (SAR 225,000 at the illustrative rate).

*Interpretation.* A positive SV is **favourable**: $60,000 more value has been earned than the baseline
scheduled for this point in time — the project is, in earned-value terms, ahead of schedule. A negative SV
would be **adverse** — behind schedule in value terms (illustrated for a different scenario in 6.2.5).

**Fig 6.2.2 — Pipeline Segment 4B, Month 3: the CV and SV bridge from PV, EV and AC.**
Chart type: grouped bar chart. Vertical axis: USD; horizontal axis: three bars — PV, EV, AC. The EV bar is
rendered in brand blue `#1D4ED8` (the pivot value both variances are measured from); PV and AC are rendered
in neutral grey. Two bracket annotations span the chart: one between the PV and EV bars, labelled
"SV = EV − PV = +$60,000 (favourable)"; one between the EV and AC bars, labelled
"CV = EV − AC = +$50,000 (favourable)". This is the formal analysis promised at KA 6.1's Fig 6.1.6.

*Underlying data:* PV $270,000; EV $330,000; AC $280,000; SV +$60,000; CV +$50,000.

**Common pitfalls.**
- Interpreting SV as a number of days or weeks late/early — it is a currency value, not a duration; a large
  SV on a large-budget package may represent less real time than a small SV on a small package.
- Ignoring that SV, like PV, depends on the baseline being current (KA 6.1.2) — SV calculated against a
  stale, un-re-baselined PV misrepresents true schedule standing.
- Relying on SV alone near project completion without reading 6.2.7 — SV (and SPI) both trend toward zero
  favourable/zero variance as PV approaches BAC, independent of true lateness.

**AI in this topic.** As with CV, automated reporting tools can calculate and trend SV continuously and
raise an exception when it breaches a threshold (cross-reference KA 4.4, KA 13.5). The tool cannot determine
whether the underlying PV baseline is current or whether a resequencing of work (rather than genuine
slippage) explains the movement — that root-cause judgement remains with the professional, particularly
before SV is used to trigger schedule-recovery action.

**Cross-references.** KA 6.1.2 (PV and the re-baselining pitfall); KA 3.3 (time-phased budget); KA 6.4
(integrating EVM with the schedule; Earned Schedule addresses SV's completion-point weakness directly);
KA 10.4 (schedule progress measurement).

### 6.2.3 Cost Performance Index (CPI)

**Definition & purpose.** The Cost Performance Index normalises cost performance into a dimensionless
ratio: how much earned value is generated per unit of currency actually spent. It answers: "for every
dollar spent, how many dollars of budgeted value are we getting?"

**The underlying principle.** A currency variance (CV) is useful, but its *size* is hard to judge without
context — is +$50,000 large or small? Dividing EV by AC instead of subtracting produces a ratio that is
immediately comparable across work packages, projects and reporting periods of very different sizes, and
that has an intuitive benchmark: **1.00**.

**Formula.**
`CPI = EV / AC`
where EV and AC are both cumulative, in the same currency (which cancels, leaving CPI as a **dimensionless
ratio**, conventionally reported to two decimal places).

**Example 6.2.3 — Cost Performance Index for Pipeline Segment 4B at Month 3.**

*Scenario.* Continuing the Month-3 data set: EV = $330,000; AC = $280,000.

*Required.* CPI at Month 3, and its interpretation.

*Working.* `CPI = EV / AC = 330,000 / 280,000 = 1.1786`

*Answer.* **CPI = 1.18** (to two decimal places).

*Interpretation.* CPI > 1.0 is **favourable**: for every $1 actually spent, the project has generated $1.18
of budgeted value — cost-efficient performance. CPI = 1.00 means spending exactly matches the value earned
(neither favourable nor adverse); CPI < 1.0 is **adverse** — less than $1 of value is being generated for
every $1 spent, a cost overrun on the work performed (illustrated for CPI = 0.80 in 6.2.5). Using the
accrual-adjusted AC of $305,000 (KA 6.1.3), CPI would read `330,000 / 305,000 = 1.08` — still favourable, but
materially lower, underscoring again why AC completeness matters before CPI is relied upon or carried into
KA 6.3's `EAC = BAC / CPI`.

**Common pitfalls.**
- Reading CPI as a percentage (e.g. treating 1.18 as "18% under budget in total") rather than as a
  per-currency-unit efficiency ratio — the two are related but not identical, especially once projected
  forward into an EAC.
- Comparing CPI across work packages of very different sizes without weighting — a small package's CPI can
  swing dramatically on small absolute changes and dominate a simple average.
- Assuming a favourable cumulative CPI guarantees a favourable outcome — cumulative CPI is typically more
  stable than *current-period* CPI, and a recent deterioration in current-period efficiency can be masked by
  strong early performance (cross-reference KA 6.3's discussion of CPI stability over time).

**AI in this topic.** Analytics tools can trend CPI period-by-period, benchmark it against similar
historical work packages, and highlight packages whose CPI is deteriorating fastest (cross-reference
KA 13.5). This is genuinely useful for prioritising where to investigate first. It cannot explain the
*cause* of a low CPI (productivity loss, price escalation, rework, incorrect coding) — that diagnosis
requires the professional to examine the underlying cost and progress data, not the ratio alone.

**Cross-references.** KA 6.1.3 (AC and the accrual-adjustment issue); KA 6.2.6 (TCPI, which measures the
CPI still *required*); KA 6.3 (`EAC = BAC / CPI` and CPI-based forecasting); KA 4.2 (variance/efficiency
analysis more broadly).

### 6.2.4 Schedule Performance Index (SPI)

**Definition & purpose.** The Schedule Performance Index normalises schedule performance into a
dimensionless ratio: how much value is being earned relative to how much was planned to be earned by now.
It answers: "for every dollar of value the plan expected by now, how many dollars are we actually earning?"

**The underlying principle.** As with CPI, expressing schedule performance as a ratio (rather than only the
currency-based SV) gives an immediately comparable, benchmarked figure, again anchored at **1.00**.

**Formula.**
`SPI = EV / PV`
where EV and PV are both cumulative, in the same currency (which cancels, leaving SPI as a **dimensionless
ratio**, conventionally reported to two decimal places).

**Example 6.2.4 — Schedule Performance Index for Pipeline Segment 4B at Month 3.**

*Scenario.* Continuing the Month-3 data set: EV = $330,000; PV = $270,000.

*Required.* SPI at Month 3, and its interpretation.

*Working.* `SPI = EV / PV = 330,000 / 270,000 = 1.2222`

*Answer.* **SPI = 1.22** (to two decimal places).

*Interpretation.* SPI > 1.0 is **favourable**: the project is earning value 22% faster than the baseline
plan required — ahead of schedule in earned-value terms. SPI = 1.00 means earning value exactly as planned;
SPI < 1.0 is **adverse** — earning value more slowly than planned, i.e. behind schedule in earned-value
terms (illustrated for SPI = 0.80 in 6.2.5).

**Common pitfalls.**
- Treating SPI as if it directly converts to calendar days ahead or behind — SPI is a value-based ratio, not
  a duration-based one; the schedule's critical path may show different lateness than SPI implies, because
  SPI reflects the whole time-phased budget, not just the critical path (cross-reference KA 6.4).
- Relying on SPI without recognising its known **completion-point weakness**: SPI mechanically drifts toward
  1.00 as the data date approaches the project's baselined finish, however genuinely late the project truly
  is — this is examined in full, with a worked illustration, in 6.2.7. This is one of the most important
  pitfalls in the whole of EVM practice and is not optional reading.
- Using SPI on a control account measured by Level of Effort (LOE) — by construction (KA 6.1.4), LOE always
  has EV = PV, so SPI is always exactly 1.00 for that package and can never reveal real slippage there.

**AI in this topic.** As with CPI, automated trending and benchmarking of SPI is a genuine efficiency gain
for routine reporting (cross-reference KA 13.5). A GenAI narrative-drafting tool asked to "explain the SPI"
will typically produce a plausible-sounding but potentially misleading statement near project completion
(e.g. "the project has recovered to on-schedule") unless it is specifically prompted to check the
completion-point effect described in 6.2.7 — a case where an AI-drafted commentary can sound authoritative
while being materially wrong; the professional must verify any AI narrative about SPI against the
underlying calendar schedule, not the ratio alone.

**Cross-references.** KA 6.1.2 (PV); KA 6.1.4 (LOE and its SPI = 1.00 property); KA 6.4 (Earned Schedule as
the fix for SPI's completion-point weakness); KA 6.3 (SPI in the schedule-adjusted EAC formula); KA 9.3, 9.5
(the analogous velocity/burnup measures in agile delivery).

### 6.2.5 Reading CPI and SPI together: the interpretation matrix and the health quadrant

**Definition & purpose.** No single variance or index tells the whole story. A controls professional must
read CV, SV, CPI and SPI **together** to characterise a project's true position, because cost performance
and schedule performance are independent dimensions — a project can be efficient with money while being
behind on time, or ahead of time while overspending to get there. This topic gives the general
**interpretation matrix** for each metric and the specific **CPI/SPI health quadrant** used throughout
project controls reporting.

**The underlying principle.** CV/CPI compare EV against AC (the *cost* dimension); SV/SPI compare EV against
PV (the *schedule* dimension). Because AC and PV are independent inputs, the two dimensions can move
independently, producing four qualitatively different project states.

**Quick-reference interpretation matrix.**

| Metric | Favourable | On target | Adverse |
|---|---|---|---|
| CV = EV − AC | > $0 — under budget for work performed | = $0 — exactly on budget | < $0 — over budget for work performed |
| SV = EV − PV | > $0 — ahead of schedule (value terms) | = $0 — exactly on schedule | < $0 — behind schedule (value terms) |
| CPI = EV / AC | > 1.00 — cost-efficient (more value per $ spent) | = 1.00 — spending matches value earned | < 1.00 — cost-inefficient (less value per $ spent) |
| SPI = EV / PV | > 1.00 — earning value faster than planned | = 1.00 — earning value exactly as planned | < 1.00 — earning value slower than planned |

**Example 6.2.5 — Four illustrative scenarios sharing the same $600,000 BAC and Month-3 PV of $270,000.**

*Scenario.* To show how CPI and SPI combine, consider Pipeline Segment 4B's real Month-3 outcome (Q1)
alongside three hypothetical "what-if" variants at the same data date and baseline, differing only in the
EV physically earned and the AC actually incurred:

| Scenario | EV ($) | AC ($) | SV ($) | CV ($) | SPI | CPI | TCPI |
|---|---|---|---|---|---|---|---|
| Q1 — actual result | 330,000 | 280,000 | +60,000 | +50,000 | 1.22 | 1.18 | 0.84 |
| Q2 — "buying schedule" | 330,000 | 412,500 | +60,000 | −82,500 | 1.22 | 0.80 | 1.44 |
| Q3 — "efficient but slow" | 216,000 | 180,000 | −54,000 | +36,000 | 0.80 | 1.20 | 0.91 |
| Q4 — "high risk" | 216,000 | 270,000 | −54,000 | −54,000 | 0.80 | 0.80 | 1.16 |

*Required.* Classify each scenario by quadrant and interpret.

*Working.* Q1 and Q2 both physically earned the same value (EV $330,000), so both show identical SV/SPI
(+$60,000 / 1.22) — the *schedule* dimension is identical. They differ only in AC, which moves CV and CPI
sharply apart (+$50,000/1.18 vs −$82,500/0.80). Q3 and Q4 both earned EV $216,000, so both show identical
SV/SPI (−$54,000 / 0.80) — again identical on the schedule dimension — but differ on AC, giving CV/CPI of
+$36,000/1.20 versus −$54,000/0.80.

*Answer.* **Q1: ahead of schedule and under budget. Q2: ahead of schedule but over budget. Q3: behind
schedule but under budget. Q4: behind schedule and over budget.**

*Interpretation.* Q1 and Q2 prove that being ahead of schedule says nothing about cost — Q2 bought that
schedule position at a steep cost premium (CPI 0.80). Q3 and Q4 prove the reverse: cost efficiency says
nothing about schedule — Q3 is a well-controlled but slow-moving account, while Q4 combines both problems
and warrants the most urgent management attention.

**The health quadrant.**

| | SPI ≥ 1.00 (on/ahead of schedule) | SPI < 1.00 (behind schedule) |
|---|---|---|
| **CPI ≥ 1.00** (on/under budget) | **Q1 — healthy**: ahead/on schedule, on/under budget | **Q3 — efficient but slow**: recoverable, usually by resequencing or adding resource within budget |
| **CPI < 1.00** (over budget) | **Q2 — buying schedule**: ahead of schedule at a cost premium; sustainable only if the premium is justified | **Q4 — highest risk**: behind schedule and over budget; escalate and investigate root cause immediately |

**Fig 6.2.5 — CPI/SPI health quadrant: Pipeline Segment 4B, Month 3, and three illustrative variants.**

0.60–1.40. A solid reference line at SPI = 1.00 (vertical) and CPI = 1.00 (horizontal) divides the plot into

*Underlying data:* the Example 6.2.5 table above (SPI and CPI columns only are plotted).

**Animation 6.2.5 — "Tracking a project's health quadrant over time" [digital-only].** Frame 1: the same

**Common pitfalls.**
- Reporting only CPI or only SPI (never both) — this is the single most common EVM reporting error and
  hides exactly the Q2/Q3 distortions shown above.
- Treating "ahead of schedule" (Q1/Q2) as unconditionally good news without checking whether it was bought
  with an adverse CV (Q2) — schedule gains achieved by overspending may not be sustainable or may not even
  be the sponsor's priority.
- Averaging CPI and SPI into a single "performance score" — the two measure different things and blending
  them destroys the diagnostic power of reading them separately.

**AI in this topic.** A BI tool can plot every control account on a live CPI/SPI quadrant chart and
automatically flag new entrants to Q4 (cross-reference KA 4.4, KA 13.5) — a strong early-warning use case at
programme scale. It cannot decide *what to do* about a Q4 account, nor whether a Q2 account's cost premium
is an acceptable trade-off for the sponsor — those are professional and commercial judgements informed by,
not made by, the chart.

**Cross-references.** KA 6.1.5 (aggregation, and how an aggregate figure can mask quadrant-level detail);
KA 6.3 (EAC forecasting differs by quadrant — see the multi-scenario EAC comparison there); KA 4.3, 4.4
(management reporting and dashboards); KA 8.4 (Monitoring & Controlling).

### 6.2.6 To-Complete Performance Index (TCPI)

**Definition & purpose.** TCPI answers a forward-looking question that CV, SV, CPI and SPI (all of which
describe performance *to date*) cannot: "what level of cost efficiency must be achieved on the *remaining*
work in order to finish within a given cost target?" It is the only one of this KA's five metrics that looks
forward rather than backward.

**The underlying principle.** TCPI compares the value of work still to be done (BAC − EV, the remaining
scope in budget terms) against the money still available to do it (BAC − AC, the remaining budget, on the
BAC basis). The result is directly comparable to CPI, because both are efficiency ratios of the same kind
(value earned per currency unit spent) — one describing the past, one describing what the future must
achieve.

**Formula.**
`TCPI = (BAC − EV) / (BAC − AC)`
where BAC, EV and AC are as previously defined and both numerator and denominator are in the same currency
(which cancels, leaving TCPI as a **dimensionless ratio**, reported to two decimal places). A variant,
`TCPI = (BAC − EV) / (EAC − AC)`, targets the current *forecast* (EAC) rather than the original BAC and is
used once EAC has been calculated — see KA 6.3 for the full EAC treatment; this KA uses the BAC-basis
formula throughout, as it requires no EAC input.

**Example 6.2.6 — TCPI for Pipeline Segment 4B at Month 3.**

*Scenario.* Continuing the Month-3 data set: BAC = $600,000; EV = $330,000; AC = $280,000.

*Required.* TCPI (BAC basis), and a comparison with the CPI already achieved (1.18, Example 6.2.3).

*Working.*
`TCPI = (BAC − EV) / (BAC − AC) = (600,000 − 330,000) / (600,000 − 280,000) = 270,000 / 320,000 = 0.84375`

*Answer.* **TCPI = 0.84** (to two decimal places).

*Interpretation.* Only 0.84 of cost efficiency is required on the remaining work to finish exactly at BAC —
comfortably *below* the 1.18 efficiency already achieved. When **TCPI < CPI**, the remaining target is
easier than the performance already delivered, so BAC remains readily achievable; this is a favourable
comparison, consistent with Q1's strong position in 6.2.5.

**Mini-case — TCPI as a red flag: revisiting the Q4 "high risk" scenario.** Using Q4 from Example 6.2.5
(BAC $600,000; EV $216,000; AC $270,000; CPI 0.80):

`TCPI = (600,000 − 216,000) / (600,000 − 270,000) = 384,000 / 330,000 = 1.1636 → 1.16`

Here **TCPI (1.16) is well above CPI (0.80)** — the remaining work must be executed at an efficiency roughly
45% better than has been achieved so far, merely to hit the original BAC. As a general rule of thumb (not a
fixed standard — organisations vary), a TCPI materially above the CPI already being delivered, and
particularly a TCPI above about 1.10–1.20, signals that the original BAC is unlikely to be recoverable
without a genuine step-change in performance or a formal re-forecast; this is the trigger point at which
KA 6.3's EAC methods become the more realistic cost target than BAC itself.

**Fig 6.2.6 — CPI achieved vs TCPI required: Q1 (healthy) vs Q4 (high risk).**
Chart type: paired bar chart. Two category groups on the horizontal axis — "Q1" and "Q4" — each with two
bars: "CPI achieved" (grey) and "TCPI required to hit BAC" (brand blue `#1D4ED8`). A horizontal reference
line at 1.00 runs across the chart. For Q1, the TCPI bar (0.84) sits below both the CPI bar (1.18) and the
reference line — a favourable gap. For Q4, the TCPI bar (1.16) sits above both the CPI bar (0.80) and the
reference line — an adverse gap, visually flagged (e.g. a warning-coloured outline).

*Underlying data:* Q1 — CPI 1.18, TCPI 0.84. Q4 — CPI 0.80, TCPI 1.16.

**Common pitfalls.**
- Comparing TCPI to 1.00 alone instead of to the CPI actually being achieved — a TCPI of 1.05 looks
  unremarkable in isolation but is a serious red flag if current CPI is only 0.85.
- Using the BAC-basis TCPI once a formal re-forecast (EAC) has superseded BAC as the realistic cost target
  — at that point the EAC-basis variant is the more meaningful figure (KA 6.3).
- Treating TCPI as achievable simply because it is mathematically calculable — a TCPI requiring, say, 40%
  better efficiency than any period achieved to date should be treated as a warning about BAC's realism, not
  as a plan.

**AI in this topic.** A forecasting tool can calculate TCPI automatically alongside CPI/SPI and flag when
the gap between them crosses an organisation-defined threshold (cross-reference KA 13.5) — useful as a
consistent, scalable early-warning trigger across many control accounts. It cannot judge whether the
required efficiency improvement is operationally realistic (e.g. whether a resourcing or productivity fix
is actually available) — that assessment requires the professional's knowledge of the work remaining, not
the ratio alone.

**Cross-references.** KA 6.2.3 (CPI, the benchmark TCPI is compared against); KA 6.3 (EAC family, and the
EAC-basis TCPI variant); KA 3.1 (management reserve — a possible response to an adverse TCPI); KA 8.4
(corrective action within Monitoring & Controlling).

### 6.2.7 Reading indices over time: trends, and the "SPI → 1" pitfall near completion

**Definition & purpose.** All five metrics in this KA are **cumulative** measures by default — each is
calculated from the sum of PV, EV and AC from project start to the current data date. Cumulative measures
are stable and resistant to single-period noise, but they have one well-documented structural weakness: as
the data date approaches the project's baselined finish, PV approaches BAC and EV can only reach BAC once
scope is 100% complete — so cumulative SPI is mathematically pulled toward **1.00** regardless of how late
the project genuinely finishes. This topic explains the mechanism and shows a worked illustration, because
misreading a late-project SPI is one of the most consequential interpretation errors in EVM practice.

**The underlying principle.** SPI = EV / PV. Near completion, PV's denominator is capped — by definition, PV
cannot exceed BAC, and in most baselines it reaches BAC exactly at the planned finish date. As the remaining
"room" between the current PV and BAC shrinks toward zero, even a project that is still behind physically
finds its SPI numerator (EV) closing the gap on a shrinking denominator, so SPI drifts upward toward 1.00 —
and, at the point of 100% scope completion (EV = BAC), SPI is *exactly* 1.00 by construction, however many
extra weeks or months it took in calendar terms to get there. SPI, being a **value-based** ratio, simply has
no mechanism left to express calendar lateness once there is no remaining PV to fall behind on.

**Example 6.2.7 — Cumulative SPI drifting toward 1.00 despite a genuine one-month schedule slip.**

*Scenario.* Pipeline Segment 4B's approved baseline (KA 6.1.2) runs PV from Month 1 to a planned finish at
Month 6 (PV = BAC = $600,000). Suppose, in this alternative trajectory, the project is consistently running
physically behind — but ultimately finishes one full calendar month later than planned, in Month 7:

| Month | PV, cumulative ($) | EV, cumulative ($) | SPI |
|---|---|---|---|
| 4 | 420,000 | 378,000 | 0.90 |
| 5 | 540,000 | 486,000 | 0.90 |
| 6 (baselined finish) | 600,000 | 560,000 | 0.93 |
| 7 (actual finish) | 600,000 | 600,000 | 1.00 |

*Required.* Compute SPI at each status point and interpret the trend.

*Working.*
`SPI(4) = 378,000 / 420,000 = 0.90`
`SPI(5) = 486,000 / 540,000 = 0.90`
`SPI(6) = 560,000 / 600,000 = 0.9333 → 0.93`
`SPI(7) = 600,000 / 600,000 = 1.00`

*Answer.* SPI reads a genuinely informative **0.90** through Months 4–5, then rises to **0.93** at the
original baselined finish (Month 6, still not complete), and reaches a perfect **1.00** at actual completion
in Month 7 — a full calendar month after the baseline finish date.

*Interpretation.* The project was, in reality, consistently and materially behind schedule (a stable 10%
shortfall through the middle of the project, and a full month's calendar slip at the end) — yet the
cumulative SPI trend actively *understates* that lateness in the final periods and erases it completely at
completion. A professional (or an unverified AI-drafted commentary, see 6.2.4's "AI in this topic") reading
only the final SPI would conclude, wrongly, that the project finished exactly on schedule. This is why
calendar-based schedule status (baseline finish date vs actual finish date, and critical-path float) must
always be checked alongside SPI in the closing stages of a project, and why the **Earned Schedule** technique
(KA 6.4) — which measures lateness in time units rather than value units — was developed specifically to fix
this weakness.

**Animation 6.2.7 — "Why cumulative SPI drifts toward 1.0 near completion" [digital-only].** Frame 1: PV and
EV lines plotted together on a Month 1–7 timeline, PV shown as a fixed baseline curve flattening at BAC from
Month 6 onward, EV shown trailing visibly below it. Frames 2–5: as the timeline advances month by month, a
live SPI readout ticks upward (0.90 → 0.90 → 0.93 → 1.00) while a separate, static "calendar lateness"
indicator continues to show a constant one-month slip throughout. Frame 6: the EV line finally reaches the
BAC ceiling in Month 7, SPI locks at 1.00, and the calendar-lateness indicator (still reading "1 month late")
remains visibly on screen for contrast. Narration cue: "SPI cannot go above 1.00 once there's no planned
value left to earn. Watch the two indicators — one converges to 'perfect,' the other doesn't move. Believe
the calendar near the finish line, not the ratio."

**Common pitfalls.**
- Reporting a late-stage improving SPI trend as evidence of "schedule recovery" without checking the
  calendar finish date and remaining float.
- Applying the same materiality thresholds to SPI throughout the project — a 0.10 shortfall is a strong
  signal mid-project but a compressed, less reliable signal in the final reporting periods.
- Forgetting that this weakness is specific to SPI (a ratio bounded by a shrinking PV denominator); CPI has
  no equivalent structural bias, because AC is not capped in the same way as PV.

**AI in this topic.** A trend-analysis or forecasting tool can be configured to compare cumulative SPI
against remaining schedule float or against an Earned Schedule calculation, surfacing exactly the kind of
divergence shown above automatically (cross-reference KA 6.4, KA 13.5) — a valuable use of AI as a
cross-check specifically because the SPI-alone signal is known to be unreliable late in a project. Without
that specific configuration, a general-purpose AI summarisation tool asked to comment on "the latest SPI"
has no inherent awareness of this completion-point effect and may produce a falsely reassuring narrative;
verifying any AI-generated schedule commentary against the actual calendar dates is essential in the closing
stages of a project.

### Key terms

- **Cost Variance (CV)** — `EV − AC`; the currency-denominated gap between value earned and cost incurred.
- **Schedule Variance (SV)** — `EV − PV`; the currency-denominated gap between value earned and value
  scheduled.
- **Cost Performance Index (CPI)** — `EV / AC`; value earned per currency unit spent; a dimensionless ratio.
- **Schedule Performance Index (SPI)** — `EV / PV`; value earned per currency unit of value planned; a
  dimensionless ratio.
- **To-Complete Performance Index (TCPI)** — `(BAC − EV) / (BAC − AC)`; the cost efficiency required on
  remaining work to hit a cost target.
- **Favourable / adverse** — CV, SV positive is favourable, negative is adverse; CPI, SPI above 1.00 is
  favourable, below 1.00 is adverse.
- **Health quadrant** — the four CPI/SPI combinations (healthy; buying schedule; efficient but slow;
  highest risk) used to characterise overall project standing.
- **Completion-point effect** — the tendency of cumulative SPI to drift toward 1.00 as PV approaches BAC
  near project completion, independent of true calendar lateness.

### Sample MCQs

**MCQ 6.2.1 [topic 6.2.1, level: recall]**
Which formula correctly defines Cost Variance (CV)?
A. `CV = PV − AC`
B. **`CV = EV − AC`** ✔
C. `CV = EV − PV`
D. `CV = EV / AC`
*Rationale:* CV compares earned value against actual cost. A uses the wrong first term (PV instead of EV);
C is the formula for SV; D is the formula for CPI.

**MCQ 6.2.2 [topic 6.2.1, level: application — numerical]**
A control account has EV = $180,000 and AC = $150,000 at the data date. What is the Cost Variance?
A. −$30,000
B. **$30,000** ✔
C. $330,000
D. 1.20
*Rationale:* `CV = 180,000 − 150,000 = 30,000` (favourable). A reverses the subtraction (AC − EV); C adds
instead of subtracting; D is the CPI (EV/AC), not CV — a unit/metric conflation.

**MCQ 6.2.3 [topic 6.2.4, level: application — numerical]**
At the data date, EV = $540,000 and PV = $600,000. What is the SPI?
A. 1.11
B. **0.90** ✔
C. −$60,000
D. 1.00
*Rationale:* `SPI = 540,000 / 600,000 = 0.90`. A inverts the ratio (PV/EV instead of EV/PV); C is the SV
value mislabelled as SPI, a unit-confusion error; D wrongly assumes on-schedule performance.

**MCQ 6.2.4 [topic 6.2.3, level: analysis]**
A project reports a cumulative CPI of 0.85. This indicates that, for the work performed to date, the
project:
A. **Has spent more than the budgeted value of the work performed — a cost overrun** ✔
B. Is running ahead of the original schedule
C. Will automatically finish exactly 15% under budget
D. Has a favourable cost variance
*Rationale:* CPI < 1.00 means less than $1 of value is earned per $1 spent — cost-inefficient, i.e. an
overrun on work performed. B confuses CPI (cost) with SPI (schedule). C wrongly assumes a simple linear
projection, which is not how CPI translates into a final outcome (that requires the EAC methods of KA 6.3).
D contradicts CPI < 1.00, which corresponds to an adverse, not favourable, CV.

**MCQ 6.2.5 [topic 6.2.6, level: application — numerical]**
A project has BAC = $1,000,000. At the data date, EV = $400,000 and AC = $500,000. What is the TCPI
(BAC basis)?
A. 0.80
B. **1.20** ✔
C. 0.83
D. 2.50
*Rationale:* `TCPI = (1,000,000 − 400,000) / (1,000,000 − 500,000) = 600,000 / 500,000 = 1.20`. A is
actually the CPI (`EV / AC = 400,000 / 500,000 = 0.80`), a common conflation of the two ratios. C inverts
the correct fraction. D mistakenly computes `BAC / EV`.

**MCQ 6.2.6 [topic 6.2.7, level: analysis]**
Why can cumulative SPI become an unreliable indicator of true schedule lateness as a project nears
completion?
A. Because EV always exceeds AC in the final reporting period
B. **Because PV is capped at BAC and EV cannot exceed BAC at scope completion, so SPI is mathematically
   pulled toward 1.00 regardless of genuine calendar lateness** ✔
C. Because CPI and SPI always converge to the same value at completion
D. Because the measurement method automatically switches to Level of Effort in the final period
*Rationale:* As remaining PV shrinks toward zero near the baselined finish, SPI's denominator stops growing
while EV can still close the gap, pulling the ratio toward 1.00 even if the project finishes calendar-late
(Example 6.2.7). A, C and D describe mechanisms that do not occur in EVM.

### Self-check questions

1. A control account has BAC = $800,000. At the data date, PV = $500,000, EV = $460,000 and AC = $400,000.
   Calculate CV, SV, CPI and SPI, and state whether each is favourable or adverse.
2. Explain, in one or two sentences, why a project can show a favourable CV at the same time as an adverse
   SV (or vice versa) — refer to the interpretation matrix in 6.2.5.
3. Using the same data as Question 1, calculate TCPI (BAC basis) and compare it with the CPI you calculated.
   What does the comparison suggest about the achievability of BAC?
4. Why should a controls professional be cautious about relying solely on cumulative SPI to judge schedule
   performance in the final reporting periods of a project?

**Answers**

1. `CV = EV − AC = 460,000 − 400,000 = +60,000` (favourable). `SV = EV − PV = 460,000 − 500,000 = −40,000`
   (adverse). `CPI = EV / AC = 460,000 / 400,000 = 1.15` (favourable). `SPI = EV / PV = 460,000 / 500,000 =
   0.92` (adverse).
2. CV/CPI measure cost efficiency (EV compared with AC) while SV/SPI measure schedule performance (EV
   compared with PV) — two independent comparisons of the same EV against two different reference points.
   As Example 6.2.5 showed, a project can be cost-efficient relative to work done while still behind the
   time-phased plan (or the reverse), because AC and PV are independent of each other.
3. `TCPI = (BAC − EV) / (BAC − AC) = (800,000 − 460,000) / (800,000 − 400,000) = 340,000 / 400,000 = 0.85`.
   Since TCPI (0.85) is below the CPI already achieved (1.15), less efficiency is required on the remaining
   work than has already been delivered — BAC remains comfortably achievable on current performance.
4. Near completion, PV approaches BAC and EV can only reach BAC once scope is 100% complete, so cumulative
   SPI is mathematically pulled toward 1.00 regardless of genuine calendar lateness (Example 6.2.7) — a
   project that finishes weeks or months late can still show SPI at or near 1.00 at completion. True
   lateness should be checked against the calendar baseline/finish date and remaining float, or measured
   with Earned Schedule (KA 6.4), not read from cumulative SPI alone.
