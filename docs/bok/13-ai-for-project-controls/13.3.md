# Domain 13 — AI for Project Controls & Project Management: Concepts, Tools & Practice

## KA 13.3 — Prompting & working with GenAI

KA 13.1 introduced what a large language model (LLM) is and, at a conceptual level, how it generates text;
KA 13.2 established why the data an AI tool sees determines the quality of what it returns. This KA turns
those foundations into a practical skill: how a project controls professional instructs a general-purpose
AI assistant so that it does useful, reliable work, and how that professional then checks what comes back
before using it. Prompting is not a party trick or a search-box habit — it is a professional technique with
identifiable good and poor practice, the same way a well-structured management report or a well-drafted
variation notice is a professional technique. Poorly instructed AI tools produce fluent, confident,
plausible-sounding output that can be subtly or badly wrong; well-instructed AI tools, checked properly,
can materially speed up drafting, extraction and summarising work that used to take hours. The dividing
line between the two is almost never the underlying model — it is the quality of the prompt and the rigour
of the verification that follows it. This KA covers, in order: how a GenAI chat interaction actually works
(13.3.1); the core prompt-engineering techniques (13.3.2–13.3.7); grounding and retrieval-augmented
generation, or RAG (13.3.8); the professional's non-delegable duty to verify AI output (13.3.9); five
worked prompt patterns for common project-controls tasks, each carried through the recurring **Meridian
Rail Contracting LLC / Pipeline Segment 4B** illustration first established in KA 6.1 (BAC $600,000 / SAR
2,250,000 at an illustrative SAR 3.75 = USD 1; Month-3 status date PV $270,000, EV $330,000, AC $280,000
ledger-only or $305,000 accrual-adjusted — KA 6.1.3, KA 6.2.1) (13.3.10–13.3.14); and confidentiality and
governance (13.3.15–13.3.16). The governing principle of the whole PCP-AI syllabus
applies with particular force here: **AI proposes; the professional disposes.** A prompt is a request, not
an instruction the professional is obliged to accept the answer to.

### 13.3.1 How generative AI chat works, for the practitioner

**Definition & purpose.** A GenAI chat tool is a conversational interface to a large language model: the
user types natural-language input (a **prompt**) and the model generates a natural-language response one
token (roughly, a word-fragment) at a time, each token chosen based on everything that has come before it
in the conversation (KA 13.1 covers the token-by-token generation mechanics in depth; this topic covers only
what a practitioner needs to prompt effectively). Three mechanical concepts matter directly for how you
should prompt: the context window, the system/user prompt distinction, and temperature.

**The context window.** Everything the model can "see" when generating its next response — the
conversation so far, any documents or data pasted in, and any standing instructions — is bounded by the
**context window**, measured in tokens. Context windows vary by tool and are typically stated in the
thousands to low hundreds of thousands of tokens; the exact size changes as tools are updated, so it should
be treated as an evolving, tool-specific figure rather than a fixed number to memorise. The practical
consequence is threefold: a very long document pasted into a chat may be truncated, summarised, or push
earlier parts of the conversation out of the model's working memory; a long-running conversation can
similarly "forget" something established many turns earlier; and the model has **no memory across separate
conversations** unless the specific tool explicitly provides a persistent memory or file-upload feature —
it does not retain what a professional told it yesterday in a different chat. Do not assume the model
remembers a constraint, a figure or a persona set earlier unless it is still visible within the current
context window; restate anything load-bearing.

**Tokens.** A **token** is the unit a model actually processes — roughly, but not exactly, a word or
word-fragment; as a rough rule of thumb, one token is often close to three-quarters of an English word,
though this varies with vocabulary, punctuation and language. The practical implication for a professional
is proportional, not precise: a two-page cost report extract consumes noticeably more of the context window
than a two-sentence question, and a prompt built from several pasted documents plus a long conversation
history can approach the window's limit faster than intuition suggests, particularly for tables and numeric
data, which tokenise less efficiently than plain prose. If a tool's response starts ignoring instructions
given earlier in a long session, a full context window — not a fault in the model's "attention" or
willingness — is a common, checkable explanation; starting a fresh conversation with the essential context
restated is often the simplest fix.

**System prompt vs user prompt.** Most GenAI chat tools distinguish between a **system prompt** — standing
instructions that frame the model's behaviour, tone or role for the whole session, often set by the
platform, the organisation's deployment, or (in some consumer tools) a user-editable "custom instructions"
feature — and the **user prompt**, the specific task instruction typed for a given turn. A professional
using a consumer chat tool typically interacts mainly through the user prompt, but where a persistent
role/style setting is available (13.3.3), setting it once removes the need to repeat that framing every
time. In an enterprise or API deployment, an organisation's project controls function may configure a
standing system prompt (e.g., "always flag any figure you cannot trace to the data provided") — this is a
governance lever, developed further in 13.3.16 and KA 13.6.

**Temperature.** Temperature is a generation setting that controls how deterministic or varied the model's
token choices are: a low temperature makes the output more focused and repeatable (the model consistently
picks its highest-probability next token), while a higher temperature allows more varied, less predictable
phrasing. Most consumer chat interfaces do not expose this setting directly — it is fixed by the tool or
only adjustable via an API — but the concept matters conceptually: for numeric, factual or extraction tasks
(13.3.10, 13.3.14), a lower-temperature, more deterministic style of output is preferable and reduces the
chance of unnecessary phrasing drift between repeated runs; for early-stage brainstorming (e.g., generating
options for a report structure), more variation can be useful. Where a tool does not expose the setting,
achieving a similarly focused result is a matter of prompt design (13.3.2, 13.3.6) rather than a slider.

**Common pitfalls.**
- Assuming the model remembers a fact, constraint or persona from earlier in a long conversation, or from a
  previous session, without it still being visible in context.
- Pasting an entire long contract or cost report and assuming the model has processed all of it with equal
  attention — very long inputs are more prone to partial omission than short, targeted extracts.
- Treating "the AI said it" as evidence, rather than as one draft, fluently generated — see 13.3.9.

**AI in this topic.** This entire chapter is, in effect, "AI in this topic" — the practical skill of
directing a general-purpose assistant. The honest limit to state up front: nothing about a larger context
window or a well-chosen temperature setting changes the model's fundamental behaviour of generating the
statistically most plausible continuation of the prompt, not a verified fact — that is why 13.3.9 exists as
a mandatory step, not an optional one.

**Cross-references.** KA 13.1 (tokens, training, inference, the mechanics of generation in depth); KA 13.2
(data quality feeding what a model can be grounded in); 13.3.16 (system-prompt governance).

### 13.3.2 The anatomy of an effective prompt

**Definition & purpose.** **Prompt engineering** is the practice of structuring an instruction to an AI
tool so that it reliably produces a usable, on-target response, first time or with minimal correction. It
is not a mystique — it is closely analogous to writing a clear work instruction or terms of reference for a
junior colleague who is fast, tireless and extremely well-read, but who has no memory of your project, no
authority to ask a clarifying question unless invited to, and no accountability for being wrong.

**The underlying principle.** A vague instruction leaves the model to guess at everything it was not told —
audience, scope, format, level of detail, what counts as "done." Because the model will always produce
*something* fluent-sounding rather than refuse for lack of clarity, an under-specified prompt does not fail
loudly; it fails quietly, by returning a confident answer to a slightly different question than the one the
professional meant to ask. Specificity is therefore not a stylistic nicety — it is the main lever a
professional has over output quality.

**Technique — the five components.** A well-formed prompt for a professional task typically supplies:

1. **Role/persona** (optional but often useful) — who the model should "act as" (13.3.3).
2. **Task** — a precise statement of what is required, in an active verb ("summarise," "extract," "draft,"
   not "tell me about").
3. **Context** — the information the model needs but does not already have: data, background, audience,
   purpose.
4. **Examples** (optional, but powerful for format/tone-sensitive tasks — 13.3.4).
5. **Constraints and output format** — length, structure, tone, what to exclude, and what to do if
   information is missing (13.3.6).

**Worked example — poor vs good.**

*POOR prompt:* "Tell me about the cost situation on Pipeline Segment 4B."

*Why it is poor.* No task verb (summarise? diagnose? draft a report paragraph?), no data supplied (the
model has no access to Meridian's actual figures unless they are pasted in or retrieved — 13.3.8), no
audience, no format, no length. A general-purpose assistant will likely respond with a generic explanation
of what "cost situation" analysis typically involves — accurate in the abstract, useless for this project.

*GOOD prompt:* "Act as a project controls analyst. Using the Month-3 data below for Pipeline Segment 4B
(PV $270,000; EV $330,000; AC $305,000, accrual-adjusted), draft a two-paragraph cost-performance commentary
for a client steering committee that has no EVM background. State CV, SV, CPI and SPI, say in plain English
whether each is favourable or adverse, and do not speculate on the cause of any variance beyond what these
figures show. Maximum 150 words."

*Why it is better.* Role, task, context (with figures explicitly stated as accrual-adjusted, forestalling
the 13.3.11 mini-case), audience, an explicit instruction against unsupported speculation, and a format/
length constraint are all present. The professional still must verify the arithmetic and tone before use
(13.3.9) — a good prompt reduces correction effort; it does not remove the verification step.

**Common pitfalls.**
- Over-loading a single prompt with several unrelated tasks ("summarise this, also check the numbers, also
  draft an email") — output quality degrades when the model must juggle several unstated priorities.
- Assuming a well-engineered prompt guarantees a correct answer — it improves the odds of a *useful first
  draft*, nothing more.

**AI in this topic.** Structured prompting is a skill that transfers across almost all general-purpose
assistants; it is not tool-specific. The honest limit: no amount of prompt craft substitutes for supplying
correct, complete source data (KA 13.2) — a perfectly engineered prompt built on an incomplete ledger
extract still produces a confidently wrong answer (13.3.11's mini-case).

### 13.3.3 Role and persona framing

**Definition & purpose.** Role or persona framing tells the model what expertise, register and perspective
to adopt — e.g., "act as a cost engineer," "act as a contracts manager writing to a subcontractor," "act as
a graduate analyst who needs each acronym explained." It is a lightweight way of setting tone, technical
depth and vocabulary without writing a long style guide each time.

**The underlying principle.** An LLM has, in effect, been exposed during training to an enormous range of
registers and professional voices; a role instruction narrows which of those registers it draws on for this
response. It does not grant the model genuine domain judgement it otherwise lacks — asking it to "act as a
FIDIC-qualified contracts lawyer" changes its *tone and framing*, not the reliability of its legal content,
which still requires the same verification as any other output (13.3.9, cross-ref 7.2).

**Worked example — poor vs good.**

*POOR prompt:* "Explain retention to me."

*GOOD prompt:* "Act as a project controls analyst briefing a newly appointed, non-commercial project
manager who is unfamiliar with construction payment mechanics. In plain English and no more than four
sentences, explain what retention is and why it is withheld, using Pipeline Segment 4B's 10.0% retention
rate as the illustration."

*Why it is better.* The persona ("briefing a non-commercial PM") and the constraint ("plain English, four
sentences") together do more to shape a usable answer than a generic knowledge request — the same
underlying question, answered for a finance director, a site engineer or a first-year graduate, should read
very differently, and role framing is the fastest way to get the right one.

**Persisting a persona.** Repeating the same role framing every prompt is tedious; several tools offer a
persistent "custom instructions" or saved-preferences feature (13.3.1) that applies a standing role, tone or
formatting preference to every new conversation without re-stating it. Where available, this is a sensible
efficiency gain for a recurring role (e.g., "always respond as a project controls analyst; always use
British English and USD with SAR in parentheses at first mention"). It is a convenience setting, not a
governance control — it does not itself enforce the verification or confidentiality disciplines of 13.3.9
and 13.3.15, which still depend on the individual using the tool each time.

**Common pitfalls.**
- Treating an assigned persona as a guarantee of accuracy ("it's acting as a lawyer, so the contract advice
  must be sound") — persona changes voice, not verified correctness.
- Stacking contradictory personas in one prompt ("act as both the contractor's QS and the client's auditor")
  without asking for the two perspectives to be clearly separated, producing a blended, unusable answer.
- Over-relying on a persistent persona setting to the point that an unusual task (needing a different tone
  or audience than the standing default) is answered in the wrong register because the standing instruction
  was never overridden for that specific prompt.

**AI in this topic.** Persona framing is one of the most reliable, low-effort techniques for tailoring
output register to audience (cross-ref KA 4.3's audience-appropriate reporting). It should never be used to
imply unearned authority (e.g., presenting an "acting as legal counsel" answer to a subcontractor without
disclosing it is AI-drafted and unverified) — see 13.3.16 on governance and disclosure.

**Cross-references.** 13.3.2 (prompt anatomy); KA 4.3 (audience-appropriate reporting); 7.2 (contract
administration, where persona-framed AI drafting is common but verification is non-negotiable).

### 13.3.4 Providing examples: few-shot prompting

**Definition & purpose. Few-shot prompting** supplies the model with one or more worked examples of the
desired input-to-output pattern before asking it to apply that pattern to a new case; **zero-shot
prompting** is asking without any example. Few-shot prompting is the single most effective technique for
locking down a specific *format*, *tone* or *level of detail* that is hard to describe in words but easy to
demonstrate.

**The underlying principle.** The model generates by pattern-continuation; showing it one or two concrete
instances of the pattern you want dramatically narrows the space of plausible continuations compared with a
prose description of the same pattern, especially for house-style formatting (a specific report layout, a
specific table structure, a specific level of technical detail).

**Worked example — poor vs good.**

*POOR prompt:* "Summarise this month's variance in our usual style." (No example of "our usual style" is
supplied — the model must guess, and different runs may drift toward different formats.)

*GOOD prompt:* "Here is last month's variance commentary as a style example:
'*Month 2: CV was favourable at +$18,000 (CPI 1.07), driven by efficient trenching productivity on WP2.
SV was adverse at −$12,000 (SPI 0.94), reflecting a two-week permit delay on WP4, now resolved.*'
Using the same two-sentence structure (cost sentence first, schedule sentence second, each stating the
figure, the index and one stated driver only if evidenced), draft the Month-3 commentary using: CV
+$25,000, CPI 1.08, SV +$60,000, SPI 1.22. Do not state a driver for either variance — none has been
confirmed yet."

*Why it is better.* The example fixes the exact structure and level of granularity; the explicit "do not
state a driver — none confirmed" instruction (a constraint, 13.3.6) prevents the model from pattern-matching
its way into inventing a plausible-sounding cause it was not given, a genuine and common failure mode.

**How many examples.** One well-chosen example is often enough to fix a simple format; two or three, ideally
spanning a small range of cases (a favourable month and an adverse month, say), help the model generalise
the pattern rather than over-fit to one instance's specific wording. A **negative example** — explicitly
showing a version of the output that is *not* wanted, alongside a short note on why — can be a sharper
corrective than a further positive example when a prior draft has repeatedly made the same mistake (e.g.,
"not like this: '...driven by strong team performance' — that names a driver with no evidence; like this
instead: '...no driver confirmed for this period'").

**Common pitfalls.**
- Supplying an example that itself contains an error or an outdated figure — the model will faithfully
  reproduce the pattern, error included.
- Providing an example from an unrelated context (a different project's report style) without checking it
  actually transfers — few-shot prompting locks in *pattern*, not *appropriateness*.
- Supplying so many examples that the prompt itself becomes unwieldy and consumes a disproportionate share
  of the context window (13.3.1) relative to the actual task instruction.

**AI in this topic.** Few-shot prompting is especially valuable for recurring, house-style deliverables
(monthly commentary, standard risk-register entries, standard meeting-minute formats) because the example
library, once built, can be reused prompt after prompt — an early, low-risk step toward the prompt
governance/template libraries discussed in 13.3.16.

**Cross-references.** 13.3.2 (anatomy); 13.3.11 (the report-narrative pattern, which builds directly on
this technique); KA 4.3 (report design and cadence).

### 13.3.5 Step-by-step decomposition and chain-of-thought style prompting

**Definition & purpose.** Asking the model to work through a task in explicit, ordered steps before giving
a final answer — often called **chain-of-thought** or **step-by-step prompting** — tends to improve
accuracy and auditability on multi-step tasks (a calculation, a multi-clause comparison, a structured
extraction) compared with asking for the final answer directly.

**The underlying principle, stated honestly.** Because the model generates its response token by token,
forcing it to lay out intermediate steps changes *what it generates first* — it commits to a partial,
checkable line of working before committing to a final figure or conclusion, which both improves the odds
of a correct multi-step answer and, importantly, gives the professional something concrete to check line by
line. This is a genuinely useful prompting technique; it is not evidence that the model possesses
human-like internal reasoning, and a plausible-looking chain of steps can still arrive at a wrong final
answer, or (less often) can itself be a fluent-sounding rationalisation rather than the model's actual
generation process (KA 13.1 covers the mechanics; the practical implication here is that the steps must
still be checked, not merely the final answer). Some current AI tools also offer a built-in "reasoning" or
"extended thinking" mode that performs a version of this decomposition automatically before answering;
where available, this can reduce — but does not remove — the value of prompting for it explicitly, and
exactly what any given tool offers is evolving quickly enough that it should be checked against the tool in
use rather than assumed.

**Worked example — poor vs good.**

*POOR prompt:* "What's the TCPI for a project with BAC $800,000, EV $460,000 and AC $400,000?"

*GOOD prompt:* "Calculate TCPI (BAC basis) for a project with BAC $800,000, EV $460,000 and AC $400,000.
Show the formula, substitute the figures, and state the result to two decimal places, then compare it in
one sentence with the CPI for the same data."

*Why it is better.* Both prompts can produce the right final number, but the second forces a visible
working (`TCPI = (BAC − EV)/(BAC − AC) = (800,000 − 460,000)/(800,000 − 400,000) = 340,000/400,000 = 0.85`)
that the professional can check step by step against the same formula from KA 6.2 — an arithmetic slip
(e.g., using EAC instead of AC in the denominator) is far easier to spot in a shown working than in a bare
final number.

**Common pitfalls.**
- Accepting a fluent, well-formatted chain of steps as proof of correctness without independently checking
  at least the final substitution — a wrong number can still be wrapped in a very plausible-looking method.
- Asking for step-by-step working on a task where no real calculation exists (e.g., a qualitative judgement
  call) — this can push the model toward inventing a spurious appearance of rigour.

**AI in this topic.** This technique is one of the most reliable ways to make AI-assisted calculation
auditable, which matters directly for project controls, where every number must trace back to a defensible
working (cross-reference the Example format in the style spine itself, §6). It does not change the duty to
verify — see 13.3.9.

**Cross-references.** KA 6.2 (the TCPI formula used above); 13.3.9 (verification); KA 13.1 (token-by-token
generation mechanics).

### 13.3.6 Specifying output format, tone and constraints

**Definition & purpose.** The final component of a well-formed prompt states the boundaries of the answer:
its structure (prose, bullet points, a table), its length, its tone/register, and explicitly what it should
*not* do (speculate, use jargon, exceed a word count, include information not supplied).

**The underlying principle.** Without an explicit format instruction, the model chooses a plausible default
format based on the apparent nature of the request — often verbose, hedged prose that is not directly
usable in a report, a table, or an email without rework. Stating the format up front removes an entire
round of manual reformatting and, more importantly, stating explicit *negative* constraints ("do not
speculate beyond the data given," "do not invent a clause reference you were not given") is one of the more
effective, if underused, techniques for narrowing the model away from its tendency to fill an information
gap with something plausible-sounding rather than flagging the gap (KA 13.1's treatment of hallucination;
13.3.9 below).

**Specifying tone.** Tone is easy to under-specify because it feels subjective, but it responds well to
concrete, comparative instruction: naming the intended reader ("a first-time client stakeholder," "a
technically literate cost engineer") is usually more reliable than an adjective alone ("professional tone"),
because different readers imply different jargon tolerance and sentence length even when both could
honestly be described as "professional." Where a house style already exists, referencing it directly
("match the tone of the attached example," combining this technique with 13.3.4's few-shot approach) is more
reliable still than describing tone in the abstract.

**Worked example — poor vs good.**

*POOR prompt:* "Give me some test cases for checking the new dashboard is calculating correctly."

*GOOD prompt:* "Produce the test cases as a markdown table with columns: Scenario ID | Input data | Expected
result | Pass/fail criterion. Cover at least: a straightforward mid-project case, a case where AC is zero
(project just started), a case using a Level of Effort work package, and a case with an adverse cost
variance. Do not calculate the 'expected result' values yourself — leave that column marked 'TBC — analyst
to compute' for me to complete and verify independently."

*Why it is better.* The table format is immediately usable; the scenario coverage is specified rather than
left to chance; and — critically — the constraint instructing the model *not* to compute the expected
values itself pre-empts a specific, realistic failure mode developed fully in 13.3.14: an AI-generated
"expected answer" in a test case is itself an unverified calculation and must not silently become the test
oracle.

**Common pitfalls.**
- Specifying tone but not structure (or vice versa) and receiving an answer that reads well but cannot be
  pasted directly into the target document without reformatting.
- Treating "keep it short" as a sufficient constraint — a stated word or bullet-point limit produces a far
  more consistent result across repeated prompts than a vague instruction.

**AI in this topic.** Precise output-format instructions are what make AI drafting genuinely time-saving
rather than merely novel — the time saved by a fluent first draft is lost again if every draft needs
substantial reformatting before it is usable.

**Cross-references.** 13.3.2 (anatomy); 13.3.14 (test-scenario pattern, developed from the example above);
KA 4.3, KA 4.4 (report and dashboard design conventions the format instruction should match).

### 13.3.7 Iterative refinement: treating the first output as a draft

**Definition & purpose.** **Iterative refinement** is the discipline of treating an AI's first response as a
draft to be critiqued and refined through follow-up prompts, rather than as a finished deliverable — asking
for a specific correction, a tone adjustment, a tightened length, or a missing element, in the same
conversation, so the model has the prior draft as context.

**The underlying principle.** Because a single prompt, however well engineered, cannot always anticipate
every requirement, the most efficient path to a usable result is frequently not "write the perfect prompt
first time" but "write a reasonable prompt, then refine in one or two further turns" — refinement turns are
typically faster than re-explaining the whole task from scratch, because the context window (13.3.1) retains
the prior exchange.

**Worked example — a refinement sequence.**

*Turn 1 (initial prompt):* the GOOD prompt from 13.3.2, requesting a 150-word cost-performance commentary.

*Turn 1 output (realistic draft, described):* a technically correct two-paragraph commentary, but one that
opens with "In the current reporting period, it is observed that..." — grammatically fine, but wordy and
passive, not matching Meridian's usual direct, active-voice house style.

*Turn 2 (refinement prompt):* "Good content. Rewrite in active voice, cut the opening throat-clearing, and
open directly with the CV figure. Keep it under 150 words."

*Turn 2 output (realistic draft, described):* a tightened version opening "Cost performance was favourable
in Month 3: CV was +$25,000 (CPI 1.08)..." — materially more usable without having re-specified the whole
brief.

*Verification step (applies regardless of how many refinement turns were used).* Before use, the
professional checks: every figure against the source EVM data (KA 6.1/6.2); that no driver/cause has been
asserted beyond what was supplied (13.3.6's constraint); and that the tone genuinely matches house style, not
merely the AI's assessment of it.

**Common pitfalls.**
- Refining tone and format extensively while never re-checking that the underlying figures are still
  correct after several edits — a late-stage refinement pass can occasionally alter a stated number along
  with the prose around it.
- Treating an unlimited number of refinement turns as a substitute for a better-specified initial prompt —
  each turn still costs professional review time; a well-engineered first prompt (13.3.2) reduces the
  number of refinement cycles needed.

**AI in this topic.** Iterative refinement is what makes prompting closer to a working conversation with a
capable assistant than a single, one-shot query — and it is precisely why the context-window discipline of
13.3.1 (know what the model can and cannot still "see") matters in practice.

**Cross-references.** 13.3.1 (context window); 13.3.2 (initial prompt anatomy); 13.3.9 (verification, which
applies to every draft regardless of how many refinement turns preceded it).

### 13.3.8 Grounding and retrieval-augmented generation (RAG)

**Definition & purpose.** A model's default way of answering draws only on patterns learned during training
— its **parametric knowledge** — which has no awareness of Meridian's actual contract, cost ledger or risk
register unless that information is supplied within the prompt or made available through a connected
retrieval system. **Grounding** means constraining the model's answer to specific, supplied or retrieved
source material rather than its general training. **Retrieval-Augmented Generation (RAG)** is the
architecture most tools use to do this at scale: before generating an answer, the system searches an
approved document store (a contract repository, a project's cost ledger extracts, a knowledge base) for
passages relevant to the query, and supplies those passages to the model alongside the user's prompt, so the
model generates its answer *from the retrieved material* rather than from memory alone. Retrieval is
typically done by comparing the *meaning* of the query against the *meaning* of indexed passages (so-called
semantic search), rather than only matching exact keywords, which is why a RAG-style tool can often find a
relevant clause even when the query's wording differs from the contract's own wording — a genuine practical
strength, and also a further point where the retrieval step itself can be checked: does the retrieved
passage actually answer the question asked, or merely resemble it?

**The underlying principle — why RAG reduces, but does not eliminate, hallucination.** A **hallucination**
is a fluent, confident output that is factually wrong or unsupported (KA 13.1). Grounding a response in
retrieved source material reduces hallucination because the model has actual, relevant text in front of it
to draw from instead of having to reconstruct an answer purely from general training patterns — this is a
genuine and material improvement for document-heavy, factual tasks. It does **not** eliminate the risk,
for several honestly stated reasons: the retriever can fetch the wrong or an irrelevant passage (a search
failure, not a generation failure, but with the same visible symptom); the model can still misread,
misattribute or blend a retrieved passage with its own general training knowledge; the retrieved material
itself may be outdated, incomplete or simply wrong (KA 13.2's "garbage in, garbage out" applies to the
retrieval store exactly as it does to any other data source); and, where no relevant passage exists at all,
a poorly governed system can still generate a plausible-sounding answer rather than clearly stating that
nothing relevant was found. A well-built RAG tool typically shows its sources (a citation or passage
reference) precisely so the professional can check grounding — but the presence of a citation is not itself
proof the citation supports the claim next to it; that must still be checked (13.3.9).

**Common pitfalls.**
- Assuming any tool that "shows sources" is automatically hallucination-free — the citation confirms *a*

- Feeding a RAG-style tool an out-of-date or incomplete document store (an old contract revision, a stale

- Assuming grounding applies automatically in an ordinary chat tool — general-purpose consumer assistants
  ground answers only in what is explicitly pasted into the conversation unless the tool specifically offers
  a document/knowledge-connection feature.

**AI in this topic.** RAG-style, document/knowledge-grounded tools are a distinct category of AI product
from a general-purpose chat assistant used without any connected data — KA 13.4 develops the tool-category
distinctions in depth. The honest summary for this KA: grounding is a real and valuable risk-reduction
technique, not a guarantee, and the professional's verification duty (13.3.9) applies identically to
grounded and ungrounded output.

### 13.3.9 Verifying AI output: the professional's duty to check

**Definition & purpose.** Verification is the deliberate, structured check of an AI-generated output against
its source data, the professional's own domain knowledge, and the standard the deliverable must meet, before
that output is used, relied upon or passed on. It is not optional, and it is not satisfied by the output
"looking right" — fluent, well-formatted, confident-sounding text is precisely what a language model is
optimised to produce whether or not it is correct, which makes surface plausibility the least reliable signal
of accuracy available to the reviewer.

**The underlying principle.** Accountability for an estimate, a forecast, a variance narrative or a contract
interpretation does not transfer to the AI tool that helped draft it — it remains with the named professional
who used and issued it, exactly as the style spine's governing principle states: **AI proposes; the
professional disposes.** Verification is therefore not a courtesy step; it is the mechanism by which that
accountability is actually discharged.

**Technique — a four-part verification checklist.**

1. **Traceability.** Does every figure, date and fact in the output trace back to a source the professional
   can independently point to (a ledger, a signed contract, a prior verified report)? Anything that cannot
   be traced is either wrong, or was supplied by the model from unstated general knowledge — treat it as
   unverified until checked.
2. **Unsupported claims.** Has the model asserted a cause, a driver or a conclusion that was not actually
   given to it or evidenced in the source material (a subtle form of hallucination — confident causal
   narrative filling a gap the data does not fill)?
3. **Internal consistency.** Do the figures agree with each other and with previously issued, verified
   reports (e.g., does a stated CPI actually equal EV/AC using the figures quoted in the same output)?
4. **Fit for purpose and governance.** Is the tool used, and the data pasted into it, appropriate for the
   sensitivity of the task (13.3.15), and does the output meet the format/audience/tone brief actually
   given?

**Fig 13.3.3 — The AI-output verification gate.**
Diagram type: a four-stage decision flow, left to right, each stage a brand-blue (`#1D4ED8`) diamond

already established for Pipeline Segment 4B in KA 6.1.3 and KA 6.2.1.

**Common pitfalls.**
- **Over-trust / automation bias** — treating a fluent, well-structured AI answer as more likely correct
  because of *how* it is written, rather than checking *what* it says; polish and accuracy are unrelated
  qualities in AI-generated text.
- Verifying only the parts of an output that look unusual, and skimming past the parts that look routine —
  routine-looking figures are exactly where a small, plausible error (an off-by-one date, a slightly stale
  balance) is easiest to miss.
- Delegating verification itself to a second AI tool ("ask the AI to check the AI's answer") as a substitute
  for tracing figures to source — this can be a useful *additional* cross-check, but it does not discharge
  the professional's own verification duty, because a second model can share the same blind spots as the
  first, or introduce new ones.

**AI in this topic.** There is no category of AI tool, however capable or well-grounded, for which this
verification duty does not apply. This is the single most important idea in this KA, and it is developed
further, at the level of an organisational policy and audit trail, in KA 13.6.

**Cross-references.** KA 13.1 (hallucination); KA 13.6 (governance, audit trail, sign-off); 13.3.11 (the
full mini-case).

### 13.3.10 Prompt pattern: extracting data from a document

**Definition & purpose.** Extraction tasks ask an AI tool to pull structured information (figures, dates,
named parties, obligations) out of unstructured or semi-structured text — an email, a site note, a scanned
report's transcribed text — into a usable table or list. This is one of the most genuinely time-saving GenAI
applications for project controls, and one of the easiest to get subtly wrong if the prompt does not force
completeness.

**Worked example — the Pipeline Segment 4B Month-3 site cost note.**

*Source document (an informal site cost update, as received by the project controls analyst):*

> "Site cost update — Pipeline Segment 4B, Month 3 close. Labour bureau confirms $140,000 posted to date.
> Materials invoiced and received: $95,000. Plant/equipment hire recharges: $30,000. Subcontract (pipe
> welding, ABC Welding Services): $15,000 invoiced and paid to date. Note: ABC's site supervisor has also
> verified an additional c.$25,000 of welding physically complete and signed off in the last three weeks,
> but ABC has not yet submitted an invoice for it — expect this on their next monthly application."

*POOR prompt:* "Extract the costs from this note."

*Why it is poor.* No output format is specified, and — critically — nothing tells the model how to treat
the final sentence, which describes cost that is *not yet invoiced*. A plausible poor-prompt response simply
totals the four invoiced figures ("Total: $280,000") and either drops the accrual note or folds it into a
narrative sentence easily missed when the table is copied into a spreadsheet.

*GOOD prompt:* "Extract the cost data from the note below into a markdown table with three columns: Cost
element | Amount ($) | Status (Invoiced or Accrued-not-yet-invoiced). Include every cost mentioned, including
any cost described as completed or verified but not yet invoiced — do not fold it into the invoiced total.
Add a final row showing (a) total invoiced and (b) total including accrued-not-yet-invoiced amounts,
separately."

*Realistic output (described).* A four-row table — Labour $140,000 Invoiced; Materials $95,000 Invoiced;
Equipment $30,000 Invoiced; Subcontract $15,000 Invoiced — plus a fifth row, Subcontract $25,000
Accrued-not-yet-invoiced, and a totals row reading "Total invoiced: $280,000; Total including accrual:
$305,000."

*Verification step.* The professional must (a) trace each of the four invoiced figures back to the actual
cost ledger (KA 6.1.3), not merely to the note describing them; (b) confirm the $25,000 accrual figure is
based on a genuine, evidenced sign-off (a measured/verified quantity, not a verbal estimate) before it is
booked as an accrual (KA 1.3, KA 1.4); and (c) re-read the source note itself for anything the extraction
might have silently dropped (a materials retention note, a disputed amount) that a purely mechanical
extraction could miss without being told explicitly to look for it.

**Common pitfalls.**
- Extracting only what is in an obviously tabular part of a source document and missing information stated
  in prose (as in the "note" sentence above) — extraction prompts should explicitly instruct the model to
  capture *all* relevant information, not only what is already table-shaped.
- Treating a clean, well-formatted extraction table as evidence the source data itself was complete and
  correct — extraction cannot manufacture information the source document never contained.

**AI in this topic.** Document/RAG-category tools (KA 13.4) can extend this pattern across many documents at
once (an entire month's site notes, a batch of subcontractor correspondence); the same verification
discipline applies at whatever scale the extraction runs.

**Cross-references.** KA 6.1.3 (the ledger and accrual-lag mini-case this example is built from); KA 1.3,
KA 1.4 (accrual accounting); 13.3.11 (this extracted data carried forward into a narrative).

### 13.3.11 Prompt pattern: drafting a report narrative

**Definition & purpose.** Narrative-drafting tasks ask an AI tool to turn numeric results into prose
commentary suitable for a management report — precisely the kind of fluent, structured writing GenAI tools
are strong at, and precisely why the source data feeding that fluency must be verified before the prose is
trusted (13.3.9).

**Worked example — poor vs good, continuing the Month-3 dataset.**

*POOR prompt:* "Write a cost commentary for Pipeline Segment 4B using AC $280,000 and EV $330,000."

*Why it is poor — and dangerous.* This prompt supplies the **ledger-only** AC of $280,000 (KA 6.1.3),
carried over without re-checking it against the accrual note captured in 13.3.10. It contains no instruction
against speculating on cause. A fluent, confident output follows: "Pipeline Segment 4B continues to
outperform its cost budget in Month 3, delivering $330,000 of earned value against $280,000 of actual cost —
a cost variance of +$50,000, or a CPI of 1.18. This reflects continued efficient execution on the trenching
work packages." The commentary is well-written, internally consistent, and **materially wrong**: CV should
be +$25,000 (CPI 1.08) once the $25,000 of verified-but-unbilled subcontract work is accrued into AC
(KA 6.2.1), and the "efficient execution" driver was never evidenced — it is a plausible-sounding
invention.

*GOOD prompt:* "Act as a project controls analyst drafting a Month-3 cost commentary for Pipeline Segment
4B for a client steering committee with no EVM background. Use the accrual-adjusted figures only: PV
$270,000; EV $330,000; AC $305,000 (accrual-adjusted per the Month-3 cost extraction). State CV, SV, CPI and
SPI, say whether each is favourable or adverse in plain English, and do not state a cause or driver for
either variance — none has been confirmed for this reporting period. Maximum 150 words."

*Realistic output (described).* "Pipeline Segment 4B's Month-3 position, on an accrual-adjusted basis, is
favourable on both measures. Cost Variance is +$25,000 (CPI 1.08): for every dollar spent to date, $1.08 of
budgeted value has been earned. Schedule Variance is +$60,000 (SPI 1.22): the project has earned
significantly more value than was scheduled by this point. No specific driver for either variance has yet
been confirmed and none is asserted here; this will be reviewed with the site team ahead of the Month-4
report."

*Verification step.* Confirm every figure against KA 6.1/6.2's verified Month-3 dataset; confirm no
unsupported driver has crept back in during any refinement pass (13.3.7); confirm the tone and length match
the brief given.

**Mini-case — what an unverified draft would have cost.** Suppose, under deadline pressure, the analyst had
used the POOR prompt above and pasted its output directly into the Month-3 steering committee pack without
re-checking AC against the site note captured in 13.3.10. The committee would have read a materially rosier
position — CV +$50,000, CPI 1.18 — than the true, accrual-complete position of CV +$25,000, CPI 1.08, and an
invented "efficient execution" driver presented as fact. On the strength of that overstated headroom, a
committee could reasonably decide, for example, that no additional contingency drawdown was needed this
quarter, or approve a discretionary scope addition it would not have approved against the true $25,000
position. When ABC Welding's invoice for the $25,000 of already-completed work lands the following month, AC
jumps with no matching EV movement, and CV appears to deteriorate sharply for no visible reason — an
unexplained-looking swing that then has to be explained after the fact, at real cost to the credibility of
the project controls function. The error was never in the AI's arithmetic (`330,000 − 280,000 = 50,000` is
correct) — it was in an unverified, incomplete input variable that a fluent narrative made look authoritative.
This is the central lesson of the KA: **verification is not optional, and it must reach back to the inputs,
not only check the arithmetic on the inputs it was given.**

**Common pitfalls.**
- Reusing a "known" figure (e.g., AC) from memory or from an earlier draft without re-confirming it is still
  the most current, complete figure at the moment of drafting.
- Allowing an AI-drafted narrative to state a cause or driver that "sounds right" without it having been
  evidenced by the actual reporting-period data.

**AI in this topic.** Narrative drafting from verified figures is one of the strongest, most defensible uses
of GenAI in project controls reporting — it removes drafting time, not verification time. KA 13.5 develops
this pattern into a fuller reporting workflow across the reporting cycle.

**Cross-references.** KA 6.1.3, KA 6.2.1 (the source accrual-lag data); 13.3.9 (the verification checklist
applied above); KA 4.3 (report narrative conventions); KA 13.5 (the fuller reporting workflow).

### 13.3.12 Prompt pattern: explaining a variance to a stakeholder

**Definition & purpose.** A closely related but distinct pattern: explaining what a variance figure *means*
in plain language for a specific, often non-technical, audience — without inventing a cause the professional
has not actually established.

**Worked example — poor vs good.**

*POOR prompt:* "Explain the variance." (no figures, no audience stated.)

*Why it is poor.* With no data supplied, a general-purpose assistant has two options, neither good: give a
generic textbook definition of cost/schedule variance disconnected from Pipeline Segment 4B's actual numbers,
or — if any prior figures remain in the conversation's context (13.3.1) — apply them, but very possibly with
an invented, unevidenced explanation of *why* the variance occurred, because "explain" implicitly invites a
causal story and the model will tend to supply one rather than state that it does not know.

*GOOD prompt:* "Using CV +$25,000 (CPI 1.08) and SV +$60,000 (SPI 1.22) for Pipeline Segment 4B at Month 3,
explain in plain English, for a client representative with no EVM background, what these figures mean about
cost and schedule performance to date. Explain only what the figures themselves show — do not suggest a
cause or driver, since none has been confirmed. If you would need more information to explain the cause,
say so explicitly and state what information you would need."

*Realistic output (described).* A short explanation stating that the project has earned more value than it
has cost (favourable cost position) and has earned more value than was scheduled by this date (favourable
schedule position), followed by a closing line: "These figures show favourable overall performance to date
but do not, on their own, explain *why* — confirming the driver would require checking work-package-level
progress records and the Month-3 site diary."

*Verification step.* Confirm the figures used are the current, verified ones (13.3.9); confirm the model
did not, despite the instruction, smuggle in a driver in its final sentence — a known tendency of fluent
text generation to want to "complete the story"; if it did, remove it before use.

**Common pitfalls.**
- Asking an AI tool to "explain why" a variance occurred when the actual root cause has not yet been
  investigated — this is asking the model to do the professional's diagnostic work for it, which it cannot
  do reliably without the underlying operational evidence (site records, progress data) that only the
  professional (or the project team) holds.
- Using a generic explanation of "what CV means" as a substitute for engaging with the project's actual
  figures — technically correct, practically useless to the reader.

**AI in this topic.** This pattern is a good illustration of a broader honest principle for this KA: the
most useful constraint a professional can add to a prompt is often not what to include, but an explicit
instruction on what *not* to infer.

**Cross-references.** KA 4.2 (variance analysis and root-cause bridges, which supply the *actual* diagnostic
method this pattern deliberately does not substitute for); 13.3.6 (constraints technique); 13.3.9
(verification).

### 13.3.13 Prompt pattern: summarising a contract clause

**Definition & purpose.** Summarising a contract clause into plain English is a common, genuinely useful
GenAI application — and one where the gap between a AI-generated paraphrase and the actual, legally
operative contract wording matters more than in almost any other pattern in this KA.

**Worked example — poor vs good.**

*Source document (an illustrative extract, in Meridian's own contract wording — not a quotation of any
standard form's clause text):*

> "Clause 13 (illustrative, Pipeline Segment 4B contract) — Variations. Where the Contractor encounters a
> physical condition it considers could not reasonably have been foreseen by an experienced contractor at
> the time of tender, the Contractor shall give written notice to the Engineer within 14 days of first
> becoming aware of the condition. No claim for additional time or cost under this clause shall be
> considered if notice is given outside this period. Following a valid notice, the Engineer shall instruct
> a variation, a rejection with reasons, or a request for further particulars, within 21 days."

*POOR prompt:* "Summarise this clause."

*Why it is poor.* No instruction on what to prioritise. A generic summary might accurately restate the
general subject ("this clause deals with unforeseen physical conditions and variations") while compressing
or omitting the single most commercially critical detail: the 14-day notice deadline, and the fact that
missing it forfeits the claim entirely.

*GOOD prompt:* "Summarise the clause below in plain English for a non-lawyer project controls audience.
Structure the answer under four headings: (1) What triggers this clause; (2) What the contractor must do,
and by when; (3) What happens if the deadline is missed; (4) What the Engineer must then do, and by when.
Do not add any interpretation not stated in the clause text itself."

*Realistic output (described).* A four-part summary: (1) an unforeseeable physical condition encountered by
the contractor; (2) written notice to the Engineer within 14 days of first becoming aware; (3) a claim is
barred entirely if notice is given late — no claim considered; (4) the Engineer must respond — instruct a
variation, reject with reasons, or request further detail — within 21 days of a valid notice.

*Verification step.* A qualified commercial/contracts professional (or legal counsel, for a genuinely live
dispute) must check the AI's summary against the actual signed clause wording before it is relied upon for
any real notice, claim or entitlement decision — an AI paraphrase, however accurate it appears, is never
itself the contract, and a live commercial claim should be assessed against the executed contract text, not
against a summary of it (cross-reference KA 7.2).

**Common pitfalls.**
- Circulating an AI-generated clause summary as if it were a substitute for the clause itself in a live
  claim or dispute — a summary can miss a qualifying phrase, a defined term with a specific contractual
  meaning, or a cross-reference to another clause that changes the operative effect.
- Pasting an entire, long, multi-schedule contract and asking for "a summary of the key terms" without
  specifying which terms matter for the task at hand — this tends to produce a broad, shallow summary that
  is not useful for a specific commercial decision.

**AI in this topic.** RAG-grounded, document-aware tools (13.3.8, KA 13.4) are particularly well suited to
this pattern at scale — searching a large contract for the clause relevant to a specific question — but the
verification duty applies identically whether the source clause was pasted directly or retrieved
automatically.

**Cross-references.** 13.3.8 (grounding/RAG); KA 7.1, KA 7.2 (contract types and administration in depth,
including FIDIC/NEC awareness-level treatment); 13.3.9 (verification).

### 13.3.14 Prompt pattern: generating test scenarios

**Definition & purpose.** Project controls professionals increasingly need to validate new tools — a new
automated EVM dashboard, a revised cost-report template, a BI integration — before trusting their output
(cross-reference KA 13.2's data-quality theme and KA 4.4's dashboard design). Generating test scenarios (test
cases) is a genuinely strong GenAI use case for *coverage*: identifying the range of situations a tool should
be tested against. It is a weak, and potentially dangerous, use case for supplying the *correct expected
answer* to each test case.

**Worked example — poor vs good.**

*Scenario.* Meridian's project controls function is validating a new automated dashboard that is meant to
calculate PV, EV, AC, CV, SV, CPI and SPI directly from the ERP and schedule feeds, ahead of switching off
the manual EVM spreadsheet.

*POOR prompt:* "Give me some test cases for checking the new dashboard is calculating correctly."

*Why it is poor.* No coverage is specified (which measures, which edge cases), no output format is
specified, and — critically — nothing prevents the model from also generating the "expected result" for
each scenario, which the professional might then be tempted to trust as the test oracle without
independently recalculating it.

*GOOD prompt:* "Produce test cases, as a markdown table (columns: Scenario ID | Description | Input data |
Expected result | Pass/fail criterion), for validating that the new dashboard correctly calculates PV, EV,
AC, CV, SV, CPI and SPI. Cover at least: (a) a straightforward mid-project case using the verified Pipeline
Segment 4B Month-3 dataset (PV $270,000, EV $330,000, AC $305,000) as a regression test; (b) a case where AC
is zero (project just started, CPI undefined — check the dashboard handles this without an error); (c) a
Level of Effort work package, where EV should always equal PV by definition; (d) a case with an adverse cost
variance. Leave the 'Expected result' column marked 'TBC — to be independently calculated and verified by
the analyst' — do not calculate it yourself."

*Realistic output (described).* A four-row table covering exactly the four scenarios requested, each with a
clearly described input data set and the Expected result column intentionally left as an instruction to the
analyst rather than a computed figure.

*Verification step.* The professional independently calculates the expected result for every scenario (using
the KA 6.1/6.2 formulae directly, not the AI's arithmetic) before running the test, then compares the
dashboard's actual output against that independently derived figure — never against a figure the AI itself
proposed, since an AI-generated "expected answer" is exactly as unverified as any other AI output and using
it as the test oracle would defeat the purpose of the test.

**Common pitfalls.**
- Allowing an AI tool to generate both the test case *and* its own expected answer, then treating a
  dashboard's agreement with that AI-generated answer as proof of correctness — this only proves the
  dashboard agrees with the AI, not that either is right.
- Under-specifying edge-case coverage (zero/near-zero denominators, Level of Effort packages, negative
  variances) and receiving only "happy path" test cases that would not have caught a real calculation bug.

**AI in this topic.** This pattern illustrates a useful general rule for this KA: AI is often strong at
generating *breadth of coverage* (thinking of scenarios a professional might not have listed) and weak, or
actively risky, as a source of the *ground truth* those scenarios are tested against — the two roles should
not be filled by the same unverified output.

**Cross-references.** KA 6.1, KA 6.2 (the formulae used to derive expected results independently); KA 4.4
(dashboard design); KA 13.2 (data-quality validation of new tools).

### 13.3.15 Confidentiality and data-leakage risk

**Definition & purpose.** **Data leakage**, in this context, means confidential or commercially sensitive
project data — contract prices, subcontractor rates, unresolved claim positions, personal data, bid
strategy — being pasted into an AI tool that is not governed for that purpose, with the risk that the data
is retained, logged, or (depending on the tool's terms) used in ways the organisation has not approved.

**The underlying principle.** Many widely available, general-purpose consumer AI tools operate under terms
where inputs may be retained, logged for abuse-monitoring or, in some product configurations, used to
improve the underlying service, unless the specific account, tier or configuration in use disables this —
terms vary by tool, by account type and over time, so the specific position for any tool in use should be
checked against its current terms and the organisation's own approved-tool list, not assumed. The
professional-grade distinction to hold onto is between an **ungoverned, public-tier tool** (no organisational
contract, no confirmed data-handling terms, default consumer settings) and a **governed, enterprise-tier or
internally deployed tool** (covered by an organisational agreement that typically includes data-handling and
retention commitments, and often integrates directly with the organisation's own approved document store —
the RAG pattern of 13.3.8, under governance). Pasting Pipeline Segment 4B's actual contract price, margin
position, or an unresolved claim narrative into an ungoverned public tool to "get a quick draft" is a
data-leakage event regardless of how useful the resulting draft is.

**Worked example — what to do instead.**

*Risky approach:* pasting the full text of Meridian's confidential subcontract with ABC Welding Services,
including its actual rates, into a free, public AI tool to ask for a summary of payment terms.

*Governed approach:* using the organisation's approved, enterprise-tier or internally deployed AI tool
(where the data-handling terms have been confirmed and approved — KA 13.6), or, where no approved tool
covers the task, working with anonymised or illustrative figures only (e.g., "a subcontract with a 30-day
payment term and a 5.0% retention" rather than the actual counterparty name and rate) when using an
ungoverned tool for a purely illustrative drafting task, and never for anything requiring the actual
confidential terms.

**Common pitfalls.**
- Assuming a tool is "safe" because it is well-known or widely used — brand recognition says nothing about
  a specific account's or tier's data-handling terms.
- Anonymising figures inconsistently (removing the counterparty name but leaving a rate specific enough to
  re-identify the contract) — partial anonymisation can still leak commercially sensitive information.
- Treating internal, non-public data as automatically "low sensitivity" because it is not a legal document —
  cost positions, margin figures and claim strategy are commercially sensitive even when informally written.

**AI in this topic.** This is a governance topic as much as a technique topic, and it is developed at
organisational-policy depth — including an AI-use policy, approved-tool lists, and a decision framework for
"when NOT to use AI" — in KA 13.6. The essential, non-negotiable point for this KA: **the sensitivity of the
data, not the convenience of the tool, decides which tool is appropriate.**

**Cross-references.** KA 13.2 (data governance in depth); KA 13.6 (AI-use policy, governance and assurance);
13.3.16 (prompt governance).

### 13.3.16 Prompt governance

**Definition & purpose.** **Prompt governance** is the set of organisational controls over how AI tools are
prompted and used for professional work: approved-tool lists, standard/template prompts for recurring
tasks, review and sign-off requirements, and awareness of prompt-level security risks — most notably
**prompt injection**.

**The underlying principle.** As individual prompting skill (13.3.1–13.3.14) becomes routine across a
project controls function, the organisational risk shifts from "does any one person know how to prompt
well" to "is prompting done consistently, safely and auditably across the whole team." A prompt template
library for recurring tasks (a standard variance-commentary prompt, a standard clause-summary prompt) both
raises the floor on quality across a team and creates a natural checkpoint for embedding the verification
and confidentiality disciplines of 13.3.9 and 13.3.15 directly into how the task is normally done, rather
than relying on every individual remembering them every time.

A usable template need not be elaborate — it is typically a short, fillable skeleton that already embeds the
anatomy from 13.3.2. For example, Meridian's monthly commentary template might read: "Act as a project
controls analyst drafting a Month-[N] cost commentary for [project] for [audience]. Use the following
accrual-adjusted figures only: [PV/EV/AC]. State CV, SV, CPI and SPI and say whether each is favourable or
adverse in plain English. Do not state a cause or driver unless it is supplied below as confirmed. Maximum
[N] words." — with the analyst filling the bracketed fields from that month's verified data. The template
does the prompt-engineering work once; the analyst's job each month is supplying correct inputs and applying
the 13.3.9 checklist to the output, not re-deriving the prompt structure from scratch.

**Prompt injection — an awareness-level note.** Where an AI tool reads content from outside the direct
conversation — a web page, an email, an uploaded document, or (increasingly) content an "agentic" AI feature
retrieves or acts on automatically — that external content can contain hidden instructions crafted to
redirect the AI's behaviour, a risk known as **prompt injection**. For example, a document an AI tool is
asked to summarise could contain text (visible or hidden) instructing the AI to ignore its original task or
to include misleading content in its output. This is a genuine and actively evolving risk, particularly for
AI features that can take actions (sending information, browsing, executing a workflow step) rather than
only generating text, and it is mentioned here at awareness level: a project controls professional should
know the risk exists, should be cautious about AI tools that read and act on untrusted external content
without a review step, and should treat an AI-summarised external document with the same "verify before you
rely on it" discipline (13.3.9) as any other output — precisely because a successful injection would look,
to the end reader, like an entirely ordinary, plausible summary.

**Worked example — a minimal prompt-governance control.**

*Ungoverned practice:* each analyst on the Pipeline Segment 4B team independently writes their own variance-
commentary prompt each month, with no shared template, no record of which tool was used, and no consistent
reminder to use accrual-adjusted figures.

*Governed practice:* the project controls function maintains a short, approved prompt template for the
monthly commentary (built from the GOOD prompt in 13.3.11), specifies which tool tier is approved for use
with project cost data (13.3.15), and requires the analyst to note, alongside the issued report, which tool
was used and that the 13.3.9 verification checklist was applied — a lightweight audit trail, not a heavy
bureaucratic process, that makes the AI-assisted step of the report as reviewable after the fact as any
other step in the reporting cycle.

**Common pitfalls.**
- Treating prompt governance as a one-off policy document rather than a living template library that is
  actually used and updated as tasks and tools change.
- No awareness-level briefing on prompt injection at all, leaving staff unprepared for a risk that is
  specific to AI tools (rather than a generic phishing/security risk they may already be trained on) even
  though the two share a similar "don't blindly trust untrusted content" logic.
- Over-engineering governance for low-risk, low-sensitivity drafting tasks to the point that staff route
  around the approved tools entirely — proportionate governance matched to task sensitivity (13.3.15) is more
  durable than a single, maximally strict rule applied to everything.

**AI in this topic.** Prompt governance is where individual technique (this KA) meets organisational
assurance (KA 13.6) — a well-run project controls function treats "how we prompt" with the same seriousness
as "how we code our costs" or "how we word a variation notice," because, done carelessly, either can
mislead a decision-maker while looking entirely routine.

**Cross-references.** KA 13.6 (the full AI-use policy, governance and assurance treatment); KA 13.7 (building
this into a maturing AI-augmented capability); 13.3.15 (confidentiality, the other half of governance
covered in this KA).

### Key terms

- **Prompt** — the natural-language instruction given to an AI tool; comprises a system prompt (standing
  instructions) and a user prompt (the specific request).
- **Context window** — the bounded amount of text (measured in tokens) an AI model can process at once,
  including the conversation history and any pasted or retrieved material.
- **Temperature** — a generation setting controlling how deterministic (low) or varied (high) the model's
  output is.
- **Prompt engineering** — the practice of structuring a prompt (role, task, context, examples, constraints/
  format) to reliably produce a usable response.
- **Few-shot / zero-shot prompting** — supplying (few-shot) or not supplying (zero-shot) worked examples of
  the desired input-output pattern.
- **Chain-of-thought / step-by-step prompting** — instructing the model to show intermediate working before
  a final answer, improving accuracy and auditability on multi-step tasks.
- **Iterative refinement** — treating an AI's first output as a draft to be corrected and improved through
  follow-up prompts within the same conversation.
- **Grounding** — constraining an AI's answer to specific supplied or retrieved source material rather than
  its general training.
- **Retrieval-Augmented Generation (RAG)** — an architecture that retrieves relevant passages from an
  approved document store and supplies them to the model alongside the query, to ground its answer.
- **Hallucination** — a fluent, confident AI output that is factually wrong or unsupported by any real
  source (KA 13.1).
- **Verification** — the professional's structured check of AI output (traceability, unsupported claims,
  internal consistency, governance fit) before it is used or relied upon.
- **Automation bias / over-trust** — the tendency to treat a fluent or well-formatted AI output as more
  likely correct because of how it is presented, rather than what it actually says.
- **Data leakage** — confidential or sensitive data being exposed through an ungoverned AI tool's input,
  logging or retention.
- **Prompt injection** — hidden instructions embedded in external content an AI tool reads, crafted to
  redirect its behaviour.
- **Prompt governance** — organisational controls (approved tools, template prompts, review, audit trail)
  over how AI is prompted and used for professional work.

### Sample MCQs

**MCQ 13.3.1 [topic 13.3.1, level: recall]**
What does a large language model's "context window" determine?
A. How creative or varied its output is
B. **The maximum amount of text (conversation, pasted material, instructions) it can process at once** ✔
C. Which specific documents it has permanently memorised
D. The organisation's approved list of AI tools
*Rationale:* The context window bounds what the model can "see" in a given interaction. A describes
temperature, not the context window; C incorrectly implies permanent memory, which general-purpose chat
models do not have across sessions unless a specific persistent feature is used; D describes prompt
governance (13.3.16), an unrelated organisational control.

**MCQ 13.3.2 [topic 13.3.2, level: application]**
A project controls analyst prompts an AI tool with: "Tell me about the cost situation on Pipeline Segment
4B." Which single addition would most improve this prompt?
A. Asking the same question in a different tone
B. Repeating the request twice for emphasis
C. **Supplying the actual PV/EV/AC figures, the required output format, and the target audience** ✔
D. Asking the model to use a larger context window
*Rationale:* The prompt fails because it supplies no data, no format and no audience — exactly what C adds.
A and B do not address the missing information; D is not a setting the user controls or that would fix a
missing-data problem.

**MCQ 13.3.3 [topic 13.3.8, level: analysis]**
Why does retrieval-augmented generation (RAG) reduce, but not eliminate, the risk of hallucination?
A. Because RAG tools never make factual errors once a document store is connected
B. **Because grounding an answer in retrieved source material reduces reliance on the model's general
   training, but the retriever can still fetch the wrong passage, the source material can itself be wrong
   or outdated, and the model can still misread or blend retrieved content** ✔
C. Because RAG replaces the language model with a simple keyword search, which cannot hallucinate
D. Because RAG only works for numerical data, not text
*Rationale:* B states the honest, multi-part limitation taught in 13.3.8. A overstates RAG's reliability; C
misdescribes the architecture (RAG still uses an LLM to generate the final answer); D is factually wrong —
RAG is commonly used for text-heavy tasks such as contract clause retrieval.

**MCQ 13.3.4 [topic 13.3.11, level: analysis]**
In the Pipeline Segment 4B mini-case, an AI-drafted cost commentary reported CV as +$50,000 (CPI 1.18)
instead of the true, accrual-adjusted +$25,000 (CPI 1.08). What was the actual source of this error?
A. The AI incorrectly calculated CV = EV − AC using the figures it was given
B. **The AI was given an incomplete Actual Cost figure ($280,000, ledger-only) that excluded $25,000 of
   verified but unbilled work, so a correct calculation on an incorrect input produced a wrong result** ✔
C. The model's context window was too small to hold the figures
D. The prompt's temperature setting was too high
*Rationale:* `330,000 − 280,000 = 50,000` is arithmetically correct — the arithmetic was not the problem;
the input (an unaccrued AC) was. B correctly locates the error at the input/verification stage, which is
the central teaching point of the mini-case. A, C and D misattribute the error to mechanisms not actually
at fault here.

**MCQ 13.3.5 [topic 13.3.15, level: application]**
A commercial manager wants quick AI help drafting a summary of a confidential subcontract, including its
actual agreed rates. What is the most appropriate action?
A. Paste the full confidential subcontract, including rates, into any free public AI tool, since the task
   is only a summary
B. **Use an approved, governed enterprise-tier or internally deployed AI tool with confirmed data-handling
   terms, or work from anonymised/illustrative figures if no governed tool is available for the task** ✔
C. Avoid using AI for this task and instead delegate the summary to a junior team member without informing
   them of the confidentiality requirement
D. Paste the subcontract into a public AI tool but delete the chat afterwards
*Rationale:* B reflects the governed-tool/anonymisation principle in 13.3.15. A and D both expose
confidential data to an ungoverned tool regardless of whether the chat is later deleted, since retention and
logging terms are not controlled by the user deleting a visible chat; C avoids the confidentiality risk but
introduces a different failure (an uninformed team member handling confidential data without guidance).

**MCQ 13.3.6 [topic 13.3.9, level: recall]**
Which of the following best reflects the professional's duty when reviewing AI-generated output, per the
principle "AI proposes; the professional disposes"?
A. If the output is well-written and confidently stated, it can generally be trusted without further checks
B. **The professional must trace figures to source, check for unsupported claims, confirm internal
   consistency, and confirm governance fit — regardless of how fluent or confident the output appears** ✔
C. Verification is only required for outputs used in external, client-facing documents
D. A second AI tool checking the first AI tool's output fully discharges the verification duty
*Rationale:* B states the four-part checklist from 13.3.9. A describes automation bias, a named pitfall; C
wrongly limits verification to external documents when internal decisions are equally consequential; D
wrongly treats AI-on-AI checking as sufficient, when 13.3.9 explicitly notes this does not discharge the
professional's own duty.

### Self-check questions (answers in Appendix C)

1. List the five components of an effective prompt's anatomy (Fig 13.3.1) and explain, using the Pipeline
   Segment 4B extraction example (13.3.10), why omitting the "constraints and format" component in a
   data-extraction task increases the risk of a materially incomplete result.
2. Using the Month-3 accrual-lag mini-case (13.3.11), explain in two or three sentences how an unverified
   AI-drafted narrative could have misled Meridian's steering committee, and state the specific verification
   step that would have caught the error before the report was issued.
3. Explain why retrieval-augmented generation (RAG) reduces, but does not eliminate, the risk of
   hallucination, and give one reason a RAG-grounded answer can still be wrong.
4. A subcontract manager wants to use a free, public AI tool to help draft correspondence that would need to
   quote Meridian's actual subcontract rates with ABC Welding Services. What should they do instead, and
   why?

**Answers**

1. The five components are role/persona, task, context, examples, and constraints/format. In the 13.3.10
   extraction example, the GOOD prompt's constraint explicitly instructed the model to capture information
   described in prose (the unbilled-work note), not only information already in table form, and to keep
   accrued and invoiced amounts in separate, clearly labelled rows. Without that constraint, a plausible
   extraction would total only the four invoiced line items and either drop or bury the $25,000 accrual
   note, producing a table that looks complete and correctly formatted but silently omits $25,000 of
   relevant cost information — exactly the failure mode later shown, unchecked, in the 13.3.11 mini-case.
2. The AI-drafted narrative used the ledger-only Actual Cost figure of $280,000 rather than the
   accrual-adjusted $305,000, reporting CV as +$50,000 (CPI 1.18) instead of the true +$25,000 (CPI 1.08),
   and it made this overstated favourable position sound authoritative and well-supported. A steering
   committee reading the unverified figure could reasonably make a less prudent decision (e.g., against
   drawing contingency, or approving discretionary scope) than it would have made against the true position.
   The verification step that would have caught this is the traceability check (13.3.9): tracing the AC
   figure back to its source and confirming it is complete and accrual-adjusted (per KA 6.1.3's accrual-lag
   note) before the narrative built on it is issued.
3. RAG grounds an AI's answer in retrieved source material instead of relying only on the model's general
   training, which is a genuine improvement because the model has real, relevant text to draw from. It does
   not eliminate hallucination because the retriever can fetch the wrong or an irrelevant passage, the
   retrieved source material can itself be outdated or incorrect, and the model can still misread, misquote
   or blend the retrieved passage with its own general training when generating the final answer.
4. They should use an approved, governed enterprise-tier or internally deployed AI tool with confirmed
   data-handling terms for any task involving Meridian's actual confidential subcontract rates, rather than
   a free, public, ungoverned tool — because such tools may retain, log or otherwise process pasted input
   under terms the organisation has not reviewed or approved, and pasting the actual counterparty name and
   rates into such a tool is a data-leakage event regardless of how useful the resulting draft is. If no
   governed tool is available for the task, they should work from anonymised or illustrative figures only,
   never the actual confidential terms.
