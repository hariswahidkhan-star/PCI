# Domain 13 — AI for Project Controls & PM: Concepts, Tools & Practice

## KA 13.2 — Data — the fuel

KA 13.1 defined what AI, machine learning and generative AI actually are — models trained on data to
recognise patterns or generate outputs, as distinct from deterministic rules. This Knowledge Area addresses
the single factor that determines, more than model choice or prompt design, whether any of that machinery
produces something a project controls professional can rely on: the **data**. An AI model — whether a
simple regression, a machine-learning classifier or a large language model — has no independent way to know
whether the numbers, dates, codes and documents it is trained or working on are complete, accurate or
current; it can only learn and reproduce the patterns actually present in what it is given. This is why the
data landscape, data quality, data governance and the disciplines of preparing data for AI use are treated
here as a Knowledge Area in their own right, not as a footnote to KA 13.1's model concepts or KA 13.3's
prompting techniques. This KA covers the data types a controls professional encounters (13.2.1), the
project-controls data landscape itself — the specific systems and artefacts that generate that data
(13.2.2) — the six dimensions used to assess whether a dataset is fit for purpose, with a fully worked
data-quality assessment (13.2.3), master and reference data and the single source of truth (13.2.4), data
governance, ownership and stewardship together with data lineage (13.2.5), the ingest-clean-transform-store
pipeline with a worked data-cleaning mini-case (13.2.6), the basics of feature engineering for controls data
(13.2.7), data labelling for supervised learning (13.2.8), bias in data and its consequences (13.2.9),
privacy, confidentiality and security at awareness level (13.2.10), and closes with the single idea that
threads through every topic in this KA: **garbage in, garbage out** (13.2.11). The chapter continues
**Meridian Rail Contracting LLC's Pipeline Segment 4B** project (BAC $600,000 / SAR 2,250,000 at an
illustrative SAR 3.75 = USD 1), the cost coding structure, cost control cycle and EVM figures already
established in KA 1.5, KA 5.2 and KA 6.1, so that every worked example here reconciles to numbers the reader
has already seen rather than introducing an unrelated dataset. Later Knowledge Areas build on this one
without repeating it: KA 13.3 assumes the reader understands why ungoverned data must never be pasted into
an ungoverned tool; KA 13.4 and KA 13.5 assume the reader can judge whether a given dataset is fit to feed a
named category of tool or workflow; and KA 13.6 covers the **governance of AI outputs** (auditability,
hallucination, sign-off) as a distinct, complementary discipline to this KA's **governance of AI inputs**.

### 13.2.1 Data types: structured, semi-structured and unstructured; time series, transactional and document data

**Definition & purpose.** Data feeding an AI system in project controls falls into three **structural**
categories. **Structured data** sits in a fixed schema of rows and columns, each field of a known type and
meaning (a cost ledger table, an EVM summary table, a risk register's scored fields) — it is directly
machine-readable without interpretation. **Semi-structured data** has some organising structure (tags,
fields, a defined file format) but not a rigid, uniform schema — a scheduling tool's exported network file,
a Bill of Quantities with structured item/quantity/rate columns alongside free-text descriptions, or a risk
register's structured probability/impact fields alongside a free-text risk description. **Unstructured
data** has no predefined schema at all — free-text correspondence, meeting minutes, scanned invoices,
photographs, contract PDFs — and requires natural-language processing, optical character recognition or
computer vision before a model can use it. Independently of structure, data can also be classified by
**temporal/functional pattern**: **time series** data (a sequence of measurements over time — PV/EV/AC by
period, KA 6.1), **transactional** data (discrete, individually dated events — a single ledger posting, a
purchase order line, KA 5.2), and **document** data (a self-contained artefact — a contract, a variation
order, a set of drawings).

**The underlying principle.** These classifications matter because they determine what kind of AI technique
is even applicable. A time series of PV/EV/AC can feed a statistical forecasting model directly; a folder of
scanned subcontract PDFs cannot be forecast from until a document-intelligence step first extracts
structured fields (dates, values, clauses) from the unstructured source (cross-reference KA 13.4's
document/RAG tool category). Treating semi-structured data as if it were fully structured — assuming every
BoQ description field follows an identical pattern, for instance — is a common source of downstream
extraction errors; treating structured data as if it needed heavyweight natural-language processing wastes
effort a simple database query would perform more reliably and more cheaply.

- Assuming "our data is in the ERP, so it's all structured" — an ERP commonly stores unstructured attachments

- Treating semi-structured data (a BoQ, a risk register) as fully structured and assuming every free-text

**AI in this topic.** Different AI technique families map onto these categories: statistical/ML forecasting

large language models are what make unstructured text usable; computer vision and optical character
recognition extract structured fields from images and scans (cross-reference KA 13.1's supervised/
unsupervised distinction, KA 13.4's tool categories). No single tool spans all three well, and a vendor
claiming one model "handles all your project data" should be treated with the same scepticism applied to any
unqualified capability claim — the honest picture is a toolkit matched to data type, not one tool for
everything.

### 13.2.2 The project-controls data landscape

**Definition & purpose.** The **project-controls data landscape** is the set of systems, registers and
document stores that together hold everything a controls function needs: the **scheduling tool** (activity
network, logic, calendars, progress — KA 10.1–10.4), the **cost ledger/ERP** (postings, purchase orders,
goods receipts — KA 5.2), the **EVM system or spreadsheet** (PV/EV/AC and derived indices — KA 6.1–6.4), the
**risk register** (KA 12.1–12.3), the **commercial/contract system** (the BoQ, variations, payment
certificates — KA 7.1–7.5), and **correspondence** (RFIs, emails, meeting minutes, site instructions). In
most organisations these are separate systems, built by different vendors for different purposes, rarely
sharing a common data model.

**The underlying principle — one event, many systems.** A single real business event on a project routinely
touches several of these systems at once, each recording a different facet of the same event in its own
structure. This is not a design flaw to be engineered away entirely (each system is specialised for good
reason) but it is exactly why data integration — and, later, AI initiatives that need a joined-up view — is
hard: no single system holds "the truth" about an event; the truth is distributed, and assembling it requires
either a disciplined manual trace or a genuinely integrated data platform.

**Example 13.2.2 — tracing one Meridian event across the data landscape.**

*Scenario.* In Month 4, the client's site engineer instructs an additional 20 m of tie-in welding on the
Al-Noor package (KA 5.2.2's mini-case), formalised as a $1,000 amendment to PO SC-PO-4B-014.

*Required.* Identify every system this single event touches, and what each one records.

*Working.*

| Touchpoint | System / store | Data type (13.2.1) | What it records | Value |
|---|---|---|---|---|
| 1. Site instruction | Correspondence / email or RFI log | Unstructured document | The engineer's written instruction | n/a (descriptive) |
| 2. Change record | Commercial change-control register | Semi-structured | The variation logged and priced | +$1,000 |
| 3. PO amendment | ERP / Procure-to-Pay system | Structured, transactional | SC-PO-4B-014 revised commitment | $50,000 → $51,000 |
| 4. Cost coding | ERP cost ledger | Structured, transactional | Coded to `4B.30.02.530` (KA 1.5.2) | commitment only at this point; no cash cost yet |
| 5. Forecast update | Cost-control / forecasting workbook | Structured, time series | Bottom-up ETC/EAC (KA 5.2.6, KA 5.2.9) | EAC $50,000 → $51,000 |

*Answer.* One instruction, worth $1,000, generates entries in **five** distinct systems, spanning all three
structural categories from 13.2.1.

*Interpretation.* An AI tool asked "what changed on Pipeline Segment 4B in Month 4 and why?" cannot answer
correctly from any single one of these five systems alone — the ERP shows a revised commitment with no
narrative reason; the correspondence log shows a reason with no priced value; only a joined-up view, or a
professional who has traced the event manually, connects "an approved 20 m variation" to "$1,000 on the PO"
to "the EAC moved by exactly that amount" (echoing the clean reconciliation already proved in KA 5.2.9). This
is the practical argument for the master-data and governance disciplines developed in 13.2.4–13.2.5.

**Common pitfalls.**
- Building an AI/analytics initiative on only the most convenient system (usually the ERP) and treating its
  view as complete, missing the narrative and justification held in correspondence and change registers.
- Assuming systems update in the same timeframe — a variation may be instructed on site days before it is
  formally logged in the commercial change register, creating a temporary but real inconsistency across the
  landscape (cross-reference 13.2.3's timeliness dimension).
- Underestimating correspondence and document volume (13.2.1's 437-of-651 finding) when scoping a data
  project, because it is the least visible part of the landscape in day-to-day reporting.

**AI in this topic.** Integration platforms, RPA connectors and, increasingly, retrieval-augmented generation
(RAG) tools (KA 13.4) can pull data from several of these systems into one queryable layer, and a well-
configured assistant can answer a question like the one posed above by retrieving from correspondence, the
ERP and the forecast workbook together. This is a genuine and growing capability, but it depends entirely on
each source system being connected, current and correctly coded (13.2.4–13.2.6) — an integration layer over
five poorly governed systems produces one poorly governed, larger dataset, not a solved data-quality problem.

### 13.2.3 Data quality: the six dimensions, and a worked assessment

**Definition & purpose.** **Data quality** is the degree to which a dataset is fit for its intended use,
assessed across six widely used, complementary dimensions: **accuracy** (does the recorded value match
reality), **completeness** (are all required fields and records present), **consistency** (do related
records agree with each other, across fields and across systems), **timeliness** (is the data current enough
for its intended use), **validity** (does each value conform to its defined format, type and allowed range)
and **uniqueness** (is each real-world event or entity represented exactly once, with no duplication). No
single dimension is sufficient alone — a dataset can be perfectly consistent and still consistently wrong,
or perfectly timely and still incomplete.

**The underlying principle.** Data quality is not a binary "clean or dirty" judgement; it is a *measured
profile* across these six dimensions, because different AI use cases are sensitive to different dimensions.
A same-day anomaly-detection alert depends heavily on timeliness; a historical parametric estimating model
depends more on accuracy and consistency over a long time series and can tolerate some lag. Measuring the
profile, rather than asserting "the data is good," is what lets a professional judge fitness for a *specific*
AI use case rather than in the abstract.

**Formula(e).** For a dataset of *n* records, each dimension is scored as a percentage:

`Completeness (%) = records with all mandatory fields populated / n`
`Validity (%) = records conforming to defined format/domain rules / n`
`Consistency (%) = records free of a cross-field or cross-system contradiction / n`
`Timeliness (%) = records captured within the agreed data-currency policy / n`
`Uniqueness (%) = records with no duplicate representing the same real-world event / n`
`Accuracy (%) = records confirmed correct on independent verification / (sample size, where a full audit of n is impractical)`

`Composite Data Quality Score (%) = mean of the six dimension scores` (unweighted, unless a specific AI use
case justifies weighting by dimension — developed in the interpretation below).

**Example 13.2.3 — a data-quality assessment of Pipeline Segment 4B's Month-3 cost-ledger extract.**

*Scenario.* Ahead of connecting an AI-assisted cost-anomaly-detection tool (KA 13.5), Meridian's data steward
audits the 200-line Month-3 cost ledger extract for Pipeline Segment 4B (13.2.1) against the six dimensions.

*Required.* Compute each dimension score and the composite Data Quality Score, and assess fitness for use.

*Working.*

| Dimension | Check performed | Pass count | Base | Score |
|---|---|---|---|---|
| Completeness | All mandatory fields (cost code, amount, date, supplier, description) populated | 189 | 200 | 189/200 = **94.5%** |
| Validity | Cost code exists in the coding manual (KA 1.5.5); amount and date within allowed ranges | 194 | 200 | 194/200 = **97.0%** |
| Accuracy | Independent audit sample traced to source GRN/invoice and agreed exactly | 48 | 50 (sample) | 48/50 = **96.0%** |
| Consistency | Supplier name and cost code combination consistent across ERP and commitment register | 188 | 200 | 188/200 = **94.0%** |
| Timeliness | Posted within the 5-working-day accrual policy of verified receipt (KA 5.2.3) | 180 | 200 | 180/200 = **90.0%** |
| Uniqueness | No duplicate posting (same PO, amount, date) | 194 | 200 | 194/200 = **97.0%** |

`Composite score = (94.5 + 97.0 + 96.0 + 94.0 + 90.0 + 97.0) / 6 = 568.5 / 6 = 94.75% ≈ 94.8%`

*Answer.* The Month-3 extract scores a **composite Data Quality Score of 94.8%**, with **Timeliness (90.0%)**
the weakest of the six dimensions and **Validity/Uniqueness (97.0% each)** the strongest.

*Interpretation.* Against an illustrative organisational threshold of 95.0% for "AI-ready" data, this extract
falls narrowly short — driven specifically by the 20 late-posted records, not by any single catastrophic
failure. This matters for *how* the shortfall is treated: it is a targeted, fixable gap (chase the 20 late
postings, tighten the cut-off routine per KA 5.2.8), not a reason to distrust the whole dataset. A weighted
variant makes the point sharper still: if this particular AI use case (real-time anomaly detection) weights
Timeliness at 30%, Accuracy at 25%, Completeness at 20%, Validity at 15%, and Consistency and Uniqueness at
5% each (reflecting that a same-day alert depends far more on freshness and correctness than on tidy
formatting), the weighted score is `0.30×90.0 + 0.25×96.0 + 0.20×94.5 + 0.15×97.0 + 0.05×94.0 + 0.05×97.0 =
27.00 + 24.00 + 18.90 + 14.55 + 4.70 + 4.85 = 94.0%` — lower than the unweighted figure, because the
weighting deliberately penalises the dimension (timeliness) that matters most for *this* use case. The two
scores tell a professional two different, both legitimate, things: 94.8% describes the dataset in general;
94.0%, weighted for this specific AI application, is the more decision-relevant figure.

**Mini-case — why the accuracy dimension needed a sample, not a full audit.** The accuracy check above used a
50-record sample rather than checking all 200 lines, because accuracy verification requires tracing each
line back to an independent source document (a GRN or invoice) — a manual step that does not scale to full-
population audit within a routine monthly cycle. This is a genuine, common constraint: accuracy is usually
the most expensive dimension to measure and therefore the one most often estimated from a sample rather than
measured exhaustively, unlike completeness, validity, consistency and uniqueness, which can typically be
checked programmatically across the full dataset. A reported accuracy score should always disclose whether it
is a full-population or sample-based figure, because a 96.0% sample result carries sampling uncertainty a
96.0% full-population result does not.

**Common pitfalls.**
- Reporting a single, blended "data quality" verdict instead of the six-dimension profile, hiding exactly
  which dimension is driving a problem and how to fix it.
- Auditing accuracy from an unrepresentative sample (e.g. only large-value transactions) and generalising the
  result to the whole population.
- Treating a high composite score as permission to skip governance altogether — a 94.8% score still means
  roughly 1 in 20 checks failed somewhere in the dataset, which is a materially imperfect input for a
  fully automated (no-human-review) process.

**AI in this topic.** Data-profiling and data-quality tools (commonly built into modern data-catalogue and
data-governance platforms, and increasingly offered as add-ons within BI and ERP suites) can compute these
six dimension scores automatically and continuously across large datasets, at a speed no manual audit could
match — a genuine and valuable capability. What such tools cannot do is decide the *right* threshold or
weighting for a specific AI use case (the weighted variant above is a professional judgement, not something
the tool can infer on its own), nor can they detect an accuracy problem without an independent source to
verify against — a purely internal consistency check can be perfectly self-consistent and still uniformly
wrong (developed further in 13.2.11).

### 13.2.4 Master data, reference data and the single source of truth

**Definition & purpose.** **Master data** describes the relatively stable, core entities a project's
transactions repeatedly refer to — suppliers/vendors, employees, the chart of accounts and cost-coding
structure (KA 1.5), the WBS, the equipment register. **Reference data** is a controlled, usually short list
of permitted values a field may take — currency codes, units of measure, discipline codes. **Transactional
data** — a cost posting, a timesheet entry — is meaningful only in reference to master and reference data
("this $25,000 belongs to *which* supplier, coded to *which* discipline"). A **single source of truth
(SSOT)** is the one designated, authoritative system of record for a given master-data domain, from which
every other system and every AI tool is expected to draw or reconcile to that value, rather than each
maintaining its own, potentially diverging, copy.

**The underlying principle.** Master data changes rarely but is referenced constantly, which makes an error
in it disproportionately damaging: one wrong supplier record, referenced by hundreds of transactions, corrupts
every report and every AI model output built on those transactions, unlike a single mis-keyed transactional
value, whose damage is normally confined to that one record. Designating an SSOT does not mean every other
system stops holding a copy of the data — most systems must, for performance and offline-use reasons — it
means every copy is understood to be *derived from*, and reconciled to, the one authoritative source, so
divergence is a detectable, correctable exception rather than a silent, permanent split.

**Example 13.2.4 — a vendor master-data split and its consequence.**

*Scenario.* Meridian's ERP holds the authoritative vendor master record "Al-Noor Site Services LLC"
(vendor code V-1042). Independently, the site's local subcontractor-tracking spreadsheet created a second,
unlinked entry, "Al Noor Site Services" (no hyphen, no "LLC"), for the same real-world supplier. By the
Month-3 data date, Al-Noor's true accrual-adjusted actual cost is $25,000 (KA 6.1.3, KA 5.2.3), but because
some cost postings were tagged against the ERP's master record and others against the spreadsheet's
unlinked name, an AI-assisted spend-analytics tool reading both sources reports $18,000 against "Al-Noor
Site Services LLC" and $7,000 against "Al Noor Site Services" as if they were two different, smaller
suppliers.

*Required.* Reconcile the split, and state the risk this creates if left uncorrected.

*Working.* `18,000 (ERP-tagged) + 7,000 (spreadsheet-tagged) = 25,000` — the true, single-supplier total
already established elsewhere in this book.

*Answer.* The two "vendors" are one vendor; the true concentration of subcontract spend with Al-Noor is
**$25,000**, not two separate exposures of $18,000 and $7,000.

*Interpretation.* This is not simply a cosmetic naming inconsistency. A supply-chain concentration check
(relevant to KA 12.1's risk appetite discussion — how exposed is the project to a single subcontractor
failing) would understate Al-Noor's true share of spend under either fragmented figure, potentially missing a
genuine over-concentration risk that only becomes visible once the two records are correctly linked to one
master vendor. An AI classification tool trained on the fragmented history (KA 1.5.6) would also learn two
separate, weaker patterns instead of one strong one, degrading its own coding-suggestion accuracy for future
Al-Noor transactions.

**Common pitfalls.**
- Allowing any system outside the designated SSOT to create a *new* master-data record rather than requesting
  a link to (or a new entry in) the authoritative source — exactly how the spreadsheet's duplicate arose.
- Assuming a clean transactional reconciliation (KA 1.5.5) would catch this — it would not, because both
  fragments' totals still sum correctly to the true $25,000; only a master-data-level check (matching supplier
  identities, not just transaction totals) surfaces the split.
- Treating "reference data" (a fixed code list) as if it were master data that individual users may extend
  informally — an ungoverned reference-code list drifts in exactly the same way an ungoverned vendor list
  does.

### 13.2.5 Data governance, ownership, stewardship and lineage

**Definition & purpose.** **Data governance** is the framework of policies, roles and decision rights that
determines who may create, change, approve and retire data, and to what standard. **Data ownership** is
accountability at the business-domain level — a named role answerable for a data domain's quality and
fitness for use (the Cost Controller owns cost-ledger data; the Scheduler owns schedule data; the Commercial
Manager owns contract and BoQ data). **Data stewardship** is the operational role that maintains quality day
to day within an owner's domain — correcting flagged errors, resolving master-data matches (13.2.4),
maintaining the coding manual (KA 1.5.5). **Data lineage** is the traceable record of where a given data
point originated, what it passed through, and where it ended up — the practical tool that makes governance
auditable rather than aspirational.

**The underlying principle.** Governance exists because data quality, once lost, is expensive to recover and
because accountability that is not explicitly assigned tends to default to nobody — a well-run data domain
has one accountable owner, even where several people touch the data operationally, exactly mirroring the
control-account principle already established in KA 1.5.4 (one work package, one accountable manager) applied
here to data rather than cost.

**Example 13.2.5 — a RACI for Pipeline Segment 4B's core data domains.**

*Scenario/Required.* Meridian assigns accountability and responsibility across its five core data domains
for Pipeline Segment 4B.

*Working.*

| Data domain | Accountable (owner) | Responsible (steward) | Consulted | Informed |
|---|---|---|---|---|
| Cost ledger | Cost Controller | Data Steward (Finance) | Project Controls Manager | Project Manager |
| Schedule | Scheduler/Planner | Scheduler/Planner | Project Controls Manager | Project Manager |

| BoQ / contract | Commercial Manager | Contracts Administrator | Project Controls Manager | Project Manager |

*Interpretation.* This table is the practical answer to "who fixes it when a data-quality check (13.2.3)
flags a problem?" — the flag routes to the domain's steward, who has both the access and the mandate to

raises a flag with nobody assigned to act on it (cross-reference KA 5.2.8's sequencing pitfall) produces the
appearance of control without its substance.

- Leaving informal channels (a phone call, an unlogged verbal instruction) as the true origin of a data point

- Assigning "Accountable" to a committee or a system rather than a named individual, which functions the same

- Confusing stewardship (an operational, hands-on role) with ownership (an accountable, decision-rights role)

  accountable for.

ungoverned channel in the first place — an AI lineage tool is only as complete as the systems it is actually
connected to.

### 13.2.6 Data pipelines: ingest, clean, transform, store

**Definition & purpose.** A **data pipeline** is the repeatable, automated (or semi-automated) sequence that
takes raw data from its source systems to a state ready for analysis or AI use, typically described in four
stages: **ingest** (extract data from a source system, on a schedule or trigger), **clean** (correct or flag
errors — duplicates, missing values, out-of-range entries), **transform** (reshape, aggregate or enrich the
data into the structure a model or report actually needs), and **store** (load the result into a target —
a data warehouse, a data mart, or a curated table a model reads directly).

**The underlying principle.** Cleaning and transformation must happen *before* data reaches an analytical or
AI use, not be left to whichever downstream report or model happens to encounter the problem first — the same
logic already established for accruals and cost coding (KA 5.2, KA 1.5): a defect fixed once, at the pipeline
stage, stays fixed for every consumer; a defect left in raw source data is rediscovered, and potentially
mis-handled differently, by every report or model that touches it independently.

**Example 13.2.6 — a data-cleaning mini-case: preparing Pipeline Segment 4B's timesheet extract for an AI
labour-cost anomaly detector.**

*Scenario.* Meridian ingests a raw, 50-row weekly timesheet extract to feed an AI-assisted labour-cost
anomaly-detection tool.

*Required.* Walk the extract through the clean stage and state the record count leaving each step.

*Working.*

| Step | Issue found | Action | Records affected | Running usable count |
|---|---|---|---|---|
| Start (ingest) | — | Raw extract loaded | — | 50 |
| De-duplication | 4 exact duplicate rows (same employee, date, hours, cost code) | Removed | 4 | 46 |
| Missing-field check | 3 rows missing employee ID | 2 resolved via lookup against the payroll master (13.2.4's SSOT); 1 unresolved, routed to the data steward and quarantined | 1 removed (quarantined) | 45 |
| Format standardisation | 2 rows with ambiguous date format (DD/MM vs MM/DD) | Standardised to ISO 8601 using the pay-period reference | 0 removed | 45 |
| Range/outlier check | 1 row logging 40 hours for a single calendar day (implausible; max plausible is ≈16) | Traced to source: a decimal-point mis-key of "4.0" entered as "40" — corrected to 4.0 hours on confirmation | 0 removed (corrected) | 45 |

*Answer.* **45 of the original 50 records (90.0%)** proceed clean to the transform stage; **1 record**
remains quarantined pending the data steward's follow-up; **4 duplicate** and **0 further** records were
permanently removed.

*Interpretation.* Had the 40-hour outlier not been caught, that single row alone would have overstated one
day's labour cost by `(40 − 4) hours × an illustrative $45/hour rate = 36 × 45 = $1,620` — a modest amount on
its own, but illustrative of how a single unclean record, left uncaught, silently distorts every downstream
total and every model trained on it (developed at project scale in 13.2.11). The transform stage that follows
aggregates the 45 clean rows into weekly cost totals by cost code, and the store stage loads that curated
table into the anomaly-detection tool's input — the model never sees the raw, uncleaned extract at all.

**Common pitfalls.**
- Silently discarding problem records instead of quarantining and routing them for steward resolution — the
  discarded records disappear from every subsequent total without a trace, understating whatever they would
  have contributed.
- Building the clean and transform logic separately inside each downstream report or model, rather than once

- Automating the pipeline fully with no periodic human sampling of what it is silently correcting or
  discarding, so a systemic source-system problem (e.g. a broken timesheet form causing repeated date-format
  errors) goes unnoticed at its root cause.

**AI in this topic.** Modern data-pipeline and data-preparation tools increasingly embed AI-assisted cleaning
— suggesting a likely duplicate match, proposing a standardised date format, flagging an implausible value
using a learned range rather than a fixed rule — which speeds up exactly the steps worked through above at a
volume manual review cannot match (cross-reference KA 13.5). The professional's review step does not
disappear: an AI-suggested correction (the 40-hour mis-key, in this example) still needs the human
confirmation shown in the working above before it is applied, because the tool's "plausible correction" is a
statistical inference, not verified knowledge of what the employee actually worked.

### 13.2.7 Feature engineering basics for controls data

**Definition & purpose.** A **feature** is a derived, model-ready variable computed from one or more raw data
fields, chosen because it is expected to carry predictive or explanatory signal for the task at hand — as
distinct from a raw field simply copied through unchanged. **Feature engineering** is the discipline of
constructing these variables: aggregating over a period, computing ratios, building rolling/lagged windows,
encoding categorical fields numerically, and scaling values onto comparable ranges.

**The underlying principle.** Raw, cleaned data (13.2.6) is necessary but rarely sufficient for a model to
perform well — many of the most informative signals in project controls are *ratios and trends*, not raw
totals, and a model given only raw totals must, in effect, rediscover those ratios for itself, usually less
reliably than a professional stating them directly. Feature engineering is where domain knowledge already
built up elsewhere in this book (EVM's CPI and SPI, KA 6.2; the cost control cycle's commitment and accrual
measures, KA 5.2) is explicitly handed to the model as an input, rather than left for the model to infer.

**Example 13.2.7 — a small feature table for Pipeline Segment 4B, Month 3.**

*Scenario.* Meridian's data science lead prepares a feature set intended to feed a hypothetical AI early-
warning classifier for cost-overrun risk, built entirely from figures already established and governed
elsewhere in this book.

*Required.* Derive each feature from its underlying, already-quality-checked source figures, with units.

*Working.*

| Feature | Derivation | Source figures | Value |
|---|---|---|---|
| CPI (ratio) | `EV / AC` | EV $330,000, AC $305,000 (KA 6.1.3, accrual-adjusted) | 330,000 / 305,000 = **1.082** |
| SPI (ratio) | `EV / PV` | EV $330,000, PV $270,000 (KA 6.1.2, 6.1.4) | 330,000 / 270,000 = **1.222** |
| Open-commitment ratio (%) | `Open commitment / BAC` | Open commitment $27,500 (KA 5.2.2), BAC $600,000 | 27,500 / 600,000 = **4.6%** |
| Accrual share of AC (%) | `Accrual / AC` | Accrual $25,000 (KA 5.2.3), AC $305,000 | 25,000 / 305,000 = **8.2%** |
| Weeks since last approved variation | Calendar difference | Most recent approved variation: Month 4 (current period) | **0 weeks** |

*Answer.* A five-feature vector — `[1.082, 1.222, 4.6%, 8.2%, 0]` — derived entirely from figures the reader
has already seen proved elsewhere in this book, none newly invented for this table.

*Interpretation.* Notice what this table deliberately does *not* do: it does not feed the model raw PV, EV,
AC and BAC values directly and hope it discovers CPI and SPI on its own — it hands the model the ratios a
controls professional already knows are meaningful (cross-reference KA 6.2's CV/SV/CPI/SPI treatment, not
repeated here), plus two further engineered ratios (open-commitment exposure, accrual share) that make the
project's *forward* and *timing* risk visible in a way a single data-date snapshot alone would not. Feature
engineering, done well, is domain expertise expressed as arithmetic a model can consume — it is not a purely
technical, data-science-only step separable from professional judgement.

**Common pitfalls.**
- Feeding a model many redundant features derived from the same few underlying numbers (e.g. both CPI and its
  reciprocal, or both AC and Accrual-share-of-AC when Accrual is already present separately) without checking
  for this redundancy, which can distort some model types' weighting of genuinely independent signals.
- Engineering a feature from data that has not passed the quality checks in 13.2.3 — a ratio computed from an
  incomplete or stale AC figure inherits and can amplify that defect (developed fully in 13.2.11).
- Building features that would not actually be available at the point a live model needs to make a
  prediction (for example, a feature using a period's final, fully reconciled AC when the model must predict
  *before* that reconciliation is complete) — a subtle but common cause of a model that performs well in
  testing and poorly in live use.

**AI in this topic.** Some modern machine-learning platforms offer automated feature-generation ("auto-ML"),
which can propose candidate ratios, lags and aggregations from raw tables faster than manual engineering,
and can be a useful starting point (cross-reference KA 13.4, KA 13.5). It has no access to the professional
context that makes CPI, SPI or an open-commitment ratio meaningful specifically *because* of how EVM and cost
control work (KA 6.1–6.2, KA 5.2) — an automated tool can propose thousands of statistically plausible
combinations, the great majority meaningless or misleading in a project controls sense, and the professional's
domain knowledge remains the filter that selects the handful worth using.

**Cross-references.** KA 6.1–6.2 (PV/EV/AC and the CPI/SPI definitions reused, not repeated, here); KA 5.2.2,
5.2.3 (open commitment and accrual, the source of the two engineered ratios); 13.2.3 (data quality as a
precondition for trustworthy features); 13.2.11 (how a quality defect in a source figure propagates through
an engineered feature into a model output).

### 13.2.8 Data labelling

**Definition & purpose.** **Data labelling** is the process of assigning a category or value to raw data to
create the "answer key" a supervised machine-learning model learns from — for example, tagging correspondence
items as "cost-impact-relevant" or not, or tagging historical cost postings as "anomalous" or "normal." A
model trained on labelled data can only be as good as the labels themselves; **inter-annotator agreement** is
the standard check on whether human labellers are applying a labelling scheme consistently enough for the
resulting labels to be trustworthy.

**The underlying principle.** Labelling looks like a simple, mechanical clerical task and is, in fact, a
professional judgement task disguised as one — a labeller deciding whether an email is "cost-impact-relevant"
is making exactly the kind of assessment a controls professional makes routinely, and two reasonable
labellers can disagree. Measuring agreement is how an organisation distinguishes a labelling scheme that is
consistently and clearly defined from one that is too ambiguous to produce a trustworthy training set,
*before* a model is trained on the result rather than after.

**Formula.** `Percentage agreement = agreements / total items labelled`. Because percentage agreement does
not account for agreement that would occur by chance alone, **Cohen's kappa** is the standard correction:

`κ = (Po − Pe) / (1 − Pe)`

where `Po` is the observed percentage agreement and `Pe` is the percentage agreement expected by chance,
computed from each labeller's marginal label distribution.

**Example 13.2.8 — inter-annotator agreement for a correspondence-labelling exercise.**

*Scenario.* Two reviewers independently label 40 correspondence items from Pipeline Segment 4B as
"cost-impact" or "not cost-impact," ahead of training a classifier to triage new correspondence automatically.

*Required.* The confusion matrix, percentage agreement, and Cohen's kappa.

*Working.*

| | Reviewer B: cost-impact | Reviewer B: not cost-impact | Reviewer A total |
|---|---|---|---|
| **Reviewer A: cost-impact** | 12 | 3 | 15 |
| **Reviewer A: not cost-impact** | 3 | 22 | 25 |
| **Reviewer B total** | 15 | 25 | **40** |

`Po (observed agreement) = (12 + 22) / 40 = 34 / 40 = 0.850`
`Pe (chance agreement) = (15/40 × 15/40) + (25/40 × 25/40) = 0.375² + 0.625² = 0.140625 + 0.390625 = 0.53125`
`κ = (0.850 − 0.53125) / (1 − 0.53125) = 0.31875 / 0.46875 = 0.680`

*Answer.* **Percentage agreement = 85.0%**; **Cohen's kappa = 0.68**.

*Interpretation.* Raw percentage agreement (85.0%) looks reassuring on its own, but because both reviewers
independently classified the *same* items as "cost-impact" about 37.5% of the time, a meaningful share of that
raw agreement would be expected even from partially random labelling; correcting for this, kappa of 0.68 is
commonly read on standard inter-rater reliability scales as "substantial" but not "near-perfect" agreement —
good enough to proceed to training a first model, but with the 6 disagreement cases (3 + 3, in the
off-diagonal cells) adjudicated by a third, senior reviewer and the labelling guidance clarified before a
larger labelling exercise is commissioned.

**Common pitfalls.**
- Using only percentage agreement and not kappa — percentage agreement alone overstates true reliability
  whenever one label is much more common than the other, exactly the pattern in this example.
- Sending confidential correspondence or cost data to a public, uncontrolled crowdsourced labelling service —
  a genuine confidentiality risk (cross-reference 13.2.10, KA 13.3) that rules out an entire category of
  labelling approach for most project controls data.
- Treating a single labeller's output as ground truth with no independent check at all, which cannot detect
  that labeller's own systematic misunderstanding of the labelling guidance.

**AI in this topic.** A partially trained model can itself accelerate labelling through **active learning** —
proposing a label for each new item with a confidence score, so a human reviewer confirms high-confidence
proposals quickly and spends more time on the genuinely uncertain, low-confidence cases — a real and widely
used efficiency technique once an initial labelled set (like the 40-item exercise above) exists. It does not
remove the need for the initial, carefully agreement-checked labelled set in the first place, nor does it
detect that the labelling *scheme itself* (not just individual labels) is ambiguous — that diagnosis, like the
kappa calculation above, remains a human quality check.

(labeller inconsistency as a source of label bias); 13.2.10 (confidentiality constraints on labelling
approach); KA 13.1 (supervised learning, the technique this labelled set ultimately trains).

### 13.2.9 Bias in data and its consequences

**Definition & purpose.** **Bias in data** is a systematic (not random) distortion in a dataset that causes a
model trained or reasoning on it to produce systematically skewed outputs for some category of case. In
project controls, the most common sources are **historical bias** (past project data reflects past
measurement or estimating practices that were themselves systematically distorted), **sampling bias**
(the available data over- or under-represents certain project types, sizes or conditions relative to the
population a model will actually be applied to), and **label bias** (developed in 13.2.8 — inconsistent or
subjective labelling baked into a training set).

**The underlying principle.** Bias is dangerous specifically *because* it is systematic, not because it is
large — a purely random data error tends to average out across a large enough dataset; a systematic bias does
not average out, it reproduces itself at scale, in every prediction the model makes for the affected category.
This is why bias must be actively investigated, by segmenting a dataset and checking for a pattern, rather
than assumed absent because a dataset's overall aggregate looks reasonable — precisely the same logic already
applied to control-account aggregates in KA 6.1.5's "an aggregate can mask offsetting performance" caution,
now applied to a training dataset instead of a performance report.

**Example 13.2.9 — historical bias from inconsistent EV measurement methods.**

*Scenario.* Meridian's historical project archive holds final-cost outcomes for 40 completed control
accounts, intended to train a parametric AI cost-estimating tool. A data audit segments the 40 accounts by
which EV measurement approach (KA 6.1.4) each used: 25 accounts used front-loaded weighted-milestone methods
(over-crediting early progress, KA 6.1.4's pitfall), while 15 used disciplined, work-nature-appropriate
methods.

*Required.* The average final-cost overrun for each subgroup, the blended organisational average, and the
implication for a model trained only on the blended figure.

*Working.*
`Front-loaded subgroup (25 accounts): average overrun = 14.0%`
`Disciplined subgroup (15 accounts): average overrun = 3.0%`
`Blended organisational average = (25 × 14.0 + 15 × 3.0) / 40 = (350 + 45) / 40 = 395 / 40 = 9.875% ≈ 9.9%`

*Answer.* The organisation's naive, blended historical average overrun is **9.9%** — but neither subgroup
actually experienced anything close to 9.9%: the front-loaded group averaged **14.0%** and the disciplined
group averaged **3.0%**.

*Interpretation.* A parametric estimating model trained on the blended 9.9% figure, without the measurement-
method segmentation, would apply a roughly uniform ~9.9% risk uplift to every new control account regardless
of which EV measurement regime it will actually use — materially overstating risk for a disciplined account
(whose true historical signal is closer to 3%) and, more dangerously, materially understating risk for one
still using front-loaded milestones (whose true historical signal is closer to 14%). The bias here did not
originate in the AI tool at all; it originated upstream, in inconsistent measurement-method discipline already
flagged as a pitfall in KA 6.1.4 — the model has simply learned, faithfully, whatever pattern (including the
distortion) was actually present in its training data.

**Common pitfalls.**
- Assuming a large historical dataset is automatically representative — volume does not correct for a
  systematic skew present throughout the whole population, only random noise.
- Checking for bias only by inspecting the model's outputs after training, rather than segmenting the training
  data itself beforehand — by the time biased outputs are noticed downstream, the cost of retraining and
  re-validating is far higher than catching the segmentation issue upfront.
- Treating "the model is accurate on average, across the whole test set" as sufficient validation — an
  aggregate accuracy figure can hide exactly the kind of subgroup skew shown above (cross-reference KA 6.1.5's
  aggregation caution).

**AI in this topic — honest limits.** Bias-detection techniques (subgroup performance analysis, fairness
metrics originally developed for other domains but increasingly applied to operational ML) can help surface a
pattern like the one above once a plausible segmenting variable (here, measurement method) is proposed for
testing. No tool can discover an *unconsidered* segmenting variable on its own — the audit in this example
only happened because a professional, who already understood KA 6.1.4's front-loading pitfall, thought to
check for it. AI-assisted bias detection is a powerful confirmatory and monitoring tool; identifying which
biases are plausible in the first place still depends on domain expertise, not the algorithm.

(the aggregation-masking principle this bias mirrors); 13.2.8 (label bias, a related but distinct source);
KA 13.6 (bias and fairness as an AI-governance topic, addressing bias in a deployed model's *outputs and
decisions* rather than, as here, bias present in the *training data itself*).

### 13.2.10 Privacy, confidentiality and security: awareness-level principles

**Definition & purpose.** Project controls data routinely includes **personal data** (employee names, hours
and, in some jurisdictions, national ID or payroll details in timesheet and HR-linked records) alongside
**commercially confidential** data (subcontractor pricing, unit rates, claims positions) that requires
protection for reasons distinct from, but related to, data protection law. Several jurisdictions maintain
comprehensive personal-data-protection regimes — the EU's General Data Protection Regulation (GDPR) is the
best known internationally, and comparable regimes exist elsewhere, including Saudi Arabia's Personal Data
Protection Law (PDPL) and similar regional frameworks. This topic covers these at **awareness level only** —
the common *principles* such regimes tend to share, described generically — not as legal advice, and not
with specific clause or article citations, which is a matter for qualified legal counsel in the relevant
jurisdiction (flagged for SME/legal verification at the end of this KA).

**The underlying principle — commonly shared data-protection principles.** Regimes of this kind typically
share a recognisable set of principles, which a controls professional should recognise even without legal
training: **lawfulness, fairness and transparency** (personal data is collected and used for a stated,
legitimate purpose, with those affected reasonably informed); **purpose limitation** (data collected for one
purpose — say, payroll processing — is not silently repurposed for an unrelated one, such as an individual
performance-scoring AI tool, without a fresh lawful basis); **data minimisation** (only the data genuinely
needed for the task is collected or shared — an AI cost-anomaly tool typically needs transaction amounts and
codes, not necessarily individual employee names); **accuracy** (personal data is kept correct and current,
echoing this KA's own accuracy dimension at 13.2.3); **storage limitation** (data is retained only as long as
needed, then deleted or anonymised); **integrity and confidentiality** (data is kept secure — access controls,
encryption, need-to-know); and **accountability** (the organisation can demonstrate compliance, commonly
through a documented risk assessment for higher-risk processing, sometimes called a Data Protection Impact
Assessment or equivalent).

**Example 13.2.10 — a data-sensitivity classification for Pipeline Segment 4B's data landscape.**

*Scenario/Required.* Meridian's data governance lead classifies the project's core data domains into
sensitivity tiers ahead of deciding which may be used with which category of AI tool (cross-reference KA
13.3, KA 13.4).

*Working.*

| Tier | Example Meridian data | Typical AI-tool constraint |
|---|---|---|
| Internal | Schedule, cost ledger totals, EVM reports, BoQ rates | May be used with an enterprise-governed AI tool under contract; not a public, free consumer tool |
| Confidential | Subcontractor unit rates, commercial terms, claims positions | Enterprise-governed tools only, with access limited to those with a commercial need to know |
| Restricted / personal data | Employee timesheets (names, hours, ID numbers), subcontractor personnel lists, named HSE incident records | Minimise and, where feasible, pseudonymise before any AI processing; never a public, ungoverned tool |
| Public | (rare on a private commercial project — e.g. a published tender notice) | No material constraint |

*Answer.* The majority of Pipeline Segment 4B's data sits in the Internal and Confidential tiers, with a
smaller but materially sensitive Restricted tier (personal data) that carries the strictest AI-tool
constraint.

*Interpretation.* This classification is the practical link between this KA's data-governance material and
KA 13.3's guardrail — "never paste confidential data into an ungoverned tool" only becomes actionable once a
professional can actually identify *which* data is confidential or restricted, which is exactly what this
tiering exercise does. Before the timesheet mini-case in 13.2.6 is ever handed to an AI-assisted cleaning
tool, for example, employee names and ID numbers should be pseudonymised (replaced with a stable but
non-identifying code) if the tool is not confirmed to be an enterprise-governed instance under an appropriate
data-processing agreement — a minimisation step consistent with the principles above.

**Common pitfalls.**
- Pasting a raw dataset containing personal or confidential fields into a free, public generative-AI tool "just
  to save time," with no confirmation of that tool's data-retention or training-use terms — a direct breach of
  minimisation, purpose limitation and, depending on the tool's terms, confidentiality altogether.
- Assuming pseudonymisation (replacing a name with a code) is equivalent to full anonymisation — a
  pseudonymised record can often still be re-identified by cross-referencing other fields (a unique job title,
  a specific date and site combination), so pseudonymisation reduces but does not eliminate risk.
- Treating data-protection compliance as an IT-department-only concern rather than something every data owner
  (13.2.5) is accountable for within their own domain.

**AI in this topic — honest limits.** AI tools increasingly offer built-in data-loss-prevention features
(automatically detecting and redacting apparent personal data before submission) and enterprise deployment
modes with contractual guarantees that customer data is not used to train the underlying model — genuine and
increasingly standard protections worth confirming before adoption. No AI tool can determine on its own
whether a specific use case has a valid lawful basis under a given jurisdiction's regime, nor can a generic
tool feature substitute for an organisation's own data-protection policy and legal advice; this remains, by
design, a professional and legal judgement, and the specific regulatory landscape evolves, so any given claim
about a tool's compliance posture should be verified against current vendor documentation and legal guidance
rather than assumed.

**Cross-references.** KA 13.3 (the "never paste confidential data into an ungoverned tool" guardrail this
topic underpins); 13.2.5 (data ownership, the accountable role for compliance within a domain); 13.2.4
(master data, which often includes personal data — the employee master); KA 13.6 (AI governance, ethics and
regulatory considerations at the level of a deployed AI system, complementing this topic's data-level
treatment).

### 13.2.11 Garbage in, garbage out: the central risk

**Definition & purpose.** "Garbage in, garbage out" (GIGO) is the principle that no AI technique — however
sophisticated the model — can produce a trustworthy output from untrustworthy input data; a model does not
detect, correct or compensate for a defect in its input data unless it has been explicitly designed and
trained to do so, and even then only within the limits of what it has been shown. This closing topic does not
introduce a new technique; it draws together 13.2.1–13.2.10 to make explicit, with one final worked example,
exactly how a data-quality defect already identified in this chapter (13.2.3's 90.0% timeliness score, traced
to the accrual-lag pitfall of KA 6.1.3) propagates into a materially wrong AI-assisted forecast — and why the
size of that propagation depends on *which* downstream calculation the data feeds.

**The underlying principle — propagation, not just presence.** A data defect does not merely sit passively
inside a dataset; it propagates through whatever calculation consumes the data, and different calculations
propagate the same defect by different amounts. An **additive** calculation (one that simply adds a term)
propagates an input error roughly one-for-one. A **multiplicative or ratio-based** calculation can amplify
the same input error, because the error affects both the numerator's relationship to other terms and the
overall scale of the result. Understanding this is what separates "the data has an error, so distrust
everything downstream equally" from the more precise, more useful question: "given this specific defect, in
this specific figure, feeding this specific formula, how large is the resulting distortion?"

**Example 13.2.11 — how a $25,000 completeness gap distorts two different EAC methods.**

*Scenario.* Returning to the accrual-lag pitfall already established in KA 6.1.3: at Month 3, Pipeline
Segment 4B's cost ledger shows an unadjusted Actual Cost of $280,000; a genuine $25,000 of verified but
unbilled subcontractor work is missing from that figure (a **completeness** defect, in this KA's own
13.2.3 terms) until it is properly accrued, giving the correct, accrual-adjusted AC of $305,000. BAC is
$600,000 and EV is $330,000 throughout (KA 6.1.4–6.1.6).

*Required.* Using the two EAC formulae already defined in KA 6.3 (restated here, not re-derived — cross-
reference KA 6.3 for the full family and its assumptions), compute the EAC under the "dirty" (incomplete) and
"clean" (accrual-adjusted) AC figures, and compare the resulting distortion.

*Working.*

**Method 1 — additive (`EAC = AC + (BAC − EV)`, future work at budget):**

`Dirty:  EAC = 280,000 + (600,000 − 330,000) = 280,000 + 270,000 = 550,000`
`Clean:  EAC = 305,000 + (600,000 − 330,000) = 305,000 + 270,000 = 575,000`
`Distortion = 575,000 − 550,000 = 25,000` — exactly the size of the original completeness defect.

**Method 2 — multiplicative (`EAC = BAC / CPI = BAC × AC / EV`, past efficiency continues):**

`Dirty:  EAC = 600,000 × 280,000 / 330,000 = 168,000,000,000 / 330,000 = 509,091` (rounded)
`Clean:  EAC = 600,000 × 305,000 / 330,000 = 183,000,000,000 / 330,000 = 554,545` (rounded)
`Distortion = 554,545 − 509,091 = 45,455` (rounded) — **1.82 times larger** than the underlying $25,000 defect.

*Answer.* The identical $25,000 completeness defect distorts the additive EAC by exactly **$25,000**, but
distorts the multiplicative (CPI-based) EAC by approximately **$45,455** — an amplification factor of
`BAC / EV = 600,000 / 330,000 = 1.818`, because `EAC = BAC × AC / EV` means every dollar of AC error is
multiplied through by that same ratio (`∂EAC/∂AC = BAC/EV`).

*Interpretation.* This is a precise, mathematically grounded illustration of GIGO, not a vague warning: the
*same* upstream data defect, caught in 13.2.3's audit and explained by 13.2.6's cleaning discipline, produces
a materially different downstream consequence — **$25,000 versus roughly $45,455, at an illustrative SAR
3.75 = USD 1 that is SAR 93,750 versus SAR 170,456** — purely because of which formula the incomplete figure
happened to feed. An AI-assisted forecasting tool that automatically selects or blends EAC methods (KA 13.5)
without first confirming the completeness of its AC input does not "average out" this risk; it can silently
choose the very method that amplifies a hidden defect the most. This is the single most important, and most
honest, statement this KA can make: **the professional's job, before any AI forecast is trusted, is to verify
the data that fed it — not merely to sanity-check whether the output looks plausible.** A plausible-looking
number, on this evidence, can still be wrong by tens of thousands of dollars for reasons entirely invisible in
the output itself.

**Common pitfalls.**
- Sanity-checking only the AI output ("does $554,545 look reasonable?") without ever checking the input data
  quality that produced it — a plausible-looking number is not evidence of a correct one, as this example
  demonstrates numerically.
- Assuming a data defect's downstream impact is proportional to its own size, rather than checking how the
  specific formula or model amplifies or dampens it — as shown here, the same $25,000 defect is not a "$25,000
  problem" once it reaches a ratio-based calculation.
- Treating GIGO as an argument against using AI at all, rather than as the argument for the data-quality
  discipline this entire KA has built — the fix is upstream data governance (13.2.3–13.2.6), not avoidance of
  AI-assisted forecasting.

**AI in this topic — the honest close of this KA.** Every genuine capability described across 13.2.1–13.2.10 —
faster classification, faster reconciliation, faster labelling, faster lineage tracking, faster bias detection
— accelerates work *on* data; none of it replaces the professional discipline of first establishing whether
that data is fit for the specific use intended. This is not a hedge or a disclaimer added for form; it is the
central, load-bearing claim of this Knowledge Area, demonstrated numerically above rather than merely
asserted. **AI proposes; the professional verifies, decides and remains accountable** — and disposing responsibly starts with knowing, in
quantified terms, what the data underneath the proposal is actually worth.

### Key terms

- **Structured / semi-structured / unstructured data** — data in a fixed schema; data with partial
  organisation (tags, mixed fields); data with no predefined schema (free text, images, scans).
- **Time series / transactional / document data** — a sequence of measurements over time; discrete, dated
  events; a self-contained artefact.
- **Data quality dimensions** — accuracy, completeness, consistency, timeliness, validity and uniqueness; the
  six measures used to assess fitness for use.
- **Composite Data Quality Score** — the (optionally weighted) average of the six dimension scores for a
  dataset.
- **Master data** — relatively stable core entities (suppliers, employees, cost codes) repeatedly referenced
  by transactions.
- **Reference data** — a controlled list of permitted values for a field (currency codes, units of measure).
- **Single source of truth (SSOT)** — the one designated, authoritative system of record for a master-data
  domain.
- **Data governance / ownership / stewardship** — the policy framework; the accountable business role; the
  operational role maintaining quality day to day.
- **Data lineage** — the traceable record of a data point's origin, path and destination.
- **Data pipeline (ingest → clean → transform → store)** — the repeatable sequence taking raw data to a
  model-ready state.
- **Feature / feature engineering** — a derived, model-ready variable; the discipline of constructing such
  variables from raw data.
- **Data labelling** — assigning categories or values to raw data to create supervised-learning training
  examples.
- **Inter-annotator agreement / Cohen's kappa** — the check on whether independent labellers apply a scheme
  consistently, corrected for chance agreement.
- **Bias in data (historical, sampling, label)** — a systematic, non-random distortion in a dataset that
  skews a model's outputs for some category of case.
- **Personal data / sensitivity tiering** — data identifying an individual; the practice of classifying data
  by confidentiality/sensitivity to determine handling constraints.
- **Data minimisation, purpose limitation, storage limitation** — commonly shared data-protection principles
  limiting what personal data is used, for what, and for how long.
- **Pseudonymisation** — replacing an identifying field with a non-identifying code; reduces but does not
  eliminate re-identification risk.
- **Garbage in, garbage out (GIGO)** — the principle that no AI technique can produce a trustworthy output
  from untrustworthy input data, and that the same defect can be amplified differently by different
  downstream calculations.

### Sample MCQs

**MCQ 13.2.1 [topic 13.2.1, level: recall]**
A scanned, signed subcontract PDF is best classified as which type of data, by structural category?
A. Structured
B. Semi-structured
C. **Unstructured** ✔
D. Reference data
*Rationale:* A scanned document has no predefined schema and requires document-intelligence extraction before
use — unstructured. Structured data sits in fixed rows/columns; semi-structured has partial organisation
(tags/fields); reference data is a controlled value list, a different classification entirely.

**MCQ 13.2.3 [topic 13.2.3, level: application — numerical]**
A 100-record dataset scores: Completeness 96%, Validity 98%, Accuracy 94% (sample-based), Consistency 92%,
Timeliness 88%, Uniqueness 99%. What is the unweighted composite Data Quality Score?
A. 92.8%
B. **94.5%** ✔
C. 96.0%
D. 99.0%
*Rationale:* `(96+98+94+92+88+99)/6 = 567/6 = 94.5%`. A undercounts the sum; C and D each mistake a single
dimension's score for the composite.

**MCQ 13.2.4 [topic 13.2.4, level: application]**
Two systems hold different names for what is, on investigation, the same subcontractor, causing its spend to
appear split into two smaller totals. Which discipline most directly prevents this recurring?
A. A monthly reconciliation between the coded cost ledger and the general ledger
B. **A designated single source of truth for the vendor master-data domain, with other systems linking to it rather than creating independent records** ✔
C. A higher data-quality threshold for the timeliness dimension
D. Increasing the sample size used in the accuracy check
*Rationale:* This is a master-data identity problem (13.2.4), not a totals reconciliation (A, which would
still balance across the split), a timeliness issue (C), or a sampling issue (D).

**MCQ 13.2.6 [topic 13.2.6, level: analysis]**
In the ingest → clean → transform → store pipeline, at which stage should duplicate records and implausible
outlier values normally be identified and resolved?
A. Ingest
B. **Clean** ✔
C. Transform
D. Store
*Rationale:* Clean is the stage dedicated to correcting or flagging defects (duplicates, missing values,
outliers) before the data is reshaped (Transform) or loaded to its target (Store); Ingest only extracts the
raw data.

**MCQ 13.2.8 [topic 13.2.8, level: application — numerical]**
Two labellers agree on 34 of 40 items; each labeller applied "cost-impact" to 15 of the 40 items. What is
Cohen's kappa?
A. 0.53
B. 0.85
C. **0.68** ✔
D. 1.00
*Rationale:* `Po = 34/40 = 0.850`; `Pe = (15/40)² + (25/40)² = 0.140625 + 0.390625 = 0.53125`;
`κ = (0.850 − 0.53125)/(1 − 0.53125) = 0.680`. A is Pe, not kappa; B is Po (uncorrected agreement), not
kappa; D would require perfect agreement.

**MCQ 13.2.11 [topic 13.2.11, level: analysis]**
A $25,000 completeness defect in Actual Cost is fed into two EAC formulae: an additive method
(`EAC = AC + (BAC − EV)`) and a multiplicative method (`EAC = BAC × AC / EV`), where BAC = $600,000 and
EV = $330,000. Which statement is correct?
A. Both methods are distorted by exactly $25,000, since the underlying data error is the same size
B. **The additive method is distorted by exactly $25,000; the multiplicative method is distorted by
   approximately $45,455, an amplification factor of BAC/EV** ✔
C. The multiplicative method is immune to the defect because CPI is a ratio
D. The additive method amplifies the defect more than the multiplicative method
*Rationale:* The additive formula propagates the AC error one-for-one; the multiplicative formula scales it
by `∂EAC/∂AC = BAC/EV = 1.818`, giving `25,000 × 1.818 ≈ 45,455` (Example 13.2.11). A ignores the different
propagation behaviour; C and D reverse or misstate the actual relationship.

### Self-check questions (answers in Appendix C)

1. Using the six-dimension results in Example 13.2.3 (Completeness 94.5%, Validity 97.0%, Accuracy 96.0%,
   Consistency 94.0%, Timeliness 90.0%, Uniqueness 97.0%), explain in your own words why reporting only the
   94.8% composite score, without the underlying six-dimension profile, would leave a data steward unable to
   act on the result.
2. A master-data vendor record is split into two differently-named entries in two systems, but a monthly
   reconciliation between the coded cost ledger and the general ledger (KA 1.5.5) shows no break. Explain why
   the reconciliation misses this problem, and what kind of check would catch it instead.
3. Explain, using the amplification factor `BAC/EV` from Example 13.2.11, why the same-sized data defect can
   produce a larger dollar distortion in a ratio-based EAC calculation than in an additive one — and why this
   means "the output looks plausible" is not sufficient evidence that an AI-assisted forecast is trustworthy.
4. A project has abundant structured cost-ledger data but very little of its correspondence has ever been
   catalogued or labelled. What kind of AI initiative would this data landscape most readily support today,
   and what would need to happen first before an initiative depending heavily on correspondence became
   viable?

**Answers**

1. The 94.8% composite blends six different measures into one number; it cannot tell a steward *which*
   dimension is weak or what to fix. The actual profile shows Timeliness (90.0%) is materially weaker than
   the other five — a steward reading only "94.8%, generally good" would not know to investigate the 20
   late-posted records specifically, and might not prioritise fixing the cost cut-off routine that is the
   likely root cause.
2. The reconciliation in KA 1.5.5 only compares two grand totals; because the vendor's total spend is still
   fully present in the ledger overall (just split across two differently-named master records rather than
   omitted or duplicated), both totals still agree and no break appears. Catching this requires a master-data
   identity check — comparing supplier records for a likely match (13.2.4) — not a transactional totals
   reconciliation.
3. `EAC = BAC × AC / EV` means the EAC is directly proportional to AC, scaled by the constant `BAC/EV`; any
   error in AC is therefore multiplied through by that same factor when it reaches EAC, whereas an additive
   formula (`EAC = AC + (BAC − EV)`) simply adds the AC error unchanged. Because the amplified, ratio-based
   EAC still produces a single plausible-looking dollar figure, checking only whether that figure "looks
   reasonable" cannot reveal that it is built on a defective input — only tracing back to the input data's
   quality (as in 13.2.3) can.
4. Abundant, quality-checked structured cost-ledger data would most readily support a structured-data AI use
   case — for example, cost-anomaly detection or a parametric estimating/forecasting model (KA 13.5) — because
   the data is already machine-readable and, subject to a quality audit (13.2.3), largely usable as-is. An
   initiative depending heavily on correspondence (for example, automatically flagging cost-impact-relevant
   emails) would first need that unstructured data catalogued, and a labelled training set built and
   agreement-checked (13.2.8), before a supervised classifier could be trained on it at all.
