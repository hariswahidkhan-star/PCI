# Domain 9 — Agile, Scrum & Adaptive Delivery for Project Controls

## KA 9.1 — Agile foundations

Domain 8 closed with KA 8.6, which placed a single development-approach spectrum — predictive, iterative,
incremental, adaptive — across Meridian Rail Contracting LLC's rail-signalling programme, and showed, in
outline, that measurement and forecasting logic must change to match whichever point on that spectrum a
piece of work actually sits at. This KA opens Domain 9 by grounding the adaptive end of that spectrum
properly: not as "a faster way to run a predictive project," but as a distinct discipline resting on its own
theory (empirical process control), its own founding statement of values and principles (the Agile Manifesto,
2001), and its own mindset, which a framework such as Scrum (KA 9.2) then operationalises into concrete
roles, events and artefacts. Getting this foundation right matters to a project-controls professional
specifically, because every measurement and forecasting choice made in the rest of this domain — velocity and
burnup (KA 9.3), Kanban flow metrics (KA 9.4), AgileEVM (KA 9.5) and hybrid governance (KA 9.6) — follows
from the reasoning set out here, not from the reasoning set out in Domain 6. Continuity runs on the same two
Meridian-adjacent illustrations KA 8.6 introduced: **Pipeline Segment 4B** (BAC $600,000 / SAR 2,250,000 at
an illustrative **SAR 3.75 = USD 1**) for the predictive/defined-process reference point, and the **Field
Progress & Punch-list App** — a three-person in-house team, funded at a fixed **$15,000 (SAR 56,250) per
two-week sprint**, against a **200-point backlog** — for the adaptive reference point. This KA does not
repeat KA 8.6.1's iterative-versus-incremental mechanics or KA 8.6.4's inverted-iron-triangle measurement
table in full; it cross-references both and builds the theory and founding text that KA 8.6 assumed.

### 9.1.1 Why adaptive delivery: defined versus empirical process control, and the cost of change

**Definition & purpose.** Two theories of process control explain why some work is best managed predictively
and other work is best managed adaptively. **Defined (theoretical) process control** applies where a process
is fully understood: given the same inputs and the same well-specified steps, the process reliably produces
the same output, so the work can be planned in detail in advance and simply checked for conformance as it
runs. **Empirical process control** applies where the process is not, and cannot yet be, fully specified in
advance; the only reliable way to converge on the right result is to produce a small piece of work, examine
it against reality, and adjust the next piece of work in light of what was learned. This distinction is the
theoretical foundation the Scrum Guide (Ken Schwaber and Jeff Sutherland) states its framework rests on; KA
9.2 develops Scrum's own mechanics from it in full. Introduced here, at foundation level, it explains *why*
adaptive delivery exists at all, one layer beneath KA 8.6.2's practical six-factor suitability filter and KA
8.6.2's cost-of-change curve (Fig 8.6.2, not reproduced here).

**The underlying principle.** Which model genuinely applies to a piece of work is a property of that work's
uncertainty, not a matter of organisational preference. Physically engineered work governed by mature,
codified methods — a welding procedure, a regulator-approved pipe route — behaves as a defined process: the
method is known, so following it predictably produces the specified result, and predictive planning with
classical Earned Value Management (Domain 6) is the correct measurement logic (cross-reference KA 6.1, KA
8.6.2). Work whose right answer genuinely cannot be known until real users interact with a real, working
version of it — a screen layout, a data-entry workflow — behaves as an empirical process: no fixed method
exists yet to follow, so the only dependable route to the right result is to build a small increment, inspect
it, and adapt. This is the *cause* that KA 8.6.2's cost-of-change curve describes the *effect* of: a late
change is expensive under a defined process because the process assumed the answer was already known; a late
change is comparatively cheap under an empirical process because the process was designed, from the outset,
to expect that the answer would only emerge over time.

**No new formula.** The defined/empirical distinction is a qualitative judgement about the nature of the
work, not a computed value — exactly as KA 8.6.2's six-factor filter is a structuring device for a judgement,
not an equation. What follows below is instead an illustrative, fully worked *cost* comparison that makes the
qualitative argument concrete in dollar terms.

**Example 9.1.1 — Quantifying the cost of a late-discovered change on the Field App.**

*Scenario.* KA 8.6.1 recorded that the Field App's photo-capture screen, first delivered in Sprint 1, was
revised a second time in Sprint 3 to simplify a tagging workflow that site engineers found slow after Sprint
2's review. Meridian's PMO sizes that Sprint 3 rework at 3 of Sprint 3's 21 delivered story points, absorbed
within the sprint's existing, fixed $15,000 (SAR 56,250) run-rate. Meridian also holds change-control cost
data for a comparable requirement discovered late — at User Acceptance Testing, after a module has been
built, integrated, tested and its documentation issued — on similarly scoped, predictively run digital work:
reopening a signed-off module, re-running regression tests across dependent modules and reissuing user
documentation costs, on average, a full sprint-equivalent of $15,000 (SAR 56,250).

*Required.* (a) The cost of the adaptive fix, allocated proportionately within Sprint 3's fixed run-rate; (b)
the cost multiple of the predictive-equivalent, late-discovered fix relative to the adaptive fix.

*Working.*
(a) `Adaptive fix cost = (3 points / 21 points) × $15,000 = $15,000 / 7 = $2,142.86 ≈ $2,143` (SAR 8,036).
(b) `Cost multiple = $15,000 / $2,142.86 = 7.0`.

*Answer.* The adaptive fix costs an illustrative **$2,143 (SAR 8,036)**; the predictive-equivalent,
late-discovered fix costs **$15,000 (SAR 56,250) — seven times as much**, for what is, in substance, the same
underlying correction.

*Interpretation.* The sevenfold gap is not a property of "software versus construction," it is a property of
*when in the process the correction is discovered and made*. Discovering it during a short, empirical
inspection cycle (a Sprint Review) keeps the correction cheap because nothing downstream has yet been built
on top of the flawed version; discovering it only once a defined, sequential process has moved on — modules
integrated, tests passed, documentation issued — makes the same correction expensive because all of that
downstream work must now be reopened. This is the arithmetic case for choosing empirical process control,
and hence adaptive delivery, specifically for work where the right answer is not yet knowable.

**Mini-case — reading Pipeline Segment 4B and the Field App through the defined/empirical lens.** Pipeline
Segment 4B's trenching, pipe-laying and welding work follows engineering standards and a regulator-approved
route fixed before excavation begins: the same inputs (route, pipe spec, welding procedure), followed
correctly, reliably produce the specified pipeline — a defined process, for which predictive planning and
classical EVM (KA 6.1) are the right tools. The Field App's screen layouts and workflows cannot be fully
specified before site engineers actually try them: the right answer is discovered, not derived — an empirical
process, for which the inspect-and-adapt cycle below is the right tool. Both scopes sit in the same Meridian
programme; the process-control theory, not the industry, decides which model each requires (reinforcing KA
8.6.1's own conclusion from a different angle).

**Common pitfalls.**
- Assuming every digital or software scope is automatically an empirical process, and every physically
  executed scope is automatically a defined one — the correct test is the nature of the specific work's
  uncertainty (KA 8.6.2's six factors), not the industry it sits in.
- Treating the sevenfold figure above as a universal constant — it is one illustrative case, sized from one
  team's own data; the true multiple varies by project and must be evidenced locally, not assumed.
- Applying inspection without genuine adaptation — reviewing progress at a Sprint Review but not actually
  changing the plan when the review reveals a problem defeats the loop's purpose and quietly reverts the team
  to defined-process behaviour under adaptive labels (developed fully as "agile-in-name-only," KA 8.6.3,
  revisited from a different angle in 9.1.4).

**AI in this topic.** AI-based analytics run over a team's own historical ticket, rework and timesheet data
can estimate an evidence-based cost-of-change multiple (an AI-derived version of the illustrative 7.0×
figure above) far more precisely than a rule-of-thumb assumption, provided the underlying rework and cost
data is complete and consistently coded (cross-reference KA 13.2, KA 13.5). Such a tool cannot itself decide
whether a given class of work is genuinely an empirical process — that classification judgement, and the
consequent choice of measurement framework, remains the professional's, applying KA 8.6.2's criteria before
any AI-derived multiple is relied upon in a forecast.

**Cross-references.** KA 8.6.1 (the development-approach spectrum); KA 8.6.2 (the six-factor suitability

logic); KA 9.2 (Scrum's three pillars and events, built directly on this theory, in full).

### 9.1.2 The Agile Manifesto: the four values

**Definition & purpose.** In February 2001, seventeen software practitioners — among them Kent Beck, Martin
Fowler, Alistair Cockburn, Ward Cunningham, Ken Schwaber and Jeff Sutherland — met at a ski resort in
Snowbird, Utah, and published a short founding statement for a family of approaches then emerging as
alternatives to heavyweight, document-driven software processes: the *Manifesto for Agile Software
Development*. The Manifesto states four relative value preferences. Described in this handbook's own words,
never the Manifesto's original wording, they are:

- **People and their interactions, valued above the tools and processes used to coordinate them.** A capable
  team that communicates and collaborates well will outperform a rigid process followed by a disengaged one,
  even where the disengaged team has better tooling.
- **A working, usable result, valued above exhaustive documentation about that result.** Documentation still
  has a role — traceability, handover, regulatory compliance — but it is not treated as a substitute for
  something a real user can actually operate and give feedback on.
- **Ongoing collaboration with the customer or business, valued above negotiating and fixing every detail in
  a contract before work starts.** The contract still matters (KA 7.1, KA 9.6), but the customer is treated
  as a continuing partner in shaping the outcome, not a party who specifies once at the start and signs off
  once at the end.
- **The capacity to respond to changing circumstances, valued above rigid adherence to an original plan.**
  The plan — a backlog, a roadmap — still matters, but it is treated as a living input that is expected to be
  revised, not a fixed contract with a reality that has since moved on.

**The underlying principle.** Each value is a *relative emphasis between two genuine goods*, not a rejection
of the item named second — a nuance this KA returns to explicitly in 9.1.4, because misreading "valued above"
as "instead of" is the single most common source of misapplied agile practice. Read together, the four values
operationalise 9.1.1's empirical process control loop: the first value supplies the people who will do the
inspecting and adapting; the second makes the thing being inspected real rather than theoretical; the third
keeps every inspection anchored to what the actual customer actually needs; the fourth makes genuine
adaptation possible once inspection reveals something new. Remove any one value and the loop degrades — for
example, retaining rigorous documentation and a fixed contract while dropping only the fourth value produces
exactly the "agile-in-name-only" pattern named in KA 8.6.3.

**Mini-case — applying the four values to a real Meridian decision.** Before Sprint 1, Meridian's programme
sponsor — used to Pipeline Segment 4B's predictive documentation standard — asks the Field App team to
produce and have formally signed off a 40-page requirements specification before any development begins, in
the same manner as a predictive work package's baseline scope. Assessed against the four values: the request
does not reject documentation outright (value 2 does not forbid it), but a single, exhaustively pre-agreed
specification for genuinely emergent, screen-level requirements contradicts value 4 (it fixes a plan the team
already expects to revise) and, if it substitutes for direct sponsor engagement each sprint, value 3 as well.
The agile-consistent response — developed fully in 9.1.4 once the "no documentation" misconception is
formally rebutted — is not *no* specification, but a right-sized one: a prioritised backlog with acceptance
criteria, revisited and re-agreed with the sponsor at the cadence of the empirical loop (9.1.1), rather than
fixed once for the whole build.

**Common pitfalls.**
- Reading "valued more" as "the only thing that matters," discarding documentation, contracts or planning
  outright — the single most consequential misreading of the Manifesto, formally rebutted item by item in
  9.1.4.
- Applying the values as a slogan without the empirical loop (9.1.1) or a concrete framework (KA 9.2, KA 9.4)
  behind them — values alone do not deliver anything; they are the mindset a framework then operationalises
  (9.1.4).
- Assuming the four values are specific to software — they are stated for software in the Manifesto's title
  and origin, and this handbook, consistent with that origin, keeps its illustrative example in a software
  context (the Field App); their extension to non-software, genuinely uncertain work is a considered
  application, not an automatic one (KA 8.6.2, KA 9.6).

**AI in this topic.** A GenAI assistant can draft a first-pass team working agreement that references the
four values, and can scan a team's actual artefacts (meeting cadence, documentation volume, change-request
acceptance rate) to flag where stated practice appears to contradict a stated value — for example, a team
claiming to value responding to change while rejecting the great majority of proposed backlog changes
(cross-reference KA 13.3, KA 13.5). Such a flag is a useful diagnostic prompt for a team's own reflection; it
is not a verdict, and deciding what the mismatch means, and what to do about it, remains the team's and the
accountable professional's judgement.

### 9.1.3 The Agile Manifesto: the twelve supporting principles

**Definition & purpose.** Alongside the four values, the same authors published twelve principles that
elaborate them into more concrete guidance for how a team actually works. Described here in this handbook's
own words and grouped thematically for teachability — never quoted from the original text — the twelve are:

*Delivering value, frequently.* The team's highest priority is satisfying the customer through early and
continuous delivery of something genuinely valuable. Delivery should happen frequently — the Manifesto's
authors favoured cycles measured in weeks rather than months. A working result, not a status report or a
plan, is treated as the most trustworthy evidence of real progress.

*Welcoming change.* Requirements are expected to change, even late in delivery, and that capacity to change
is treated as an advantage the customer can use, not a planning failure to be prevented.

*People, collaboration and environment.* Business or customer representatives and the delivery team are
expected to work together continuously throughout delivery, not only at hand-off points. The team is built
around motivated individuals, given the environment, support and trust to organise their own work, on the
premise that this produces better outcomes than close, detailed direction. Rich, direct conversation — where
practicable, face-to-face — is treated as the most efficient way to move information within the team, a
principle increasingly read today as favouring the richest practical channel available to a given team,
including well-run synchronous video conversation for distributed teams, rather than requiring physical
co-location. A sustainable pace is expected: the team, its sponsors and its users should be able to sustain
their rate of work indefinitely, rather than relying on repeated bursts of unsustainable effort.

*Technical practice and simplicity.* Ongoing attention to sound technical practice and good design is treated
as what keeps a team able to remain adaptive over time, rather than a one-off investment. Keeping the
solution as simple as the goal allows — deliberately avoiding unnecessary work rather than merely tolerating
it — is treated as a core discipline.

*Self-organisation and reflection.* The best architectural, requirements and design outcomes are expected to
emerge from teams that organise their own work, rather than from centrally specified detail. At regular
intervals, the team is expected to step back, reflect on how effectively it is working, and adjust its own
behaviour accordingly — a built-in improvement loop rather than a one-off process design.

**The underlying principle.** The twelve principles are the operational bridge between the four abstract
values (9.1.2) and a concrete framework's specific mechanics (KA 9.2). Several map almost directly onto
named Scrum elements developed in full there: the reflection principle becomes the Sprint Retrospective; the
frequent-delivery principle becomes the Sprint's fixed timebox; the working-result-as-progress principle
becomes the Increment and the Definition of Done; the welcoming-change principle becomes ongoing Product
Backlog refinement. Reading the twelve principles as a checklist to be individually satisfied misses this —
they cohere as a single operating philosophy, and a framework earns the description "agile" by embodying
that philosophy as a whole, not by ticking off principles one at a time.

**Mini-case — mapping the Field App's Sprint 3 fix (Example 9.1.1) onto the twelve principles.** The tagging-
workflow simplification illustrates several principles operating together, not one in isolation: welcoming
change (the requirement to simplify only emerged from real use, and was accepted rather than resisted);
working results as progress (the flaw was visible only because a working screen existed to inspect, not from
a written specification review); and reflection (the fix followed directly from the Sprint 2 review, the
kind of regular, structured look-back the twelfth principle describes). The $2,143 cost computed in Example
9.1.1 is, in effect, the price of exercising these three principles together — and, per that example, a
fraction of the cost of not exercising them until much later.

**Common pitfalls.**
- Treating the twelve principles as an audit checklist scored item by item, rather than judging whether a
  team's overall way of operating embodies the philosophy they describe as a whole.
- Over-applying the face-to-face communication principle to conclude that any distributed or remote agile
  team is automatically "doing it wrong" — an honest, current reading favours the richest practical channel
  available, not physical co-location as an absolute requirement.
- Assuming the principles prescribe specific ceremonies by name — they describe outcomes and behaviours; KA
  9.2's named Scrum events are one framework's concrete way of embodying them, not the only possible one (KA
  9.4 covers Kanban's different embodiment).

**AI in this topic.** AI-based retrospective-analysis tools can scan sprint artefacts, retrospective notes and
delivery metrics to suggest which of the twelve principles a team appears weakest against — for example, a
low, irregular release frequency against the frequent-delivery principle (cross-reference KA 9.6, KA 13.5) —
giving a team a data-informed starting point for its own reflection. Genuine reflection and the decision to
change behaviour (the twelfth principle itself) is the team's and the professional's own act; it cannot be
delegated to an automated summary, however well the summary is drafted.

### 9.1.4 Agile as a mindset, not a framework — and the common misconceptions that follow from confusing the two

**Definition & purpose.** Three distinct levels sit beneath the word "agile," and keeping them separate
resolves most of the misconceptions a project-controls professional is likely to encounter:

- **Mindset** — the values (9.1.2) and principles (9.1.3) themselves: a way of thinking about how to deliver
  work under genuine uncertainty. The mindset is not tied to any specific ceremony, role or artefact.
- **Framework/method** — a concrete, named structure of roles, events and artefacts that operationalises the
  mindset. Scrum (KA 9.2, the most widely adopted, developed here in full) and Kanban (KA 9.4, at awareness
  level in this handbook, per the domain map) are two different, named frameworks built on the same
  underlying mindset; scaled variants such as SAFe and LeSS (KA 9.4, awareness level) extend a framework's
  ideas across multiple teams.
- **Practice** — the specific, team-level technique used within a framework, such as a particular relative-
  estimation method or a specific board layout (KA 9.3, KA 9.4).

**The underlying principle: adopting the middle level does not confer the top level.** A team can run every
ceremony a framework prescribes — daily stand-ups, fixed-length cycles labelled "sprints," a visible board —
while never adopting the mindset those ceremonies were built to serve: this is precisely the "agile-in-name-
only" pattern KA 8.6.3 names from a hybrid-governance angle. Restated from this KA's mindset-versus-framework
angle: the ceremonies are the *outward form* of empirical process control (9.1.1) and the four values (9.1.2);
running the form without the underlying inspect-and-adapt substance — for example, holding a Sprint Review at
which nothing about the plan is ever actually allowed to change — produces a team that looks agile and
measures like a predictive one, because, in substance, it still is one.

**Iterative and incremental delivery, briefly recapped.** The mechanics by which any agile framework actually
delivers — building in repeated passes that refine the same work (iterative) and in successive, separately
usable slices (incremental) — are defined and fully worked, with the Field App's own Sprint 1–3 example, in
KA 8.6.1; that treatment is not repeated here. What this KA adds is the reason those mechanics are combined
with an *adaptive, empirically driven planning cycle* specifically: iterative and incremental delivery could,
in principle, be run against a fixed, pre-agreed sequence of increments (a phased predictive rollout is
iterative-and-incremental too, KA 8.6.1) — what makes a framework genuinely *agile* is pairing those delivery
mechanics with the mindset and empirical loop set out in 9.1.1–9.1.3, so that *which* increment comes next,
and how it is refined, is itself decided empirically rather than fixed in advance.

**Common misconceptions, addressed directly.**

| Misconception | What is actually true |
|---|---|
| "Agile means no planning." | Agile plans continuously, at a shorter horizon and in a different, living artefact (a prioritised backlog, a Sprint Goal) rather than in one long-range, fixed plan (value 4, principle: welcoming change). |
| "Agile means no documentation." | Value 2 favours a working result as the primary vehicle of progress over documentation as that vehicle — it does not forbid documentation; regulatory, contractual and handover documentation still exists where the work genuinely requires it (KA 9.6). |
| "Agile means no discipline, no metrics, no deadlines." | Scrum's fixed timeboxes, the sustainable-pace principle, and agile metrics (velocity, burnup, cycle time — KA 9.3) impose a tighter, more frequent measurement cadence than a single end-of-project deadline provides. |
| "Agile is only for software." | Agile frameworks originated in, and remain most mature in, software delivery — where this handbook's own illustrative example, the Field App, sits. Genuinely uncertain, emergent work in other domains can borrow agile techniques; a physically executed, defined-process scope such as Pipeline Segment 4B remains a poor fit, per KA 8.6.2's own criteria, for reasons of process, not industry. |

**Mini-case — resolving 9.1.2's sponsor request with the misconceptions table.** Returning to 9.1.2's
scenario: Meridian's sponsor's underlying, legitimate concern — that the Field App's scope should not be
completely undocumented and ungoverned — survives the misconceptions table's rebuttal intact; what does not
survive is the specific request for one, fixed, exhaustively pre-agreed 40-page specification signed off
before Sprint 1. The right-sized alternative is a living backlog with acceptance criteria and a Definition of
Done, reviewed and re-agreed with the sponsor at the cadence of the empirical loop (9.1.1) rather than fixed
once — satisfying value 2's spirit (a real, working screen each sprint, not a document, is the primary
evidence of progress) without discarding governance (KA 9.6 develops the full hybrid-governance treatment).

"The ceremonies are supposed to rest on the mindset. Built the other way round, they don't hold."

**Common pitfalls.**
- Conflating "we adopted Scrum" with "we are agile" — framework adoption is necessary but not sufficient; the
  mindset layer above it must genuinely be present too.
- Assuming every framework fits every context equally, rather than matching the framework to the work's
  nature (Scrum's fixed-length sprints versus Kanban's continuous flow — KA 9.4 develops the choice).
- Treating a misconception's rebuttal as license to swing to the opposite extreme — for example, "documentation
  is not forbidden" does not mean "as much documentation as a predictive project"; the right-sizing judgement
  in the mini-case above still has to be made deliberately, not defaulted in either direction.

**AI in this topic.** General-purpose AI chat assistants can explain Scrum or Kanban mechanics accurately most
of the time and can be a fast, convenient way to look up a definition (cross-reference KA 13.3, KA 13.4).
Because these are widely documented but frequently *mis-explained* topics even in human-authored material,
a subtly wrong AI-generated explanation of a framework element is a real and easy-to-miss risk; any AI
explanation of Manifesto, Scrum Guide or framework content used in training material, a policy document or an
exam item should be checked against the authoritative source before it is relied upon, rather than treated as
itself authoritative.

**Cross-references.** KA 8.6.1 (iterative and incremental mechanics, in full); KA 8.6.3 (hybrid delivery and
"agile-in-name-only," from the governance angle); KA 9.2 (Scrum, the framework layer, in full); KA 9.4
(Kanban and scaling, awareness level); KA 9.6 (hybrid delivery and agile governance, in full).

### 9.1.5 What agile means for a project-controls professional: measuring value and progress differently

**Definition & purpose.** For a professional trained on predictive measurement (BAC, PV, EV, AC — Domain 6),
adaptive delivery changes more than *how developers work* — it changes what "progress" and "value" mean as
measured quantities, which is why Domain 9 is a distinct domain in this Body of Knowledge rather than a
short appendix to Domain 8. This topic sets out that change at foundation level; KA 9.3 defines velocity and
burnup/burndown metrics in full, and KA 9.5 — flagged as the project-controls crux of this domain — adapts EV,
CPI, SPI and EAC themselves to a variable-scope backlog as AgileEVM.

**The underlying principle: value is recognised differently, not less rigorously.** KA 8.6.4's Table 8.6.4
(cross-referenced, not repeated here) already established the inverted iron triangle: predictive delivery
fixes scope and forecasts time/cost; adaptive delivery fixes time/cost and forecasts scope. The consequence
for *value* follows directly. Under predictive measurement, value is conventionally recognised as earned once
work reaches an agreed percentage complete against a fixed scope baseline (EV, KA 6.1) — a graduated,
continuous measure. Under adaptive measurement, value is recognised only once a backlog item is genuinely
usable and accepted against its Definition of Done (KA 9.2) — a binary, per-item standard, applied across a
backlog whose total scope is itself variable. This is, if read carefully, a *stricter* test of "real" value
than a percentage-complete claim: an item is either genuinely usable or it is not, whereas a percentage-
complete figure can (and, per KA 6.1.4's front-loading pitfall, sometimes does) claim value for work that is
not yet usable by anyone. Velocity — story points completed per sprint, the canonical adaptive progress unit
defined once in the spine's formula-symbol table and developed fully in KA 9.3 — is the metric this stricter,
per-item standard is built on; it is introduced by name here only to establish that it exists, not defined in
depth in this KA.

**Example 9.1.5 — Value delivered over time: adaptive versus a hypothetical predictive treatment of the
same Field App scope.** *This is a teaching counterfactual: the Field App was, in fact, delivered adaptively,
exactly as recorded in KA 8.6.1 and KA 8.6.4. The "predictive-equivalent" column below is a hypothetical, not
an event that occurred, constructed only to show how the same underlying 200-point build effort would report
its progress under a single-release measurement approach.*

*Scenario.* Reusing KA 8.6.4's established figures: cumulative story points delivered and placed into live
use were 16 after Sprint 1, 35 after Sprint 2, and 56 after Sprint 3 (of the 200-point backlog), with
completion forecast at Sprint 11. A hypothetical predictive treatment of the identical build effort, reported
as a single release with progress measured by conventional weighted milestones (design, build, integration,
test), might plausibly show 20% "complete" after Month 1, 45% after Month 2 and 65% after Month 3 — yet, by
construction of a single-release plan, nothing would be usable by an end user until integration and testing
finish, near Sprint 11.

*Required.* Compare cumulative *usable* value delivered under each treatment at the same three checkpoints.

*Working.* Adaptive, usable value (% of 200-point backlog, live in production): Sprint 1 `16/200 = 8.0%`;
Sprint 2 `35/200 = 17.5%`; Sprint 3 `56/200 = 28.0%` — usable to end users from Sprint 1 onward. Hypothetical
predictive-equivalent, usable value: 0% at every one of the three checkpoints, despite a reported 20–65%
"complete," because nothing is released until the single end-of-build delivery.

*Answer.*

| Checkpoint | Adaptive: cumulative usable value (of 200 pts) | Adaptive: usable to end users? | Predictive-equivalent: % "complete" (hypothetical) | Predictive-equivalent: usable to end users? |
|---|---|---|---|---|
| Sprint/Month 1 | 16 pts (8.0%) | Yes — photo-capture live | ~20% | No |
| Sprint/Month 2 | 35 pts (17.5%) | Yes — growing | ~45% | No |
| Sprint/Month 3 | 56 pts (28.0%) | Yes — growing | ~65% | No |
| Sprint 11 (forecast) | 200 pts (100%) | Fully delivered, incrementally, since Sprint 1 | 100% | Yes — first point anything is usable |

*Interpretation.* The predictive-equivalent column can look, on paper, like the more advanced project through
Month 3 (65% against 28.0%) while delivering precisely zero usable value to a real user in that time — the
percentage tracks *effort expended against a plan*, not *value in anyone's hands*. The adaptive column reports
a lower cumulative percentage but real, growing, usable capability from Sprint 1. Neither figure is wrong on
its own terms; using the wrong one to answer "how much value have we actually delivered" is the error this
example exists to prevent.

**Mini-case — a teaser for revenue recognition on an agile contract.** A commercial or project-controls
professional who assumes a predictive-style percentage-of-completion figure is equivalent to genuinely
delivered, accepted value on an agile-delivered contract risks a revenue-recognition position under IFRS 15
(KA 2.2) that does not match what has actually been transferred to the customer — over-billing or
under-billing risk that mirrors, but is not identical to, the over-/under-billing analysis in KA 7.5. This KA
only flags the issue; KA 9.5 works a full, reconciled example linking story-point progress, AgileEVM and IFRS
15 revenue recognition on an agile contract.

**Fig 9.1.5 — Cumulative usable value: adaptive versus a hypothetical predictive-equivalent treatment.**
Chart type: a two-series line/step chart. Vertical axis: cumulative value (% of the 200-point backlog),
0–100%. Horizontal axis: Sprint/Month 1–11. Series 1 (brand blue `#1D4ED8`, a step line): adaptive cumulative
*usable* value, stepping up at each sprint boundary (8.0%, 17.5%, 28.0%, … to 100% at Sprint 11). Series 2
(grey dashed line): the hypothetical predictive-equivalent "% complete" curve, rising smoothly from Month 1
but shown as a flat, separate marker at 0% *usable* until it jumps to 100% at Sprint 11. A shaded band between
the two series through Sprints 1–10 is labelled "the value-delivery gap — reported progress that is not yet
usable by anyone."

*Underlying data:* the table in Example 9.1.5 above (Sprints 1–3 and the Sprint 11 forecast); intermediate
sprints interpolated smoothly for the chart's rendering.

**Animation 9.1.5 — "Two lines, one gap" [digital-only].** Frame 1: both series start together at Sprint 0.
Frame 2: the adaptive step line rises sprint by sprint, each step accompanied by a small "usable" icon.
Frame 3: the predictive-equivalent dashed line rises smoothly on its own separate "% complete" track, with no

tells you what's been built. The other tells you what's been used. A project-controls professional needs to
know which one they're reading."

**Common pitfalls.**
- Treating a predictive-style percentage-complete figure and a genuinely delivered, accepted value as
  interchangeable on adaptive work — they answer different questions, as Example 9.1.5 shows numerically.
- Assuming "measuring differently" means "measuring less rigorously" — the Definition of Done standard behind
  adaptive value recognition is, if anything, a stricter binary test than a graduated percentage-complete
  claim, which is exactly why KA 6.1.4's front-loading pitfall cannot occur in the same way once a
  Definition of Done is properly enforced.
- Forgetting that changing the measurement framework does not change who is accountable for the resulting
  forecast: whichever metric a piece of work uses — EV/CPI/SPI/EAC or velocity/burnup/AgileEVM — the governing
  principle of this Body of Knowledge still applies without exception: **AI proposes; the professional
  disposes.** An AI-generated velocity forecast or a burnup projection carries exactly the same sign-off
  obligation as an AI-drafted EAC.

**AI in this topic.** AI-based forecasting tools can compute rolling velocity averages and project burnup
trends (developed fully in KA 9.3, KA 9.5) and can generate a first-draft "value delivered" narrative from
sprint data, considerably faster than a manual roll-up (cross-reference KA 4.4, KA 13.5). Such a tool cannot
decide which measurement framework — predictive EVM or adaptive velocity/AgileEVM — genuinely fits a given
piece of work; that classification judgement was made once, upstream, per KA 8.6.2, and an AI narrative built
on the wrong framework will be fluent and wrong. Nor can an AI tool verify that a backlog item reported as
"done" has actually been accepted against its Definition of Done rather than merely coded — that verification,
and sign-off on any forecast reported to a sponsor or client, remains the professional's.

**Cross-references.** KA 6.1 (classical EV, the predictive comparator throughout this topic); KA 8.6.4 (the
inverted iron triangle and its full measurement-comparison table, not repeated here); KA 9.2 (the Definition
of Done, in full); KA 9.3 (velocity and burnup/burndown, defined and worked in full); KA 9.5 (AgileEVM and

recognition and the over-/under-billing analysis this topic's mini-case anticipates).

### Key terms

- **Defined (theoretical) process control** — a process fully understood in advance, where given inputs
  reliably produce a given output, so work can be planned in detail and checked for conformance.
- **Empirical process control** — a process not fully understood in advance, where progress and quality are
  assured by working in small increments and adjusting continually in light of what is observed.
- **Transparency, Inspection, Adaptation** — the three pillars of empirical process control (9.1.1), fully
  developed as Scrum's own pillars in KA 9.2.
- **The Agile Manifesto** (*Manifesto for Agile Software Development*, 2001) — the founding statement of four
  relative value preferences for adaptive software delivery, described in this KA in the authors' spirit but
  never in their original wording.
- **The four values** — people/interactions over processes/tools; a working result over comprehensive
  documentation; customer collaboration over contract negotiation; responding to change over following a
  plan (each a relative emphasis, not an exclusion — 9.1.2).
- **The twelve principles** — the Manifesto's supporting guidance elaborating the four values into concrete
  behaviour (9.1.3).
- **Agile mindset** — the values and principles themselves, independent of any specific framework or
  ceremony.
- **Framework/method** — a concrete structure of roles, events and artefacts (Scrum, Kanban, XP, scaled
  variants) that operationalises the mindset (9.1.4; KA 9.2, KA 9.4).
- **Agile-in-name-only** — running a framework's ceremonies without the underlying mindset or genuine
  adaptation (KA 8.6.3, revisited in 9.1.4).
- **Sustainable pace** — the principle that a team, its sponsors and its users should be able to sustain their
  rate of work indefinitely, rather than through repeated unsustainable effort (9.1.3).
- **Definition of Done** — the shared, agreed standard a backlog item must meet before it is recognised as
  genuinely usable/delivered value under adaptive measurement (9.1.5; full treatment KA 9.2).
- **Velocity** — story points completed per sprint (spine formula-symbol table; defined in full in KA 9.3).

### Sample MCQs

**MCQ 9.1.1 [topic 9.1.1, level: recall]**
Which best describes "empirical process control"?

A. A process so well understood that the same inputs always produce the same output
B. **A process not fully understood in advance, where progress is assured by producing small increments and
   adjusting in light of what is observed** ✔
C. A process used only for financial reporting under IFRS
D. A synonym for the critical path method
*Rationale:* 9.1.1 defines empirical process control as applying where the process is not yet fully knowable,
relying on inspect-and-adapt cycles. A describes defined process control, its counterpart; C and D are
unrelated concepts from other domains.

**MCQ 9.1.2 [topic 9.1.1, level: application — numerical]**
A 4-point rework item is absorbed within a sprint that delivered 20 points in total, at a fixed sprint cost of
$12,000. Using the same proportional-allocation method as Example 9.1.1, what is the allocated cost of the
rework item?

A. $2,000
B. **$2,400** ✔
C. $3,000
D. $12,000
*Rationale:* `(4/20) × $12,000 = 0.20 × 12,000 = $2,400`. A and C are arithmetic slips; D wrongly assigns the
whole sprint's cost to a single item.

**MCQ 9.1.3 [topic 9.1.2, level: analysis]**
Under the Agile Manifesto's four values, which statement correctly captures how "a working result" and
"comprehensive documentation" relate to one another?

A. Documentation is forbidden under agile delivery
B. **A working, usable result is valued more highly than documentation as the primary evidence of progress,
   but documentation still has a role** ✔
C. The two are unrelated and neither is prioritised over the other
D. Documentation must always exceed working software in volume
*Rationale:* 9.1.2 explains each value as a relative emphasis, not an exclusion — documentation is not
discarded, simply not treated as the primary vehicle for demonstrating progress. A overstates the value into
prohibition (the core misconception rebutted in 9.1.4); C denies the stated preference; D is unsupported.

**MCQ 9.1.4 [topic 9.1.4, level: application]**
A team holds daily stand-ups, calls its two-week cycles "sprints," and maintains a visible backlog board, but
the backlog's contents and sequence were fixed before work began and are never re-prioritised in light of
Sprint Review feedback. This is best explained, per 9.1.4, as:

A. A well-executed Scrum implementation
B. **A framework's ceremonies adopted without the underlying mindset — agile-in-name-only** ✔
C. Genuine Kanban flow management
D. An example of the twelve principles being fully satisfied
*Rationale:* Per 9.1.4's mindset/framework/practice hierarchy, running ceremonies without genuine adaptation
is exactly the agile-in-name-only pattern (also KA 8.6.3). A and D assume the mindset is present, which the
scenario contradicts; C misidentifies the framework in play.

**MCQ 9.1.5 [topic 9.1.5, level: analysis]**
In Example 9.1.5's comparison, at Month 3 the hypothetical predictive-equivalent treatment shows roughly 65%
"complete" while the adaptive treatment shows 28.0% cumulative usable value. What does this gap primarily
illustrate?

A. That the adaptive team is performing worse than a predictive team would
B. **That a percentage-complete figure can measure effort expended against a plan, while usable value measures
   what has actually been delivered and accepted — the two are not interchangeable** ✔
C. That percentage-complete figures are always inaccurate and should never be used
D. That the Field App backlog was mis-estimated
*Rationale:* 9.1.5 shows the two metrics answer different questions; neither is inherently wrong, but using
one to answer the other's question misleads. A and D are not supported by the example; C overstates the
lesson into a blanket rejection of percentage-complete measurement, which remains valid for its own,
predictive purpose (KA 6.1).

### Self-check questions (answers in Appendix C)

1. In your own words, explain why the cost of the Field App's Sprint 3 tagging-workflow fix (Example 9.1.1)
   was significantly lower than Meridian's illustrative cost for a comparable, late-discovered change under a
   predictive treatment. Which of the three pillars in Fig 9.1.1 is most directly responsible for keeping the
   cost low?
2. A colleague says: "our team dropped detailed documentation entirely because we're doing agile now, in line
   with the Manifesto." Using the four values (9.1.2) and the misconceptions table (9.1.4), explain what is
   wrong with this statement and what the Manifesto's second value actually says.
3. A team completes a 5-point rework item within a sprint that delivered 25 points in total, at a fixed sprint
   cost of $18,000. Using Example 9.1.1's proportional-allocation method, calculate the allocated cost of the
   rework item.
4. Explain, in your own words, the difference between the "mindset," "framework" and "practice" levels set
   out in 9.1.4, and give one example of each using either Scrum (KA 9.2) or Kanban (KA 9.4) by name.

**Answers**

1. The fix was found during Sprint 2's review — an inspection point that occurred before anything else had
   been built on top of the flawed tagging workflow — so adapting it in Sprint 3 only required reworking that
   one small piece. A predictive, defined-process treatment would not discover the same flaw until much later
   (User Acceptance Testing), by which point dependent modules, tests and documentation would already have
   been built on the flawed version, making the correction far more expensive. **Inspection** is most directly
   responsible: without a frequent, structured point at which the work was examined against reality, the flaw
   would not have surfaced early enough for a cheap adaptation.
2. The statement conflates "valuing a working result over documentation" with "documentation is forbidden,"
   which is exactly the misconception rebutted in 9.1.4's table. The Manifesto's second value states that a
   working, usable result is valued *more highly* than comprehensive documentation as the primary evidence of
   progress — it does not state that documentation should not exist; regulatory, contractual and handover
   documentation still has a role wherever the work genuinely requires it.
3. `Allocated cost = (5/25) × $18,000 = 0.20 × 18,000 = $3,600.`
4. **Mindset** is the underlying values and principles (9.1.2, 9.1.3) — for example, the value that favours
   responding to change over following a fixed plan. **Framework** is a concrete, named structure that puts
   the mindset into practice — for example, Scrum's defined roles, events and artefacts (KA 9.2), or Kanban's
   visualise-and-limit-WIP approach (KA 9.4). **Practice** is a specific team-level technique used within a
   framework — for example, planning poker as a relative-estimation technique used within a Scrum team's
   backlog refinement (KA 9.3).
