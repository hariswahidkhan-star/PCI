# PCI Standard Compliance-Test Catalogue

**Instrument status: none.** This is a derived register. It is not a PCI Standard, it creates no obligation, and nothing in it may be cited as a requirement (Charter §3).

It is element 21 — the compliance test — of all 113 PCI Standards in one place, with the reviewer’s actions, the records the test needs, and an assessment of whether two reviewers performing it independently would reach the same answer. It was derived by extracting element 21 from each standard mechanically; the first three columns are generated from that text, and the last column was assigned by reading every element 21 against the five tests stated in §2 and is carried, with its reason for each standard, in `make_standards_registers.py`. **The tests are reported, not rewritten** — where a test is weak, that is the standard’s wording and not this catalogue’s. Generated by `make_standards_registers.py` from the four standard files. **It is derived, not authoritative: it goes stale the moment a standard file changes.** Re-run the generator after any edit, and read the standard itself before relying on any row here.

**The last column is the point of this catalogue.** A compliance test whose answer turns on the reviewer produces inconsistent assessment: the same file passes with one assessor and fails with another, and a candidate cannot be examined on it fairly. 26 of the 113 tests are in that class.

**4 of them say the opposite of themselves** — the element 21 text asserts that two reviewers reach the same answer while containing a step that requires a judgement: `PCI-PCL-STD-06.04` · `PCI-PCL-STD-07.01` · `PCI-PCL-STD-07.03` · `PCI-PCL-STD-13.03`. `PCI-PCL-STD-07.01` is the honest one: it concedes that two reviewers may differ and says that the disagreement is itself the signal.

## 2. How the last column was decided

A test is **judgement-dependent** where at least one stated compliance condition requires the reviewer to evaluate the *substance* of content rather than to observe a fact about a record. The five triggers:

| | Trigger |
|---|---|
| **J1** | The reviewer must decide for themselves whether something is *material*, *adverse* or *significant*, and no recorded threshold or recorded conclusion supplies the answer |
| **J2** | The reviewer must judge whether an explanation, a response or an assessment is *complete*, *adequate* or *substantive* |
| **J3** | The reviewer must reach a substantive conclusion **from** the evidence — that a provision *supports* a use, that a record *supports* an entitlement |
| **J4** | The reviewer must apply a **counterfactual** — which decisions *would have* differed, which assumptions’ failure *would* change the conclusion |
| **J5** | The reviewer must form a view about another person’s recorded state of mind |

Otherwise the answer is **yes**: it follows from a document’s presence, a date order, a name comparison, a query over a population, an arithmetic reconciliation or a re-performance.

**Materiality used only to scope a sample is not counted.** Selecting *a sample of material outputs* leaves each sampled item’s pass condition objective. Materiality that decides whether a sampled item passes, or that the reviewer must apply to build a population whose **completeness** the test turns on, is counted — that is the difference between `PCI-FND-STD-01` (yes) and `PCI-FND-STD-11` (judgement-dependent).

**Secondary observation.** A further **6** tests whose answer is otherwise reviewer-independent nonetheless draw their **sample** by applying materiality: `PCI-FND-STD-01` · `PCI-FND-STD-03` · `PCI-FND-STD-04` · `PCI-FND-STD-06` · `PCI-FND-STD-07` · `PCI-PML-STD-01.01`. They are recorded as *yes* on the rule above, but two reviewers applying the materiality test differently will test different populations, which is a second, quieter route to inconsistent assessment.
