# Re-baselining is a governance act, not a scheduling task

**Post body (1,885 characters):**

Re-baselining does not fix a project. It changes the question you are allowed to ask about it, which is why it should never sit with the planner alone.

Here is what it moves. Budget at completion £48.0m. Earned value £21.0m. Actual cost £26.2m.

CPI = 21.0 ÷ 26.2 = 0.80
Cost variance = 21.0 − 26.2 = −£5.2m
TCPI to the original budget = (48.0 − 21.0) ÷ (48.0 − 26.2) = 27.0 ÷ 21.8 = 1.24

Re-baseline to £53.2m and reset earned value to actual cost, which is what most re-baselines quietly do. CPI becomes 1.00. TCPI becomes 1.00.

The £5.2m has not been recovered or written off. It has moved from the variance column into the budget, and the obligation to run the remaining work at 1.24 while delivering 0.80 has been assumed away rather than answered.

So the test is one question, asked before anyone opens the tool. Did the scope change, or did the performance? A client instruction, a scope addition, a ground condition nobody could have priced: re-baseline. Poor productivity or an optimistic original estimate: do not, because the variance is the only evidence that any of it happened.

A governed re-baseline records five things. The trigger, and who had the authority to call it. The variance at the moment of the change, frozen and still reportable afterwards.

What is in and out of the new scope. The bridge from the old budget to the new one, line by line, so the £5.2m is visible as a line rather than absorbed. And the name and date of the approver.

Then report against both baselines for the rest of the job. It is the only way anyone sees the size of the reset a year later.

One more reason this is not a scheduling task. A change in expected total costs changes the measure of progress under an input method, so the margin gets restated in the period the estimate moves. The planner presses the button. The accounts carry the consequence, and it is the same event.
