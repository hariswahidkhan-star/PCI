# PCI Platform — Incremental Test Coverage Matrix

_Audit-first output of the Master Incremental Testing Programme (Section 1). Produced by a read-only fan-out audit (one agent per module) against the actual repository. This is the baseline before any new test is written — it records what EXISTS, what is MISSING, and the minimal increment to add. It does not claim the platform is defect-free._

## Existing test surface (baseline)

- **Backend (strong, API/integration layer):** ~680 live-HTTP assertions across `backend/tests/` — `integration_test.py` (567 `chk`), `founding_test.py` (46), `honorary_test.py` (19), `honorary_application_test.py` (48), `sweep_500_test.py` (every `/api/*` route × anon/student/owner), logic suites (`lifecycle/release/casework/settings/publication/storage`), `storage_s3_test.py` (moto). Runs in CI on **SQLite and MySQL**.
- **.NET unit tests:** only `secureexam/PCI.SecureExam.Tests` (xUnit ×4). `PCI.Backend` has **no** xUnit unit project.
- **Frontend:** `tsc --noEmit` typecheck only — **no** Vitest/RTL component tests, **no** Playwright E2E, no axe/visual.
- **Absent layers:** component, browser-E2E, accessibility, visual, contract, k6 performance, dependency/secret/SAST scans, mutation.
- **Environment limit:** outbound egress is blocked in the build/test environment, so live external-provider (Stripe/Certuvo/exam-vendor/WhatsApp/Meta/Google), Render-deployment, real backup/restore/DR, and production-scale load tests are classified **External Provider / Operator Required** — documented, not simulated as if real.

### Findings surfaced while adding coverage (not defects introduced; recorded, not fixed here)

- **`/api/verify` treats a `suspended` credential as valid.** The public verify endpoint (`Endpoints/Public.cs`) computes `state` as `revoked` / `expired` / `active` only, so a `suspended` credential falls through to `active` and reports `valid: true` — while the download gate (`Endpoints/Certificates.cs`) correctly blocks it with a 403. §31 therefore asserts only the (correct) download-gate behaviour and does not assert verify for suspended. Candidate one-line fix for a later change: fold `suspended` into the non-active branch of the `state` computation. Left unchanged here to keep this a test-only PR.
- **Membership has no time-based expiry sweep** (§35): every gate reads the `status` column literally, so a `memberships.expiry_date` in the past with `status='active'` still grants access. Only an explicit `status='expired'` (set on payment reversal) revokes it. §35 codifies both behaviours. A time-based expiry sweep would be a product decision, not a bug fix.
- **The blog scheduled-publish due-sweep has no on-demand HTTP hook** (§36): `ScheduledPublisher.PublishDue` only runs on a 60s background timer, unlike the social dispatcher's `POST /api/admin/content/social/drain`. §36 therefore asserts the queued (scheduled, non-public) state rather than firing a sweep. A parity "run scheduled now" admin endpoint would make the `scheduled → published` transition HTTP-testable (and give operators a manual trigger).
- ~~**Partner commission accrual from a paid redemption is not yet asserted** (§37)~~ — **closed by §41.** The ledger is derived from `code_redemptions ⋈ payments(paid)` scoped to the partner's discount codes; §37 asserted only the shape. §41 now drives a real partner-code redemption through the signed webhook and asserts `accrued == attributed × pct/100` (119 × 20% = 23.80) and the payout deduction (balance = accrued − paid_out).

## Cross-cutting structural findings

1. **Backend business logic is validated only at the HTTP/integration layer.** Pure functions (fee/discount math, exam eligibility, attempt limits, certificate rules, reminder stop-conditions, login lockout, TOTP replay) have no fast unit tests. Recommendation: add a `PCI.Backend.Tests` xUnit project for the pure/decision logic while keeping the Python suites as the integration/E2E layer.
2. **The entire React frontend is untested** beyond `tsc`. No component tests for forms/student/admin pages; no browser E2E; no accessibility. Recommendation: introduce Vitest + React Testing Library (unit/component) and Playwright (critical-journey E2E + axe) — new frameworks, additive, wired into the existing `frontend` CI job.
3. **Client-side auth guards are UX-only** (real authorization is server-enforced and well-tested); the per-section admin 403 gate is spot-checked on ~4 of ~50 sections — a cheap, high-value increment is to parametrize the existing limited-admin token across all admin section endpoints.
4. **Provider/Render/DR/perf** cannot be exercised here (egress blocked); they need staging + operator execution and are tracked as such rather than marked done.
